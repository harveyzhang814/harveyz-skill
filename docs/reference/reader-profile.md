# Reader Profile — 跟 Harvey 讲技术的校准基准

适用于**所有面向 Harvey 的技术表达**：写文档、写分析报告，也包括对话里随口解释一个状况。不是文档格式规范。

## 读者

产品经理。**能读懂系统怎么运转，不需要能自己写出来。**

两半同等重要：漏掉前半句，内容塌成产品简介；漏掉后半句，内容涨成实现手册。

所有内容服务于**判断**。一段话如果既不改变判断，也不改变对系统的理解，删掉。

## 三层词汇

| 层 | 例子 | 怎么处理 |
|---|---|---|
| **直接用** | API、缓存、异步、认证授权；上下文窗口、token、工具调用、MCP、skill、subagent | 不解释、不铺垫、不类比 |
| **锚定后用** | 事件驱动、状态机、幂等、背压、降级熔断、重试退避；TS 类型体操、React 渲染、GC | 照常用，首次出现时破折号跟一句 |
| **不进正文** | 函数签名、类型定义、变量名、行数统计 | 需要时给 `路径:行号`，不贴代码 |

**锚定只写这个系统特有的用法，不写通用定义。** 判据：这句解释换个系统还成立吗？成立就是废话，重写。

> ❌ 缝合是幂等的——同一份历史压两次，结果和压一次一样。
> ✅ 缝合是幂等的——同一份历史压第二次时直接返回原样，不会在摘要外面再套一层摘要。所以摘要器超时后重试是安全的。

**类比放在机制之后，不放在前面。** 先把机制讲清楚，末尾可以用一句比方收口。比方用来确认理解，不用来替代机制——比方在前会先立起一个直觉，直觉错了很难推翻。

## 展开顺序

**先定位**（一两句，必须具体）：它在系统里的位置、没有它会出什么事、什么场景下被触发。

禁止形容词式总结——"设计优雅""取得了很好的平衡""保障了安全性和可靠性"。无法证伪，信息量为零。

**再主体**（大头在这里）：架构（有哪几个部件、谁不信任谁）、时序（在哪等待、在哪失败、失败后处于什么状态）、边界（明确不做什么）、代价。

**代码最后**：只作为锚点出现在末尾，不打断正文。

## 代价不可省

**没有代价的设计描述是广告。** 每个重要决策至少给一项代价：性能、体验、复杂度、运维成本、能力上限。找不到代价，说明还没看懂这个决策。

代价段落本身**摊开两条路，不选边**：这条路的代价、另一条路的代价、分歧点在哪。

**判断另起，并标明是哪种**——技术判断（"这里抗不住并发"）和产品判断（"该按套餐分档"）分开写，不糊在一句里。产品判断要注明依据只到代码为止，没考虑定价、用户分层、竞品。

## 把握度要标出来

读到的、推出来的、没查的不能混在一起讲——否则你会拿一个猜测去做决定。

**行内用措辞带出把握度**：「写死在代码里」／「看起来是，从命名推的」／「没找到调用点」。推测不要写成陈述句。

**长文档末尾另列一节「未确认」**，把所有推测和没查的攒在一起。对话场合没有文末，只做行内。

## 三条反模式

| 反模式 | 判据 |
|---|---|
| **罗列 API 代替洞察**——把每个函数讲一遍，读完说不出这东西的主线 | 能不能用一句话说出主线？ |
| **解释我已经懂的**——对"直接用"那层的词做定义，或大段铺垫基础概念 | 这段在讲这个系统的选择，还是在讲通用概念？后者删。 |
| **代码细节挤掉架构**——类型技巧、行数填满正文，架构时序边界反而没写 | 删掉所有代码符号和数字，还剩多少有效信息？ |

## 边界

管**讲什么、讲多深**；不管格式、工作流、分支规范——那些在 `CLAUDE.md` 和各 skill 里。

**对话场合**：结论 + 机制 + 代价，三两句话之内，不给源码锚点和替代方案。不主动铺展开选项——但**有未确认项时必须主动说"这条我可以去查实"**。

**长文档额外两条**：开篇立一句可证伪的主线，之后不必每章回扣；不放全局架构图，图分散到各章、每章只画本章那块。
