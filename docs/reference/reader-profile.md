# Reader Profile — 给 Harvey 写文档的校准基准

这份文档定义**文档的读者是谁、他的认知边界在哪、内容应该按什么梯度展开**。任何 Agent 在为 Harvey 撰写分析报告、调研文档、方案说明、代码库解读之前，先读这里。

它约束的是**写什么、写多深**，不约束格式和工作流（那些在 `CLAUDE.md` 和各 skill 里）。

---

## 1. 读者是谁

产品经理。判断方案、评估取舍、决定做不做与怎么做，**不负责写实现**。

能力边界的正确表述是：

> **能读懂系统怎么运转，不需要能自己把它写出来。**

这句话的两半同等重要，漏掉任何一半都会写偏：

- 漏掉前半句 → 内容降级成产品简介，读完不知道系统实际怎么工作
- 漏掉后半句 → 内容升级成实现手册，把决策不需要的细节全倒出来

文档的用途是**支撑判断**，不是支撑实现。一段内容如果既不改变判断、也不改变对系统的理解，它就不该在正文里。

---

## 2. 认知基线

### 直接用，不要铺垫

这些词出现时直接用，不加定义、不加类比、不加"简单来说"：

**通用软件概念**
API、接口、数据库、缓存、同步/异步、客户端/服务端、认证与授权、请求/响应、超时、重试、日志、环境变量、并发

**AI / Agent 领域概念**
上下文窗口、token、工具调用、MCP、prompt / system prompt、skill、subagent、RAG、模型路由、流式输出、结构化输出

对这些词做解释会触发反模式 2（见第 4 节）。

### 照常用，但给一句锚定

这些是**工程语言的原生词汇**，B 层绕不开。规则不是回避——回避会让内容塌回产品层——而是**首次出现时用一句话把它钉在当前场景里**。锚定不是教学：不讲来源、不讲通用定义，只讲"在这里它意味着什么、带来什么后果"。

**工程架构模式**
事件驱动、状态机、中间件、消息队列、幂等、退避重试、降级与熔断、单飞 / 请求去重、租约与续期、乐观锁、最终一致、读写分离、背压

**具体语言与技术栈机制**
TypeScript 类型体操、React 渲染与 diff、Rust 所有权、GC 行为、具体库的 API 约定

锚定的写法：

> ❌ 回避 —— "这里做了一些处理，保证重复调用不会出问题。"
> ❌ 教学 —— "幂等（idempotent）是数学与计算机科学中的一个概念，指一个操作执行一次与执行多次产生相同结果……"
> ✅ 锚定 —— "这里做了幂等——同一个请求重发多次，结果和发一次一样。所以网络超时之后可以直接重试，不用先查一遍状态。"

一句话，落在后果上。同一个词在同一篇文档里只锚定一次。

### 只在源码锚点出现

函数签名、类型定义、变量名、行数统计、语法技巧。这些不进正文，进每节末尾的源码锚点（见第 3 节 A 层）。

---

## 3. 展开梯度：C → B → A

每一节都按这个顺序展开。这是**固定结构**，不是建议。

### C 层 — 开场，1–3 句

回答三件事，缺一不可：

1. **它在整个系统里的位置** —— 上游是谁、下游是谁、拿掉它会断什么
2. **它在解决什么具体问题** —— 用"如果没有它会出什么事"来写，不要写能力描述
3. **谁在用它、什么场景下被触发** —— 用一个真实的调用场景把抽象模块钉在具体事件上

**C 层的禁区是形容词式总结。** 以下句式一律不许出现：

- "取得了很好的平衡"
- "设计优雅 / 架构清晰"
- "保障了安全性和可靠性"
- "提供了强大而灵活的能力"

这些句子的信息量是零，且无法证伪。C 层短，但必须每句都是具体的。

### B 层 — 主体，正文篇幅的绝大部分

四类内容，**代价那一类不可省略**：

| 类别 | 写什么 |
|------|--------|
| **架构** | 有哪几个部件、各自负责什么、谁不信任谁、职责边界画在哪 |
| **时序** | 一次完整调用从头到尾经过什么、在哪里等待、在哪里可能失败、失败之后系统处于什么状态 |
| **边界** | 它明确**不**做什么、和相邻模块的分界线在哪、什么情况超出它的设计范围 |
| **代价** | 这个设计换来了什么、付出了什么、什么场景下会变成负担 |

**没有代价的设计描述是广告，不是分析。** 每个重要设计决策都要给出它的代价——性能、体验、复杂度、运维成本、能力上限，至少一项。如果找不到代价，说明这个决策还没看懂。

B 层的语言是工程语言：用架构模式的词汇，配合第 2 节的锚定规则。

### A 层 — 每节末尾的「源码锚点」

正文不被代码打断。想深入时看节末这一小块。

固定格式：

```markdown
### 源码锚点

- 四步协议的状态流转：`src/credentials/keychain.ts:142-210`
- 过期判定（读时惰性计算，不是定时任务）：`src/credentials/keychain.ts:88`
- OAuth state 签名与 nonce 校验：`src/credentials/oauth.ts:301-340`
```

一行一个：**做什么** + **`路径:行号`**。可以带少量关键代码片段，但不解释语法——语法是读者需要时自己看的，不是文档的职责。

## 4. 三条反模式

这三条是实际发生过的偏差，每条配一组对照。

### 反模式 1：罗列 API 代替洞察

把每个函数每个参数讲一遍，读完不知道这个模块到底在解决什么问题、主线是什么。

> ❌ `getCredential(id)` 获取凭证，`listCredentials()` 列出所有凭证，`revokeCredential(id)` 撤销凭证，`refreshCredential(id, opts)` 刷新凭证，其中 opts 支持 force 和 timeout 两个选项……
>
> ✅ 凭证层的主线是一个词：**借**。agent 从不拥有第三方密钥，只能走"申请 → 批准 → 物化 → 用掉"这条借还协议，每一步都留痕。对外暴露的那几个方法（获取、列举、撤销、刷新）都是这条协议上的操作，没有一个能绕过它直接拿到明文。

判断标准：读完之后能不能用一句话说出这个模块的主线。不能，就是在罗列。

### 反模式 2：解释读者已经懂的

对第 2 节"直接用"清单里的词做定义，或者用大段篇幅铺垫基础概念。

> ❌ OAuth 是一种开放标准的授权协议，它允许用户授权第三方应用访问自己在某个服务上的资源，而无需将用户名和密码提供给第三方应用。其核心流程包括……
>
> ✅ 走的是标准 OAuth，值得说的是它在标准之外加的两道：state 签名只防伪造，重放靠单独的 nonce 记录；而且去重设施不可用时**失败关闭**——宁可拒绝授权，也不放行一个可能重放的请求。

判断标准：这段话是在讲这个系统的选择，还是在讲一个通用概念？后者删掉。

### 反模式 3：代码细节挤掉架构

用类型技巧、行数、具体实现填满正文，架构、时序、边界反而没写。

> ❌ `KeychainCredentialMeta = Omit<KeychainCredential, "secretEnc">`，通过 Omit 剔除密文字段，使 `listCredentials()` 的返回值在类型层面无法携带明文。存储层是一张 `DurableMap<string, KeychainCredential>`，靠三种 ID 前缀区分三类凭证，`keychain.ts` 共 1240 行。
>
> ✅ 保密职责被下推到了类型系统：列举凭证的接口在类型上就拿不到密文，不依赖开发者记得过滤。三类凭证（长期密钥、OAuth 令牌、一次性借条）共用一张表，靠 ID 前缀区分——省了三套存储，代价是三者的生命周期规则混在同一段代码里，改任何一类都要看懂另外两类。
>
> ### 源码锚点
> - 类型层面的密文隔离：`src/credentials/types.ts:24`
> - 三类凭证共表与 ID 前缀：`src/credentials/keychain.ts:60-95`

判断标准：把所有代码符号和数字删掉之后，这段话还剩下有效信息吗？不剩，就是反模式 3。

## 5. 交稿自检

写完之后逐条对照，任何一条不过就返工：

1. **主线** —— 能用一句话说出这篇（这节）的主线吗？
2. **C 层** —— 开场三件事（位置、解决什么问题、谁在什么场景触发）齐了吗？有没有混进形容词式总结？
3. **B 层** —— 架构、时序、边界、**代价**四类都有吗？代价是最容易漏的。
4. **锚定** —— 用到的工程模式词，首次出现处有没有一句落在后果上的锚定？有没有对"直接用"清单里的词做多余解释？
5. **A 层** —— 代码级细节是否都收进了节末源码锚点，正文有没有被打断？
6. **删除测试** —— 删掉所有代码符号和数字，正文还剩多少有效信息？
