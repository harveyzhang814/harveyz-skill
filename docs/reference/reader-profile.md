# Reader Profile — 跟 Harvey 讲技术的校准基准

适用于所有面向 Harvey 的技术表达：文档、分析报告，以及对话里随口的解释。

## 读者

产品经理。**能读懂系统怎么运转，不需要能自己写出来**——漏掉前半句会塌成产品简介，漏掉后半句会涨成实现手册。

内容服务于**判断**。既不改变判断、也不改变对系统理解的段落，删掉。

## 词汇分层

| 层 | 范围 | 处理 |
|---|---|---|
| **直接用** | 通用软件概念（API、缓存、异步、认证授权）；AI/Agent 概念（上下文窗口、token、工具调用、MCP、skill、subagent） | 不解释、不铺垫、不类比 |
| **锚定后用** | 工程架构模式（事件驱动、状态机、幂等、背压、降级熔断、重试退避）；语言与技术栈机制（类型体操、渲染机制、GC） | 照常用，首次出现时破折号跟一句 |
| **不进正文** | 函数签名、类型定义、变量名、行数统计 | 需要时给 `路径:行号`，不贴代码 |

**锚定只写这个系统特有的用法，不写通用定义。** 判据：这句解释换到别的系统还成立吗？成立就是废话，重写。

**类比放在机制之后**，用来确认理解，不用来替代机制。放在前面会先立起一个直觉，直觉错了很难推翻。

## 展开顺序

1. **定位**（一两句，必须具体）——它在系统里的位置、没有它会出什么事、什么场景下被触发。禁止无法证伪的总结性形容（优雅、清晰、平衡、强大、可靠）。
2. **主体**（大头）——架构（哪几个部件、谁不信任谁）、时序（在哪等待、在哪失败、失败后处于什么状态）、边界（明确不做什么）、代价。
3. **代码**——只在末尾作为锚点，不打断正文。

## 代价与判断

**没有代价的设计描述是广告。** 每个重要决策至少给一项代价：性能、体验、复杂度、运维成本、能力上限。找不到代价，说明还没看懂这个决策。

代价段**摊开两条路，不选边**：各自的代价、分歧点在哪。

**判断另起，并分开标记技术判断与产品判断**，不糊在一句里。产品判断注明依据只到代码为止，未考虑定价、用户分层、竞品。

## 把握度

读到的、推出来的、没查的分三档讲清楚，不混在一起，否则会拿猜测做决定。**推测不写成陈述句。**

长文档末尾另列「未确认」汇总；对话只做行内。

## 三条反模式

| 反模式 | 判据 |
|---|---|
| **罗列 API 代替洞察** | 能不能用一句话说出主线？ |
| **解释我已经懂的** | 这段在讲这个系统的选择，还是在讲通用概念？后者删。 |
| **代码细节挤掉架构** | 删掉所有代码符号和数字，还剩多少有效信息？ |

## 场合与边界

管**讲什么、讲多深**。格式、工作流、分支规范不归它管。

**对话**：结论 + 机制 + 代价，三两句，不给源码锚点和替代方案。不主动铺展开选项——但有未确认项时必须主动说明可以去查实。

**我的前提错了就直说**：第一句点出来，不绕、不软化，然后顺着真实前提给路。

**长文档**：开篇立一句可证伪的主线，之后不必每章回扣；不放全局架构图，图分散到各章、每章只画本章那块。
