## 0. 主线

> **在 Pi 上做定时任务，缺的不是调度器，是"无人在场"这整套语义。** Pi 把权限、投递、常驻进程三件事全部推给了宿主环境；而这三件正好是定时任务和普通 agent 调用的**全部**区别。调度本身在 Pi 之上是最容易的一块。

这句可证伪：只要在 Pi 仓库里找到内建的权限拦截层、任何形式的消息投递抽象、或者一个设计上可以长期常驻的进程宿主，主线即被推翻。实测结果：`grep -i "cron\|schedul"` 在 Pi 的文档和 README 里只命中重试调度相关的事件名，没有任何任务调度设施；安全文档第一句就写明 Pi 以启动用户的权限运行、不含沙箱；聊天集成明确在另一个仓库（`earendil-works/pi-chat`）；`packages/server` 自己标着 experimental。

## 1. Pi 现状盘点

### 1.1 定位与包结构

Pi 自称 "agent harness project"，本体是一个可自我扩展的编码 agent。相关包：

| 包 | 作用 | 与定时任务的关系 |
|---|---|---|
| `pi-ai` | 多 provider 统一 LLM API | 间接 |
| `pi-agent-core` | agent 运行时：工具调用、状态管理 | 间接 |
| `pi-coding-agent` | 交互式 CLI，**同时也是 SDK 的发布包** | 核心依赖 |
| `pi-tui` | 终端 UI 库 | 无关 |
| `pi-server` | 实例监督进程（experimental） | 候选宿主 |
| `pi-storage` / `pi-evals` | 存储、评测 | 未评估 |

### 1.2 已有能力：对定时任务直接可用的部分

**非交互运行模式**。三种，都明确不弹交互提示：

| 模式 | 形态 |
|---|---|
| `-p` / `--print` | 打印回复后退出 |
| `--mode json` | 所有会话事件按 JSON Lines 输出到 stdout |
| `--mode rpc` | stdin/stdout 上的 JSON-RPC |

`--mode json` 的事件类型覆盖了 agent 生命周期（开始/结束）、回合生命周期、消息生命周期（含流式增量）、工具执行（开始/中途/结束，带 `isError`）、压缩、自动重试。**这是判定"这一轮算成功还是失败"的原始素材。**

**会话管理**。会话自动保存到 `~/.pi/agent/sessions/`，按工作目录组织，每个会话是一个树结构的 JSONL 文件。SDK 侧提供四种会话管理器形态：

| 形态 | 语义 | 对应定时任务的哪种绑定 |
|---|---|---|
| 内存态 | 不落盘 | 一次性的临时运行 |
| 新建 | 新的持久会话 | 隔离运行（可追溯） |
| 打开指定文件 | 复用某个会话文件 | 长期命名会话 |
| 续最近 | 接着最近一次 | （定时任务不适用） |

运行时层另外提供替换活动会话的能力（新建/切换/fork/clone）。

**工具集控制**。SDK 层的粒度比 CLI 细：

- 允许列表（只开这几个）
- 全关（`noTools: "all"`）
- 只关内置、保留扩展和自定义工具（`noTools: "builtin"`）
- 在允许列表之后再排除若干个

内置工具默认是读、bash、编辑、写；可选的还有 grep、find、ls。

**每个会话独立的工作目录**。传入自定义 cwd 时，**内置工具是按这个目录构建的**。这一点很关键：它意味着并行运行多个不同目录的任务不需要改进程的当前目录——Hermes 正是因为工作目录是进程全局的，被迫把带工作目录的任务串行化（见 [01 报告](01-hermes-openclaw.md) 1.4 节）。

cwd 同时决定了资源发现范围：项目扩展、项目 skill（`.pi/skills/` 和向上查找的 `.agents/skills/`）、项目 prompt、上下文文件（从 cwd 向上找 `AGENTS.md`）、会话目录命名。

**自定义工具**。两条路：SDK 直接传入工具定义数组，或扩展内注册。两者会合并。注意一个坑：如果同时传了工具允许列表，**必须把自定义工具的名字也写进列表**，否则它不会被启用。

**扩展系统**。这是 Pi 最强的一块，对定时任务有三处直接价值：

1. **可阻断的工具调用钩子**。在工具执行前触发，能读到工具名和参数，**参数是可变的**（就地改会影响实际执行，后续处理器能看到前面的修改，改完不做二次校验），返回阻断指令可以拒绝执行并给出理由。
2. **运行时切换活跃工具集**。可以查当前活跃工具、查全部工具的元数据（名字、描述、参数、提示词指引、来源信息），然后重设活跃集合。
3. **内联扩展工厂**。资源加载器接受直接传入的工厂函数，**不需要在磁盘上放任何扩展文件**。

**其他可用件**：注册斜杠命令、注册 CLI flag、注册快捷键、设置模型与思考等级、上下文用量查询、手动压缩、系统提示词读取。

### 1.3 明确缺失的

| 缺失 | 证据 |
|---|---|
| 任何形式的任务调度 | 全仓库文档 grep 无命中 |
| 权限系统 | README 与安全文档均明说"不含内建权限系统 / 不含沙箱" |
| 消息投递抽象 | 聊天/工作流集成指向另一个仓库 `pi-chat` |
| 稳定的常驻进程宿主 | `pi-server` 标注 experimental，CLI/API/行为均不稳定 |
| prompt 注入防护 | 安全文档明确把它划在安全边界之外 |

### 1.4 安全模型：最影响设计的一条

Pi 的安全文档立场非常明确，值得逐条记，因为它决定了定时任务层必须自己承担什么：

- Pi 以启动它的用户账户权限运行，把该用户可写的文件视为同一个本地信任边界之内
- **项目信任（project trust）不是沙箱**。它只控制要不要加载项目本地的设置、资源、包和扩展，不限制模型开始工作后能让工具做什么
- **不含内建沙箱**。内置工具能读写文件、能跑 shell 命令；扩展是以同等权限运行的 TypeScript 模块。这是**刻意的**——文档给出的理由是：一个部分沙箱很容易被误解成安全边界，但它仍然依赖宿主的 shell、文件系统、包管理器、凭证和扩展代码；真正的隔离必须来自操作系统或虚拟化边界
- **来自仓库文件、注释、文档、上下文文件或构建产物的 prompt 注入，是预期中的本地 agent 风险，Pi 无法可靠防止**
- 对于不受信仓库、不打算细看的生成代码、或**无人值守的自动化**，文档直接建议跑在容器/虚拟机/微虚拟机/受策略控制的沙箱里，只挂载任务需要的文件和凭证

非交互模式的信任行为也写明了：`-p`、`--mode json`、`--mode rpc` 不显示信任提示；没有适用的已保存决定时，默认值 `ask` 和 `never` 会忽略需要信任的项目资源，`always` 则信任；可以用 `--approve` / `--no-approve` 覆盖单次运行。

**这一节的结论**：Pi 把"无人值守要不要更安全"这个问题的答案定死为"由宿主环境解决"。所以定时任务层不是"要不要做权限"的选择题——它是唯一有机会做这件事的地方。

## 2. 宿主形态：三条路与推荐

调度器必须活在一个比任何交互会话都长命的进程里。Pi 提供的三种可能：

### 方案 A：独立守护进程（推荐）

自己写一个常驻进程持有定时器和任务存储，到点为每个任务拉起一个执行子进程。

- **优点**：不依赖 Pi 的任何不稳定 API；进程边界天然存在；崩溃隔离；可以给子进程一份收窄的环境变量
- **代价**：每次运行付一次进程启动和 Pi 初始化的开销；跨轮不共享任何内存状态

### 方案 B：挂在 `pi-server` 上

复用它已有的实例注册表和长连 RPC 子进程。从源码看，它维护实例记录、订阅事件流、管理 RPC 子进程生命周期，形状上确实是个监督者。

- **优点**：进程管理、实例持久化、事件订阅都现成
- **代价**：包自己标注 experimental，"CLI、API 和行为尚不稳定，可能变更或移除"。把调度器绑在上面等于把稳定性外包给一个明说自己不稳定的东西

### 方案 C：做成 Pi 扩展 —— 不成立

扩展文档里有一段直接否掉了这条路：**扩展工厂可能运行在从不开始会话的调用里，不要从工厂里启动后台资源，包括进程、套接字、文件监视器和定时器**；后台资源要推迟到会话开始或需要它的事件，并注册幂等的会话关闭处理器来释放。

也就是说扩展的生命周期是会话级的，设计上就不允许它持有跨会话的定时器。

### 推荐

**方案 A**。理由不是它更优雅，是它对 Pi 的耦合面最小——只依赖非交互执行这一个稳定契约。方案 B 可以在 `pi-server` 稳定之后再评估迁移。

## 3. SDK 还是 CLI：真正的分界不在这里

一个容易走偏的问题是"用 SDK 还是用 CLI 参数"。实际的分界是**要不要进程边界**，这两个问题正交：

| 组合 | 评价 |
|---|---|
| 同进程 + SDK | 能力最全，**但没有任何隔离**：agent 的 shell 工具和调度守护进程共享进程、环境变量、凭证。一个跑飞的任务能带走整个调度器 |
| 子进程 + CLI 参数 | 有边界，但配置能力被参数表卡死——动态权限规则、按任务生成的工具集，参数表里没有对应项 |
| **子进程 + SDK**（推荐） | 两头的好处都拿到 |

推荐形态是：**控制面**（调度器、任务存储、运行历史、投递、告警）是独立守护进程，不引 SDK；**执行面**是一个薄壳子进程，壳里用 SDK 组装并订阅事件，把结果写回控制面。

薄壳要做的事就四件：读任务定义 → 组装会话参数（工作目录、工具允许列表、模型、内联扩展、会话管理器形态）→ 订阅事件流 → 把最终结果和判定所需的事件写回控制面。

**SDK 相对 CLI 的关键增量**是内联扩展工厂：它让你可以**按任务动态生成一段"这一轮的规则"**（权限拦截、工具集收窄、自定义工具），而不需要往用户磁盘写扩展文件。CLI 路线要达到同样效果，得先落盘再用 `-e` 指路。

**同进程什么时候可以接受**：全部任务都是自己手写的、跑在自己机器上、产出只落盘不外发。此时上面的代价都不咬人。

**什么时候一定不行**：任务的 prompt 可能来自对话（也就是"让 agent 自己排期"这个功能）。那一刻起任务内容就是不可信输入，同进程等于把守护进程的全部权限交给一段模型生成的文本。

## 4. MVP 功能清单

假设的产品路线：**开发者在指定仓库里定时干活，产出的第一消费者是文件系统**。另一条路线的差异见第 7 节。

一句话范围：**一个人手工创建的任务，按时在指定仓库里跑一轮 Pi，产出落盘，出事能通知到一个地方。**

### 4.1 任务定义与存储

字段：名字、启用开关、调度、工作目录、prompt、工具允许列表、模型、超时、投递目标、告警目标。

定义与运行态分两份文件——定义那份可手改、可进版本控制，运行态那份（上次跑没跑、下次几点、连续失败几次）不进。这是 OpenClaw 的做法，配套要做的是「调度身份」比对：外部改了定义之后，比对调度相关字段的归一化结果，变了就重排、没变（只是格式或键顺序）就保留待运行槽位。

- **验收**：手改定义文件再重启，排期正确；删掉运行态文件，任务还在，只是当作从未跑过。
- **代价**：多一套比对逻辑；旧版本读新文件会把任务当全新的。

### 4.2 三种调度触发

一次性时间点、固定间隔、cron 表达式 + 时区。

**三条必须现在定死并写进文档的语义**（每一条都对应 [01 报告](01-hermes-openclaw.md) 里的一个真实事故）：

1. **省略时区 = 宿主机本地时区**，不是 UTC。OpenClaw 在工具描述里为这一条重复了三次。
2. **错过的只补跑最近一次**，不是全补。补跑策略两家都有各自的形态：Hermes 用"周期一半、钳在 120 秒到 2 小时"的自适应宽限期，超出就快进；OpenClaw 用"取前 N 条串行执行，其余推迟"。**MVP 建议用 Hermes 那种自适应宽限**，因为它不需要区分任务类型。
3. **先推进下次运行时间再执行**。这是至多一次的保证点。代价是执行中崩溃这一轮就丢。

**建议一并做的**：整点循环任务的抖动。用任务 id 的哈希算稳定偏移（不要用随机数，否则重启后漂移），窗口 5 分钟以内。成本很低，能避免"所有日报都在整点同时开跑"。

- **验收**：把机器挂起 3 小时再唤醒，一个每小时的任务只跑一次。
- **代价**：至多一次意味着丢；固定的哈希偏移意味着某个任务永远落在同一个偏移点上。

### 4.3 命令行管理面

增、删、改、列、看详情、暂停、恢复、立即跑一次、看运行历史。不做图形界面。

暂停必须是独立操作，不能让用户靠删了重建来实现——重建会丢掉运行历史和连续失败计数。

- **验收**：所有操作在守护进程运行中生效，不用重启。

**做完 4.1–4.3，手上就有一个不带 agent 的定时器**，可以单独验收。这是第一个应该停下来检查的节点。

### 4.4 执行 runner

每个任务起一个薄壳子进程，壳里用 SDK 组装：工作目录、工具允许列表、模型、prompt。

- **会话形态**：全新会话，**落盘**而不是纯内存——出问题要能翻当时的完整对话。
- **超时**：用不活动超时而非总时长（只要还在调工具或收流式增量就允许继续，卡死的调用才杀），默认 10 分钟。Pi 的事件流里有工具执行和消息增量事件，足够驱动这个判定。
- **产出判定**：从事件流里取最终助手文本；同时检查是否出现工具执行错误和运行级失败。**空产出要降级为失败**——[01 报告](01-hermes-openclaw.md) 里两家都补过这个洞（agent 跑完但什么都没说，被记成 ok）。

- **验收**：两个不同工作目录的任务同时到期，各自的文件工具只看得到自己那个目录，互不串。
- **代价**：每次运行付一次进程启动 + Pi 初始化开销。

### 4.5 权限层

**这一项不能延后。** 理由：4.4 一旦跑通，就已经是一个无人值守的全权限 agent 了。而 Pi 明确不提供任何权限设施。

做法：每次运行注入一段内联扩展，挂上可阻断的工具调用钩子。对外只暴露一个开关——撞到危险操作时：拒绝（默认）／放行／只记录不拦。

参考 Hermes 的两条经验：
- 默认值应该是**拒绝**。理由很直白：没人可以批准。
- 这个开关只能放宽到"自动批准可批准的操作"，**不能放宽到什么都能干**——Hermes 有一条专门的测试断言 `cron_mode=approve` 不能绕过硬性黑名单。

另外一层是真正的隔离边界：Pi 的文档建议无人值守跑在容器里。所以这一项的完整形态可能是"每个任务声明自己的隔离级别"，而不是一个全局开关。**MVP 阶段可以只做钩子这一层，但要在文档里明确写出它不是安全边界。**

- **验收**：一个 prompt 里含破坏性命令的任务，默认配置下被拦，且**运行历史里看得到拦截原因和被拦的具体命令**（只写"失败"是不够的，用户会以为是模型问题）。
- **代价**：需要提权的任务会失败，用户必须去看运行历史才知道原因。

### 4.6 产出与投递

两条路：产出写成 markdown 落盘（按任务分目录、带时间戳）+ 一个 webhook POST。

**静默协议必须一起做**：约定一个标记，agent 说"这次没什么可报的"就不投递，**但仍然落盘**。

两条来自 [01 报告](01-hermes-openclaw.md) 的具体要求：
- 禁止"半沉默"。Hermes 的执行须知里明确写了不许把静默标记和内容混在一起——说明模型确实会输出"[SILENT] 另外我还发现……"。
- 失败的任务**总是**投递错误告警，不受静默影响。否则一个坏掉的看门狗会安静地坏下去。

- **验收**：连续三次静默运行，webhook 端零请求，磁盘上三份记录。
- **代价**：没有真正的聊天渠道；要进 IM 得在 webhook 那头自己转。

### 4.7 运行历史与失败告警

每次运行记一条：开始/结束时间、成功与否、错误、产出文件路径、token 用量与成本（事件流里有）。

告警：连续失败 N 次触发，走**独立配置**的目的地——任务自己的投递目标可能正好就是坏的那个。告警后进退避，成功一次重置计数。

退避可以直接抄 OpenClaw 的表：30 秒 → 60 秒 → 5 分钟 → 15 分钟 → 60 分钟。

- **验收**：把 API key 改错，第 3 次失败时收到一条告警，之后不再刷屏。
- **代价**：无。这一项是纯收益，只是要记得做。

### 4.8 建议留在 MVP 的第八项：组装后的 prompt 扫描

容易被砍，但我建议留。

理由：只要任务支持加载 skill 或把文件内容读进 prompt，这个洞就立刻存在。Hermes 踩过一次——创建时只扫了用户填的 prompt，而 skill 内容是运行时从磁盘加载的，从来没被扫过，一个恶意 skill 就能把注入载荷直送进这个自动批准的非交互 agent。

后补很贵，因为要改执行路径；现在做只是在 4.4 里多一步。

**同时要诚实标注它的能力上限**：Hermes 的扫描器是 10 条正则加不可见字符检测，绕过成本极低。它拦的是直白的载荷，不是有意的攻击者。

- **验收**：一个引用了含注入载荷 skill 的任务，执行前被拦，运行报告里写明命中了哪条模式、要求审计哪个 skill、以及误报时怎么改。
- **代价**：每次执行多一次全文扫描；误报会让任务直接不跑，所以必须有清晰的申诉路径。

## 5. MVP 明确不做

| 不做 | 理由 | 要接受的后果 |
|---|---|---|
| agent 自己排期 | 一进来就要同时解决"模型写的任务可不可信"和"跑起来的任务能不能再建任务"两个信任问题 | 用户只能命令行建任务，对话里说"下周提醒我"没用 |
| 会话延续 / 命名会话 | 会话污染和上下文膨胀的处理没想清楚 | "基于昨天的日报写今天的"做不了 |
| 多渠道投递 | 聊天集成在 Pi 的另一个仓库，接进来是独立工作量 | 只能落盘和 webhook |
| 任务间产出链接 | 依赖编排语义（等不等上游）要单独设计 | 两步流程只能拆两个任务靠时间错开 |
| 自动重试 | 重试语义和"至多一次"纠缠 | 网络抖一下就是一次失败，靠告警和下一次调度自愈 |
| 纯脚本模式 | 见下 | 每个任务都要过模型 |

**关于纯脚本模式的补充**：Hermes 的 `no_agent`（脚本本身就是任务，stdout 原样投递，空 stdout 等于静默）是一个被低估的功能——很多"定时任务"根本不需要 LLM。但它在 Pi 上等于绕过 Pi 本身，属于另一个产品。MVP 不做，但如果用户开始抱怨"就为了发一句磁盘告警还要付一次模型调用"，这就是第一个该补的。

## 7. 另一条产品路线的差异

如果目标不是"在仓库里干活"而是"个人助理式提醒"，两项要换：

- **4.6 提到第一优先**，且落盘不算数，必须有一个真实的投递渠道。这意味着要先解决 Pi 的聊天集成在另一个仓库这件事——是接 `pi-chat`，还是自己定义一个投递适配器接口，这是一个需要先做的独立决策。
- **4.4 里的工作目录可以先不做**，换成"创建时捕获的上下文"：用户在哪说的这句话，结果就回哪去。Hermes 的 `origin` 字段就是这个东西，而且它记了线程/话题 id——工具描述里专门警告不带话题 id 会丢掉定位，说明"提醒发到了群里但不在原话题下"是真实痛点。

**这两条路线的分歧点是：产出的消费者是文件系统还是人。** 建议动手前先定死。

## 8. 判断

### 技术判断

**1. 这个项目的难点不在调度，在执行契约和权限。** 调度器写完两天就稳了；"这一轮带什么、能干什么、跑完谁知道"会改半年。[01 报告](01-hermes-openclaw.md) 的证据支持这一点：两家能追溯到 issue 编号的补丁里，调度侧的事故虽然多（热循环、静默死亡、48 小时跳跃），但都是有限的、可枚举的状态机问题；而执行契约那侧（模型选择优先级、投递目标推断、结果判定、资源泄漏）是持续演化的。

所以建议先把执行契约的数据结构定死，调度器反而可以粗糙起步——OpenClaw 那套精细的定时器逻辑是被真实 bug 逼出来的，不是设计出来的。

**2. Pi 没有权限系统这件事，是双面的。** 好的一面：不用去适配一套别人定义的权限模型，可以直接按"无人在场"的语义从零定义，而且 Pi 给了刚好够用的原语（可阻断的钩子 + 运行时工具集切换 + 内联扩展工厂）。坏的一面：安全责任全在这一层，出事没有上游可以指望，而且**必须在文档里诚实地说明它不是安全边界**，否则用户会误以为有保护。

**3. Pi 的 per-session 工作目录设计，让并行比在 Hermes 上更干净。** Hermes 因为工作目录是进程全局的，只能把带目录的任务串行跑；Pi 的内置工具是按传入的 cwd 构建的。但这只是缓解，不是消除——进程级共享的东西（环境变量、Node 全局状态、走进程当前目录的第三方代码）还在。**这一点建议动手前写个两会话并行的小实验验证。**

### 产品判断

*依据只到代码和文档，未考虑定价、用户分层、竞品。*

**1. 如果第一版就要"agent 自己排期"，那子进程边界不是可选项，必须先做。** 反之如果第一版只做人工创建的任务，同进程能快两周，之后加子进程是一次局部重构——把参数组装和事件订阅那段搬进另一个入口文件，控制面不用动。这个重构成本可控，**值得先快后稳**。

**2. 静默协议的产品价值远超它的实现成本。** 一个每小时运行的任务如果每次都说话，用户三天内就会关掉它。这是这类产品的存亡开关，不是优化项。

**3. 权限层的用户体验决定了它会不会被关掉。** 默认拒绝是对的，但如果被拒绝时用户只看到"任务失败"，他们会直接把开关改成放行——那就等于没做。所以"拦截原因写进运行历史"不是锦上添花，是这个功能能不能存活的前提。

**4. MVP 之后的第一优先级，我判断是「会话延续」而不是「多渠道投递」。** 理由：`session:<id>` 这类长期命名会话是这堆功能里唯一一个**新能力**（让定时任务能积累历史，日报可以基于昨天的日报），其余大部分复杂度都是在补"无人在场"带来的坑。这条依据只到功能性质，没有用户访谈支撑。

## 9. 未确认项汇总

1. **Pi 同进程多会话并行的真实行为**没有验证。第 3 节和第 8 节技术判断 3 里关于"进程级共享仍在"的说法，是从"Pi 无沙箱 + Node 单进程"推的，**不是实测**。建议动手前做实验。
2. **内联扩展工厂在阻断钩子上的完整能力**没有验证。扩展文档在扩展章节给了可阻断钩子的例子，SDK 文档给了内联工厂的用法，但**没有一处明说两者组合起来行为一致**。这是权限层方案成立的前提，优先验证。
3. **事件流是否足够判定"这一轮算成功还是失败"**没有验证。事件类型清单里有工具执行错误标志和 agent 结束事件，但运行级失败（provider 报错、重试耗尽）是否有独立信号、终态文本从哪个事件取，我只看了类型定义没有实跑。4.4 的产出判定质量完全取决于这个。
4. **`pi-server` 的实际稳定性与 CLI 面**只看了监督者源码的形状和 README 的 experimental 声明，没有跑过。方案 B 的可行性评估基于这些间接证据。
5. **`pi-chat` 仓库**没有看。它可能已经有投递层，那会直接改变 4.6 和第 7 节的结论。**建议动手前先看一眼。**
6. **`pi-storage` 和 `pi-evals`** 两个包完全没看，不排除里面有可复用的持久化设施。
7. **RPC 模式的完整能力**（`rpc.md` 有 1576 行）只读了 SDK 文档里的对照段落，没有通读。如果方案 A 的薄壳想用 RPC 而不是 SDK，需要补读。
8. **性能数据**全无。"每次运行付一次进程启动 + Pi 初始化开销"这句没有量化，实际是几百毫秒还是几秒未知，这会影响分钟级任务的可行性。
