# Agent 权限模块横向调研 — 调研 Spec

**日期**: 2026-08-19
**类型**: 调研任务规格（非实现计划）
**方法论依据**: `~/Projects/harvey-agent/docs/how-to/analyze-agent-systems.md` v1.0 —— 本 spec 是该方法论在「权限与审批」这一垂直议题上的实例化，复用它的取舍矩阵、隐含假设、模式词汇表、Feature Card 四类产物格式，收窄它的议题范围。

---

## 1. 主线

> 六家 agent 系统在「权限」上的真正分歧，不在拦不拦，而在**一次「同意」被记成了什么** —— 记成一次调用、一个工具、一类命令模式，还是一个信任域。这个「记什么」的选择，同时决定了重复打扰率和误批敞口，且两者不可兼得。

这句是可证伪的：如果调研发现六家的决策单元高度趋同、差异只在 UI 措辞，则主线证伪，总纲改写为「分歧在别处」。

## 2. 调研要回答的问题

核心问题：**已经审批过的状态，如何被转换、存储、泛化，使得下一次同类操作不再打扰用户。**

这个问题不能直接问，它会得到六份功能罗列。拆成 §3 的八个切面后才可对比。

## 3. 分析框架：八个切面

六家全部按同一组切面作答，缺项写「未查到」而非省略。切面 2、3、5 是核心问题的正身，其余是使其可解释的上下文。

### 切面 1 — 拦截点

审批发生在调用链的哪一环：LLM 决策后 / 工具分发前 / 参数解析后 / 沙箱系统调用层？谁不信任谁（宿主不信任模型？宿主不信任工具实现？工具不信任参数？）

要害：拦截时拿得到的信息决定了记忆粒度的**上限**。只拿得到工具名，就不可能实现基于参数的泛化。

### 切面 2 — 决策单元

一次「同意」的作用对象是什么：

- 这一次调用（一次性）
- 这个工具（工具级）
- 这一类命令 / 参数模式（模式级）
- 这个路径或域名前缀（资源级）
- 这个会话 / 项目 / 设备（信任域级）

要害：作用对象越抽象，复用率越高，误批敞口越大。找出每家**默认**落在哪一级，以及用户能否手动升降级。

### 切面 3 — 生命周期

批准活多久：单次 → 本轮 → 本 session → 本项目 → 全局永久。

- 层级升迁由谁触发：用户显式选（"always allow" 类选项）？系统按频次自动学习？配置文件预置？
- 有无降级或过期机制？
- 进程重启、session resume、机器重装分别会丢掉哪一层？

### 切面 4 — 持久化与作用域

- 存储介质：内存 / 配置文件 / 数据库 / keychain
- 索引 key 的构成：工具名？命令字符串 hash？归一化后的 pattern？cwd？项目根？设备 ID？
- 作用域边界：跨 session 是否共享，跨项目是否共享，跨设备是否同步
- resume / 冷启动时如何重建这份状态，重建失败时的行为

### 切面 5 — 泛化与匹配（核心机制）

从「这一次」到「这一类」的转换规则。已知的谱系，由弱到强：

| 档 | 机制 | 复用率 | 误批敞口 |
|---|---|---|---|
| 0 | 不泛化，每次都问 | 无 | 无 |
| 1 | 精确匹配（命令原文 / hash） | 极低 | 极低 |
| 2 | 前缀 / glob（路径、域名） | 中 | 取决于前缀选得多宽 |
| 3 | 结构化 pattern（命令拆解后按 argv 形状匹配） | 高 | 中，取决于哪些位置被通配 |
| 4 | 规则 DSL（用户手写的 allow/deny 表达式） | 高 | 由用户承担 |
| 5 | 模型判定（让 LLM 判断这次是否属于已批准的那一类） | 最高 | 高，且不可预测 |

对每家：落在哪档、有无多档混用、**归一化规则是什么**（大小写、路径符号链接、相对路径、shell 展开、管道与复合命令怎么拆）。

归一化是这一切面最容易出安全洞的地方，要专门查：有没有「批准了 `git status`，结果 `git status; rm -rf /` 也被放行」这类绕过，以及各家的防护做法。

### 切面 6 — 撤销与可审计

- 批错了怎么收回：有无撤销入口，撤销粒度与批准粒度是否对称
- 用户能否查看自己累计批准了什么（清单在哪、可读性如何）
- 批准状态被污染后（误批一条过宽的规则）的恢复路径
- 有无审批日志 / 审计轨迹

### 切面 7 — 审批 UX

- 提示文案给用户看到了什么信息：工具名？完整参数？影响范围？风险说明？
- 选项集合有哪些（典型：允许一次 / 总是允许 / 拒绝 / 拒绝并说明），默认选中哪个
- 键盘交互、误触保护
- 超时行为
- 批量场景：一次要批多个工具调用时怎么呈现

### 切面 8 — 无人值守降级

cron、headless、后台任务、CI 场景下：

- 有无「非交互模式」开关，开关打开后审批怎么处理
- fail-safe 朝哪边倒（无人应答时默认拒绝还是默认放行）
- 有无「预授权」机制专供无人值守使用
- 降级时的可观测性（用户事后怎么知道发生了什么）

### 横切要求：每个切面必须给出代价

每个切面的结论后面强制附一条代价，格式：这个选择在什么场景下会变成问题。找不到代价的条目视为未完成，标注「代价未识别」而非留空。

### 为什么名单是这六家

前四家（Claude Code、Codex、Hermes、OpenClaw）是问题提出时指定的对象。补入两家的理由：

- **Pi** —— 六家里唯一的「程序化 SDK 形态 + 权限委托给扩展层」样本，其余五家都是 CLI 形态、权限内核自带。这个形态对照本身是调研价值所在：当权限不由框架实现而由使用方实现时，框架必须暴露什么原语才够用。
- **Claude Agent SDK** —— 与 Claude Code CLI 同厂但形态相反（宿主代理审批 vs 终端自审批），可以在控制变量的条件下看出「形态」对权限设计的影响有多大。

### 路线差异带来的把握度不对称

Claude Code 与 Codex 恰好是审批 UX 打磨最成熟的两家，却只能拿到「中」把握度。总纲里凡涉及这两家的内部机制推断，必须标推断而非结论。**代价：这两家的结论对决策的支撑力天然弱于源码可读的三家，横向对比表在「泛化与匹配」「持久化」两列会出现精度不齐。**

## 5. 隔离约束（双层）

本调研刻意与「调研结果将要服务的目标系统」隔离，防止调研方向被目标系统的现有实现反向裁剪。

### 第一层：subagent 不知道目标系统存在

六个分报告 subagent 只拿到 §3 的八切面框架和 §4 的自家路线。它们：

- 不被告知目标系统是什么、叫什么、已经做了什么
- 不写「对我们的启示」「值得借鉴」「建议采用」这类章节
- 只描述这一家怎么做的、代价是什么、边界在哪

### 第二层：本 spec 正文不记录目标系统的现状

本 spec 不描述目标系统当前的权限实现。目标系统在本 spec 中只以抽象形态出现：

> 一个宿主进程内嵌、由程序化事件流驱动、跨重启常驻的 agent。

这个描述足以让总纲第 6 章的启示有收件人，不足以让人从中反推「已经做了什么、还缺什么」。

### 收敛时机

「对目标系统的启示」只在总纲中出现，在全部六份分报告落地之后统一撰写。届时才去读目标系统的实现现状 —— 此时框架已定死，读现状只用于对位，不得回头修改调研框架或补做调研。

**代价**：spec 里没有目标系统的现状当锚点，就没有现成的「缺口清单」，第 6 章启示的收敛完全押在总纲第 2 节的分歧点矩阵上。如果六家做法高度趋同、矩阵摊不开，启示章会偏薄。这个风险被接受，理由是反方向的偏差（用现状裁剪调研）更难在事后察觉。

## 6. 执行编排

六个 subagent 并行，模型 sonnet，统一 prompt 模板，统一输出 schema。

### 统一 prompt 模板

```
你是一名 AI 产品经理的技术调研助手。任务：把 <对象名> 的权限/审批模块拆解清楚，
产出一份供产品决策使用的机制报告。

【你的调研对象】
<对象名>
路线：<源码 / 黑盒 / 半黑盒>
依据来源：<路径 / commit / 文档入口 / 本地配置文件>

【核心问题】
已经审批过的状态，如何被转换、存储、泛化，使得下一次同类操作不再打扰用户。

【必答的八个切面】
1. 拦截点：审批在调用链哪一环发生？拦的是工具名还是工具名+参数？谁不信任谁？
2. 决策单元：一次「同意」作用于什么对象（一次调用 / 一个工具 / 一类模式 /
   一个资源前缀 / 一个信任域）？默认哪一级？用户能否升降级？
3. 生命周期：批准活多久？层级升迁由谁触发？有无过期或降级？重启 / resume /
   换机分别丢掉哪一层？
4. 持久化与作用域：存哪？索引 key 由什么构成？跨 session / 跨项目 / 跨设备
   是否共享？冷启动如何重建，重建失败怎么办？
5. 泛化与匹配：从「这一次」到「这一类」的转换规则落在哪一档
   （不泛化 / 精确匹配 / 前缀 glob / 结构化 pattern / 规则 DSL / 模型判定）？
   归一化规则是什么（大小写、符号链接、相对路径、shell 展开、复合命令拆分）？
   有无已知的绕过路径与对应防护？
6. 撤销与可审计：怎么收回？撤销粒度与批准粒度是否对称？用户能否查看累计批准
   了什么？误批一条过宽规则后的恢复路径？有无审计日志？
7. 审批 UX：提示里展示了哪些信息？选项集合是什么？默认选中哪个？超时行为？
   批量审批怎么呈现？
8. 无人值守降级：非交互模式怎么处理审批？fail-safe 朝哪边倒？有无预授权机制？
   降级后用户事后如何知情？

【硬性要求】
- 每个切面的结论后必须附一条「代价」：这个选择在什么场景下会变成问题。
  找不到就写「代价未识别」，不许留空，不许用「灵活」「健壮」这类无法证伪的词搪塞。
- 每条结论标注把握度，三选一：
  [读到] —— 直接读到源码或官方文档明文，附 `路径:行号` 或文档 URL
  [推断] —— 由读到的内容推导，写清推导链条
  [未查] —— 没查到，写清楚缺口在哪、去哪能查到
  三档不许混写。推断不许写成陈述句。
- 源码路线：所有关键结论必须有 `路径:行号` 锚点，并在报告开头声明分析覆盖了哪些文件。
- 黑盒路线：必须区分「文档明说」「实测观察到」「推断」，实测要写清怎么测的、
  观察到什么。
- 不要解释通用概念（什么是 allowlist、什么是最小权限原则）。只写这个系统的选择。
- 不要写「对我们的启示」「值得借鉴」「建议采用」任何章节。你不知道调用方是谁，
  也不需要知道。只描述这一家。

【输出】
Markdown，写入 <报告路径>。结构见下方 schema，章节顺序不得调整。
```

## 7. 总纲结构

全部六份分报告落地后，由主 agent 撰写，不外包。

1. **主线** —— 一句可证伪的判断（§1 的主线在此确认或改写）
2. **分歧点矩阵** —— 六家在「批准状态复用」上的理念分歧。是分歧不是功能对比：同一列里各家的差异必须能追到不同的前提假设，追不到的列删掉
3. **决策单元 × 生命周期定位图** —— 二维网格，标出每家落在哪个格子；空着的格子单独讨论「为什么没人做这里」
4. **泛化机制谱系** —— 按 §3 切面 5 的档位排列六家，每档给出误批敞口与漏打扰率的方向，以及归一化绕过风险
5. **可复用模式词汇表** —— 沿用方法论 §5.3 的模式描述格式（模式名 / 别名 / 问题域 / 解法 / 代码特征 / 收益 / 代价 / 适用条件 / 已知实现 / 标签），追加进现有的 7 个模式
6. **对目标系统的启示** —— 分三档：可直接采用 / 需改造后采用 / 应避免。每档附理由，理由必须指回前五章的具体结论。产出 3–5 张 Feature Card（方法论 §5.4 格式）
7. **未确认项汇总** —— 六份分报告 [未查] 条目的合并去重，按「是否影响启示章结论」排序

### 总纲的读者约定

总纲面向产品经理：要读懂系统怎么运转，不需要能自己写出来。约束依 [docs/reference/reader-profile.md](../../reference/reader-profile.md)：

- 技术判断与产品判断分开标记；产品判断注明依据只到代码为止，未考虑定价、用户分层、竞品
- 把握度三档不许混写
- 不放全局架构图，图分散到各章，每章只画本章那块
- 无法证伪的形容词（优雅、清晰、健壮、灵活）一律不用
- ASCII 图不使用 Unicode 制表符

## 9. 明确不做什么

- **不做实现**。本调研的产物是报告与 Feature Card，不含任何代码改动、不含实现计划。实现计划是后续独立任务。
- **不做 Phase 5 闭环验证**。方法论的实验设计与模式移植实验不在本次范围，留待启示章的 Feature Card 进入排期后再谈。
- **不覆盖认证与身份**（谁是用户、怎么登录）。只覆盖「已确认身份的用户，如何授权 agent 的具体操作」。
- **不覆盖沙箱与隔离的实现细节**（容器、seccomp、文件系统 namespace）。沙箱只在它影响审批决策时被提及（例如「沙箱内的操作免审批」这类规则）。
- **不覆盖 prompt injection 防护**。它是相邻问题，不是同一个问题。
- **不做商业 IDE agent 对照**（Cursor、Windsurf 等）。已在名单讨论中排除，理由是无源码、把握度过低。

## 10. 已知的未确认项
