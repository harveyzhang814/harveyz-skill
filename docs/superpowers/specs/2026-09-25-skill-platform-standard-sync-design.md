# Skill 平台适配标准单源分发设计

## 决策与目标

采用“仓库内一份权威标准 + 自动生成随 skill 安装的副本”。权威文本为 `docs/reference/skill-platform-adaptation.md`；它目前只在 `doc/skill-platform-adaptation-standard` 分支，尚未进入 `staging`。本设计不直接合并该分支。实施前须先让权威文本出现在从明确 `staging` 基线创建的实施分支中，并确认其最终集成方式；不能让已安装 skill 依赖仓库中不存在的文档。

目标是新建和导入 skill 时使用同一套判定边界，同时保留各 skill 单独安装后的离线可读性。规则不得把所有 skill 强制改为七宿主通用：有意限定的宿主或研究对象可以保留，但必须说明范围，不能冒称通用。`publish-skill` 继续负责格式、索引、版本和打包，不承担模型对语义兼容性的自动裁决。

## 文件与权威关系

| 文件 | 职责 |
|---|---|
| `docs/reference/skill-platform-adaptation.md` | 唯一手工编辑的完整平台适配标准 |
| `skills/mint/init-skill/references/platform-adaptation.md` | 从权威文本确定性生成的完整装机副本 |
| `skills/mint/contribute-skill/references/platform-adaptation.md` | 同一权威文本的完整装机副本 |
| 两个消费者的 `SKILL.md` | 指明何时读取本地副本、如何报告检查结果，并保存自动生成的标准摘要标识 |
| `skills/mint/init-skill/references/skill-standard.md` | 保留通用设计哲学；只写适配标准的调用点及两类附属文件的分工，不复制平台规则全文 |

同步脚本从权威文本读取原始字节，计算 SHA-256，给两个副本写相同的生成说明和源摘要，并在两个消费者的 `SKILL.md` 中更新一处机器维护的摘要标识。输出不含时间戳等非确定性字段。人工改副本属于漂移；检查模式必须报错，不自动覆盖。应用模式只更新这两个副本和两个摘要标识：先在内存中生成四份目标内容并校验源文件与目标结构，再备份原文件、写临时文件并替换；任一替换失败时恢复已替换的文件，恢复失败则报告准确路径并停止，不继续版本或发布步骤。

当前 `contentHash` 只对去除 `version:` 差异后的 `SKILL.md` 计算，不能感知单纯的引用文件改动。消费者 `SKILL.md` 中的源摘要标识使权威标准变化时其 `contentHash` 也变化；随后按现有发布规则递增两个 skill 的版本并更新 `skills-index.json`。同步脚本不自行决定版本号，不直接改索引，不合并、推送或部署。

## 适配内容的统一分类

共享 `SKILL.md` 保存任务顺序、输入输出、授权点、失败条件及能力缺失时的回退或安全停止。短小的宿主差异可放共享正文的明确适配章节；较长的 agent 宿主调用接口（工具名、委派、等待、worktree 进出、调度入口）放 `platforms/SKILL.<host>.md`。`references/<dim>/` 用于领域或技术栈资料；`references/platform-adaptation.md` 是两个编写入口的标准副本，不是某个宿主的运行适配器。现有 `skill-standard.md` 中“平台/技术栈特定内容放 `references/<dim>/`”须按此区分修订。

任何平台适配文件都不得改写共享流程的任务语义。独立适配文件必须在发布包内，且共享入口说明何时读取。没有对应适配文件时，如共享流程有可执行回退则执行回退；核心能力无法替代则说明边界并停止。安装时替换只用于安装时已知、稳定的值；运行时能力仍须现场确认。

## 消费者流程

`init-skill` 在现有 Step 2 读取 `skill-standard.md` 时一并读取本地 `platform-adaptation.md`。提炼要素时增加目标宿主或有意限定范围、核心能力、路径来源、适配点及验证状态；缺信息按现有“一次一问”策略澄清。标准检查输出可核查的“通过／缺口／不适用”及理由。Step 3 只在确有宿主差异时生成短适配章节或 `platforms/` 文件，并在用户预览与确认后把所需文件一并写入；不机械生成七份空白适配器，不把“可安装”写成“已运行验证”。

`init-skill` 自身也按相同规则校准：将“由 Claude 推断”和固定 `Read`／`Write` 工具名改为当前 agent 的能力表述。其 Git 写入顺序改为：设计与预览保持只读；获用户确认后，从明确的 `staging` 提交创建独立分支与 worktree、配置仓库 hooks，再在该 worktree 写入新 skill 并提交。若宿主有可靠的原生 worktree 入口，可使用该入口；否则使用带显式路径的 Git fallback。不得先在 `staging` 工作区写文件再建分支，也不自动合并、推送或部署。

`contribute-skill` 在源目录确认、复制目标摘要与用户确认之间加入同一标准的评估：区分有意限定、已确认断点和未经实测风险；必要时把宿主调用从共享入口移入适配点。不得仅凭某个宿主目录存在就把来源当成通用路径。原有“同步回源需用户确认”和失败保留边界不变。

`publish-skill` 不增加“语义兼容通过”结论；它只验证上述生成副本在 npm 包中、版本与索引一致，并提示缺少运行验证的适配器仍为“未验证”。既有格式与注册职责不变。

## 验收与边界

1. 修改权威文本后，检查模式先报告两个副本和两个摘要标识过期；应用同步后检查模式通过，重复同步不产生 diff。直接改任一副本时检查模式失败。
2. `npm pack --dry-run --ignore-scripts --json` 能列出两个副本；两个 skill 从各自安装目录读取标准，不需要仓库 `docs/` 路径。
3. 用至少三个受控案例核对创建／导入检查：宿主专有命令无回退、明确单宿主限定、以及共享流程有顺序回退。报告区分断点、限定和待实测，不把文本检查称为端到端兼容。
4. 隔离 worktree 测试证明 `init-skill` 写入与提交均不发生在 `staging` 工作区；已存在目标目录、脏工作区或缺少可靠工作区入口时安全停止。
5. `SKILL.md` 版本、`skills-index.json` 的 `contentVersion`／`contentHash` 与生成副本同步；保留 `npm test` 的实际结果和未覆盖宿主，不以豁免或跳过冒称全绿。

不在本设计内：修改所有已发布 skill、为七个宿主补齐运行适配器、改变全库 `contentHash` 算法、安装时按 target 渲染宿主行为，以及自动合并／推送／部署。若实施时发现必须改变这些边界，先提出独立设计，不在同步脚本里暗中扩展。
