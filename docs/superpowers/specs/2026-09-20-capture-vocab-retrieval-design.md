# capture-vocab 检索机制重构设计

- 日期：2026-09-20
- 状态：设计已确认，待实施
- 影响 skill：`skills/coding/capture-vocab`（`1.1.2` → `1.2.0`）
- 影响项目：agent-canvas（仅 `CLAUDE.md` 一节）

## 主线

**词汇表进上下文的成本，取决于切片工具，不取决于存储格式。** 加一个脚本把切片做在 shell 里，
`vocab.md` 一个字节都不用改，三类检索场景的成本全部降到与词汇表总量无关——除了语义查重，
那一项线性不可消除，只能压低斜率并封顶。

这句话可证伪：如果实施后仍需改动 `vocab.md` 的格式才能达成成本目标，主线就是错的。

## 1. 定位与现状

### 1.1 这个 skill 在系统里的位置

`capture-vocab` 维护项目级领域术语字典，落盘在 `<project-root>/.hskill/capture-vocab/vocab.md`。
它解决的是「同一个东西在人、代码、文档里叫法不一致」——没有它，agent 会把项目自造名词
按字面理解，或者在输出里用上早已废弃的旧叫法。

当前唯一实际使用者是 agent-canvas：33 条术语、23008 字节、21 次提交（每次一条术语），
文件被 git 追踪。

### 1.2 三类检索场景，及其频率

| # | 场景 | 频率 | 需要什么 |
|---|---|---|---|
| 1 | `add` 时查重：新词是否与已有词条重复 | 低 | 语义判断 + 代码引用关系 |
| 2 | agent 不确定用户说的词指什么 | **高** | 该词有无定义；有则要定义正文 |
| 3 | agent 判断某词在 vocab 里有无明确定义 | **高** | 有无即可，多数时候答案是「无」 |

**贵的操作正好是最低频的那个。** 这决定了整个设计的成本分配策略：把线性成本全部压到
场景 1，让场景 2/3 的成本与词汇表总量无关。

### 1.3 今天的真实状态（不是文档里写的状态）

SKILL.md 文档建议在 `CLAUDE.md` 里写「每次 session 开始读取 vocab.md」。**agent-canvas
没有照做**，它手工写了缓解：

> 先用检索（如 grep）在词汇文档 `.hskill/capture-vocab/vocab.md` 里查该词条，
> 不要把整篇文档读进上下文。

所以本设计的净增量不是「省掉 session 开头的 8–10k」，而是相对这个手工 grep 方案的增量：

- **别名匹配**：grep 按字面，查「抽屉」找不到「工作区」（「抽屉」在该条的 `_Avoid_` 里）
- **section 边界精确**：grep 出行号后由模型自己圈范围，实际多半会多读
- **未命中成本**：手工 grep 未命中仍要付出若干轮工具调用；脚本一行 ~20 token
- **查重**：今天完全没有这个机制

## 2. 为什么不换存储引擎

评估过 SQLite / 轻量数据库，结论是**不换**。理由按重要性排：

1. **它碰不到要优化的约束。** 成本中心是 token，不是查询耗时。23KB grep 是亚毫秒；
   1000 条约 700KB 仍是亚毫秒。换了引擎，进上下文的还是「命中的那条内容」，
   一个 token 都不会少。省 token 的是**切片**这个动作。
2. **会失去 git diff。** `vocab.md` 被 git 追踪、21 次提交、每次 commit message 写明
   新增了哪条术语。二进制 blob 无法 diff、无法解冲突，而本仓库是多 worktree 并行的。
3. **会失去直接读写与零依赖退路。** 词汇表是给人读的散文。脚本挂了还能退回读全文；
   DB 挂了就是读不了。
4. **它不解决语义查重。** 那需要模型读定义，或 embedding（已排除）。SQLite FTS5
   默认分词器不切中文，要中文全文检索需挂 trigram/ICU，折腾完效果与 grep 别名相当。

**改口的条件**（可证伪，将来照此量）：单项目 vocab 超过 ~500 条**且** `add` 查重明显变慢或变不准；
或出现多 session 并发写导致的真实数据损坏。即便那时，正确做法也是「Markdown 仍是权威源 +
gitignore 掉的派生缓存」，权威源永远是文本。

## 3. 脚本契约

```
skills/coding/capture-vocab/SKILL.md                    # 只留查词路径（§4.1）
skills/coding/capture-vocab/references/manage.md        # add/update/remove 细则
skills/coding/capture-vocab/references/project-setup.md # 项目接入说明
skills/coding/capture-vocab/scripts/vocab.py     # python3，无第三方依赖
skills/coding/capture-vocab/tests/test_*.py      # pytest，npm test 自动发现
```

选 python 不选 shell：匹配要做中文/全半角/大小写归一化，awk 干这个会碎。

**定位词汇文件**：从 cwd 逐级向上找 `.hskill/capture-vocab/vocab.md`，到 git root 或 `/` 为止。
不接受路径参数（测试用 cd 进 fixture 目录）。

### 3.1 三个子命令

| 命令 | stdout | exit | 成本量级 |
|---|---|---|---|
| `lookup <词或整句>` | 命中 section 原文（含 `## ` 标题行），多条则多段 | 0 | 200–400 |
| | `N matches: a, b, c, d` 单行（命中 > 3 时降级） | 0 | ~40 |
| | `no match: <词>` 单行 | 1 | ~20 |
| `list` | `术语名 \| 别名1,别名2` 每行一条 | 0 | ~15/条 |
| `refs <路径>` | `术语名 \| 档位 \| 命中的 reference 片段` 每行一条 | 0 / 1 | O(命中) |

文件不存在一律 exit 2 + 单行 `no vocab file`。

**`lookup` 未命中为什么不顺带列出全部术语**（今天的 `query` 是这么干的）：自动查的高频路径上，
未命中是常态。未命中若要花 ~500 token（33 条的 `list`），高频路径的平均成本会被它拉上去。
未命中就一行，真要看全量由调用方再花一次 `list`。

**退路**：脚本不存在或 python3 缺失时，退回读全文——贵，但能干活。这条退路必须写进 SKILL.md，
否则 agent 撞上会当成「查不了」。

### 3.2 匹配规则

整套规则坍缩成一条：**两边归一化后，任一方是另一方的子串即命中。**

**归一化**：casefold（`Tab`/`tab`、`IPC`/`ipc` 同一）；全角括号转半角；去反引号
（`` `画布操控` profile `` 要能被「画布操控」命中）；去首尾空白。归一化后输入长度 < 2 直接判未命中。

**双向子串**，两个方向都要：

- 输入 ⊆ 术语名 → `lookup 画布` 命中「画布区」
- 术语名 ⊆ 输入 → `lookup "把工作区的节点关系改一下"` 命中「工作区」「节点」「关系（relation）」

第二个方向的额外好处：**`lookup` 不必区分「查一个词」和「扫一整句」**，同一条规则两种用法，
因此不需要单独的 `scan` 子命令。

这条规则也吃掉了两类本来要单独写的特例——括号别名拆分（`Widget (瓦片)` 被「瓦片」命中）
与斜杠拆分（`分支/Worktree 追踪机制` 被 "Worktree" 命中），双向子串自动覆盖。

**Avoid 行当别名**：按 `,` `，` `;` `；` 切片，切完去掉尾部括号说明
（`画布工具栏（易与内嵌的 ToolBar 子组件混淆）` → `画布工具栏`）。
**只有长度 < 20 的片段算别名**——部分 Avoid 写的是成段散文（「席位」那条是两行解释），
拿散文做子串匹配会满屏假阳性。

**命中数上限 3**：≤3 吐完整 section；>3 只吐单行 `N matches: ...`。
没有这个上限，丢一整句进去可能命中五六条、一次 1500+ token。有了它，`lookup` 最坏情况锁死在
~1000 token，超出自动降级成名字列表，调用方再挑一条查。

### 3.3 `refs` 的路径提取与分档

`_Reference_` 是自由文本，但**路径长在自由文本旁边，不是与之缠绕**：

```
src/renderer/src/App.tsx（第 355 行附近，AppToolbar 在 Canvas 之外、之上）
src/main/pilot/、src/pilotGate/、docs/explanation/copilot-north-star.md §1.1-1.2
```

一个正则覆盖两种形态即可：`路径.扩展名[:行号]` 与 `路径/`（无扩展名的目录式）。

提取后按**字符串前缀关系**分两档：

| 档位 | 判据 | 含义 |
|---|---|---|
| `same-file` | 路径去掉 `:行号` 后相等 | 强候选，多半是同一实体的两个名字 |
| `dir-contains` | 一方是另一方的目录前缀 | 弱候选，多半是父子实体 |

这正是 §4.3 那个「同一实体 vs 父子实体」歧义所需的依据。脚本不下判决，只把候选分档摆出来。

## 4. 三条执行路径

### 4.1 高频路径（场景 2/3）——走 skill，不直接调脚本

> **2026-09-20 修订。** 本节初稿主张「完全绕开 skill、项目 `CLAUDE.md` 直接写脚本路径」，
> 已推翻。下面是定稿，保留初稿主张与推翻理由，因为那个取舍本身是这份 spec 的主要内容之一。

agent 遇到看起来像项目术语的词，**invoke `capture-vocab` skill**，由 skill 内部按
§3.1 的契约调 `vocab.py`（流程见 §4.2 的 `query`）。项目 `CLAUDE.md` 只声明
**什么时候查**，不声明**怎么查**。

**推翻初稿的理由**：脚本路径、子命令、退出码语义写进每个项目的 `CLAUDE.md`，等于
把 skill 的调用契约复制若干份到 skill 管不到的地方。skill 换子命令、改路径、换实现
语言时，这些副本会**静默失效**——不报错，只是从此查不到词，而表面上看一切照旧。
调用契约必须由 skill 自己持有。

**代价，明确记下来**：每次 invoke 都会把整份 `SKILL.md` 注入一次上下文，而直接调脚本
是命中 200–400、未命中 ~20。

**「每次」是实测的，不是推测**：本设计讨论期间同一 session 内 invoke 了 `handoff` skill
三次，上下文里出现了三份完整副本（各约 11.5k 字符）。所以这不是一次性开销——没有任何
机制限制一个 session 里 invoke 几次，成本从「确定的、随查词次数增长」变成「2k × 模型
决定 invoke 几次」，后者不受设计控制。

**顺带一个可复用的观察**：本地会话 JSONL（`~/.claude/projects/.../*.jsonl`）对同一次
交互只记了 1 份，正文是组请求时才展开的。**不能拿 JSONL 推算上下文窗口里有什么**，
它会系统性低估。

**缓解（已实施）**：`SKILL.md` 只保留查词路径，写操作细则与项目接入说明按渐进式披露
挪进 `references/`，**5700 → 2582 字节（降 55%）**，只在真要做那些事时才读。

接受这个代价的依据：**它是固定开销，不随词汇表条数增长**。本设计要守的性质是「成本与
词汇表总量无关」（§4.5），这条性质不受影响；涨的是一笔定额过路费，不是斜率。

**评估并否决了「拆成两个 skill」**（`search-vocab` 只读 + `capture-vocab` 读写）：拆完
每次查词约 350 token，比瘦身后的 ~900 省得有限；而两个 skill 要共用同一个 `vocab.py`
和同一套 `vocab.md` 格式，脚本放哪个目录里都尴尬，调用契约又散成两份——正是本节要消除
的那类问题。两个描述里都带「vocab」还会给触发判断多加一层可能出错的分辨。

**未验证**：走 skill 之后触发率会更高还是更低，没有数据。调 skill 比跑一条 bash 是
更「重」的动作，模型可能更不愿意为一个随口的词去调；但 skill 的 description 常驻
上下文，本身就是触发钩子，可能比 `CLAUDE.md` 里一段话更容易命中。两个方向都讲得通，
用过才知道。

### 4.2 `query`（用户显式调用）

skill 被 invoke，SKILL.md 的成本躲不掉。跑 `lookup`；未命中再跑 `list` 列全部术语名。

### 4.3 `add`（低频，贵操作全压在这里）

查重分三层，**严格按成本升序**，因为前两层不命中时几乎不花钱，第三层不管有无结果都付 O(N)：

| 层 | 动作 | 成本 | 抓什么 |
|---|---|---|---|
| 1 | `lookup <新词>` | O(命中) | 名字/别名字面重叠 |
| 2 | `refs <新词的每个 Reference 路径>` | O(命中) | 同一代码实体，**与命名无关** |
| 3 | `list` 全量名字+别名 | **O(N)** | 语义相近但字面不沾边 |

完整流程：

1. `lookup <term>`，字面撞了就报「已存在，请用 update」并退出
2. 从对话上下文推断 定义 / Avoid / Reference（保留 1.1.2 的行为）
3. 对推断出的每个 Reference 路径跑 `refs`，得到分档候选
4. **若第 1、3 步均空手**（`lookup` 未命中且 `refs` 无候选），才跑 `list` 走第 3 层；
   否则跳过，不付 O(N)
5. 对已得到的候选跑 `lookup` 取完整定义，模型**必须显式判一个结论并说给用户**，三选一：
   - **同一实体两个名字** → 建议改用 `update`，把新叫法并进 `_Avoid_`
   - **父子实体各有其名** → 正常新增，并建议在两条定义里互相点名
   - **无关** → 正常新增
6. 展示条目 + 查重结论，等用户确认后写入

第 4 步的跳过是**在判结论之前**就做的决定，判据只有「前两层有没有候选」这一个事实，
不依赖第 5 步的判断结果——否则顺序会成环。代价是：前两层出了候选、第 5 步却判成「无关」时，
不会再回头跑第 3 层。这正是 §7.2 里那条「主动接受一类漏」。

第 5 步「必须显式说出来」是有意设计：Reference 重叠的父子歧义脚本判不了，只有用户能拍板，
默默放过等于把这个需求丢了。这也是整套分层查重唯一的兜底。

**关键性质**：新词只要挂得上已知代码，第 2 层就能出候选，于是**永远不付 O(N)**。
O(N) 只在一种情况触发——新词没有 `_Reference_`（纯 spec 术语，如现有的「Widget (瓦片)」）。

### 4.4 `update` / `remove`

只把「读文件找 section」换成 `lookup`，其余不变。删除后不需要重建任何东西——**没有落盘索引**，
这是本方案相对「拆分文件 + 索引」方案的直接红利：少一个失步源。

### 4.5 语义查重的线性为什么消不掉

语义相似没有字面结构可剪枝——任何一条老词都可能是那个重复。要回答「这个新概念是不是已经存在」，
必然要过一遍全部词条。**唯一能打破线性的是让索引本身编码语义（embedding），已排除。**

既然线性躲不掉，就把每条的单位成本压到地板并证明地板是结构性的：**第 3 层只输出
`术语名 | 别名`，不含定义正文。** 术语名和别名在构造上就是短词——它们是词，不是句子，
所以 ~15 token/条是结构性上界，不是估算值。

| 词条数 | 第 3 层成本 |
|---|---|
| 33（现状） | ~500 |
| 100 | ~1.5k |
| 300 | ~4.5k |
| 1000 | ~15k |

**什么时候这套才真的不够用：超过 ~1000 条。** 到那时不是「再优化一次查重」，
而是必须引入语义索引，也就是推翻当前已排除的前提。在那之前这块不需要再动。

## 5. 加载约定与迁移

### 5.1 `CLAUDE.md` 术语澄清节（唯一的项目侧改动）

```markdown
## 术语澄清

遇到定义含糊的词或特殊称谓，不要凭猜测理解，用 `capture-vocab` skill 查该词条。
两种时机都要查：
(1) 用户消息里出现不像通用软件概念、像本项目自造的名词；
(2) 要在回复、文档或 commit message 里首次使用某个项目名词时
    （避免用上 `_Avoid_` 里的旧叫法）。
```

常驻成本 ~80 token。**这段里不出现任何脚本路径、子命令或退出码**——理由见 §4.1。

### 5.2 什么时候该查

两条判据，已写进上面那段：

1. 用户消息里出现**不像通用软件概念、像本项目自造**的名词
2. 要在回复、文档或 commit message 里**首次使用**某个项目名词时

第 2 条是输出侧的，目的是避免用上 `_Avoid_` 里的旧叫法。

**项目侧只写这两条。** 「怎么查」属于 skill 的内部契约（§3.1 / §4.2），不外泄。

### 5.3 脚本放在哪

`~/.claude/skills/capture-vocab/scripts/vocab.py`，**单一副本，不往项目里拷**，
且这个路径**只出现在本 skill 的 `SKILL.md` 里**，不出现在任何项目的 `CLAUDE.md`（§4.1）。
好处是不会有装机副本漂移，也不会有调用契约的散落副本；代价是 skill 未安装时
`SKILL.md` 里那条路径是死的，由 `query` 流程的 exit 2 退路兜底。

### 5.4 迁移清单

| 对象 | 动作 |
|---|---|
| `vocab.md`（33 条） | **不动，零迁移** |
| agent-canvas `CLAUDE.md` 术语澄清节 | 替换为 §5.1 |
| `SKILL.md` 「Agent 加载约定」节 | 重写，给出 §5.1 的可复制片段 |
| `SKILL.md` add/query/update/remove | 按 §4 改写 |
| 新增 `scripts/vocab.py` + `tests/` | — |
| 新增 `references/manage.md` + `references/project-setup.md` | 渐进式披露，低频内容不进每次 invoke（§4.1） |
| 版本号 | `1.1.2` → `1.2.0` |
| `skills-index.json` | 不动（path 与 bundle 均未变） |

## 6. 测试

**接线：零配置。** `scripts/run-skill-tests.sh` 自动发现 `skills/*/*/tests/` 下含 `test_*.py`
的目录并跑 pytest。本机 pytest 9.1.1 可用，capture-vocab 不带 venv，会用系统 python3。

**fixture**：固化一份真实 `vocab.md` 快照进 `tests/fixtures/`——它带着全部真实怪癖：
半角 `(瓦片)` 与全角 `（主体）` 混用、反引号术语名、斜杠术语名、跨行散文型 Avoid、
`src/main/pilot/` 这种无扩展名目录式 Reference。**固化不跟随**，agent-canvas 后续变更不影响测试。
另补两条人工构造条目：一条用于凑够 4 个命中触发降级，一条 Avoid 全为散文。

**测什么**：

- 归一化：`Tab`/`tab` 同一条；`瓦片` 命中 `Widget (瓦片)`；`画布操控` 命中 `` `画布操控` profile ``
- 双向子串：`画布` → 「画布区」；整句 `把工作区的节点改一下` → 「工作区」「节点」
- 输入归一化后长度 < 2 → exit 1
- 命中 4 条 → 单行 `N matches:`，**不吐任何 section**
- 未命中 → 单行 + exit 1；无文件 → exit 2
- **section 边界**：命中内容到下一个 `## ` 为止，不多不少（用「席位」这种多行带空行的条目测）
- Avoid 别名：`抽屉` 命中「工作区」；≥20 字的散文片段不产生命中
- `refs` 路径提取：从 `src/renderer/src/App.tsx（第 355 行附近…）` 提出路径；
  从 `src/main/pilot/、src/pilotGate/` 提出两个目录式路径
- `refs` 分档：`same-file` 与 `dir-contains` 标注正确
- `list`：行数等于 `## ` 数

**不测什么**：语义查重的准确率（模型行为，非脚本行为）；`add` 的分层查重流程
（活在 SKILL.md 指令里，`npm test` 只校验 SKILL.md 格式，不执行它）。

**因此 §4.3 的三层查重没有自动化验证**，脚本测的只是它三个零件各自正确。

### 6.1 验收条件

1. `npm test` 全绿
2. **人工**：在 agent-canvas 上真跑一次 `/capture-vocab add <新词>`，确认
   (a) 按 1→2→3 顺序走；(b) 新词带 Reference 时不触发第 3 层；
   (c) 查重结论被显式说出来并等待确认
3. **人工**：在 agent-canvas 上按 §5.1 改完 `CLAUDE.md` 后，用一个 `_Avoid_` 里的旧叫法
   （如「抽屉」）提问，确认 agent 自发 invoke 了 `capture-vocab` 并命中「工作区」。
   这一条同时是 §4.1「走 skill 之后触发率未知」那个未验证项的唯一观测点

## 7. 代价与边界

### 7.1 明确不做的

- **不改 `vocab.md` 格式。** 结构化 `_Reference_`（拆成路径列表 + 自由备注）评估过，
  当前正则提取已够用，不做。
- **不上 hook。** 因此没有「用户消息进来时自动匹配」的强制机制。
- **不上向量/embedding。**
- **不拆分文件、不落盘索引。**

### 7.2 代价清单

| 代价 | 说明 |
|---|---|
| **触发靠自觉，无强制力** | 没有 hook，§5.2 的两条判据全靠模型自觉。机制只能做到「查的时候很便宜」，做不到「一定会查」。这是整个设计最软的一环。 |
| **语义近似、字面不沾边的，查不到** | 用户说「右边那个滑出来的框」，术语是「工作区」——`_Avoid_` 里写了「抽屉」也接不住。脚本做不了语义匹配，这是设计边界。**查得准不准，取决于录入时 `_Avoid_` 写得全不全。** |
| **第 3 层条件触发，主动接受一类漏** | 新词挂上了已知代码、第 2 层判成「父子」或「无关」，但别处藏着一条名字毫不相干的真重复——这条不查了。 |
| **无 Reference 的词条是盲区** | 它自己录入时要付 O(N)，别人录入时也匹配不到它。副作用是鼓励「能写 Reference 就写」。 |
| **泛用短词频繁触发降级** | 「节点」「项目」「视图」在任何长句里都会命中，长句查询大概率落到降级档，等于多一轮。 |
| **Avoid 的散文片段被丢弃** | 20 字阈值是拍的，无依据。里面若藏着真别名就漏了。 |
| **脚本是唯一低成本入口** | 脚本坏了/未装，退路是读全文——回到今天的状态。 |
| **单文件在几百条时 git 体验变差** | 这个代价是推后了，不是消掉了。 |
| **worktree 局部性** | `.hskill/` 被 git 追踪，每个 worktree 有自己的 `vocab.md`，worktree 里加的词是分支局部的。非本设计引入，1.1.2 就如此。 |

### 7.3 判断

**技术判断**：现在上数据库是拿一个确定的损失（git 可读性、直接编辑）换一个不存在的收益
（查询性能）。切片脚本能拿到全部实际收益，且零迁移、零失步源。

**技术判断**：三层查重中第 2 层（代码引用）价值最高——它是唯一能抓到「同一实体、命名毫不相干」
这类重复的信号，且成本 O(命中)。把它排在语义初筛之前是这次设计最实质的改进。

**产品判断**（依据只到代码为止，未考虑多人协作场景）：单一副本脚本 + 项目 `CLAUDE.md`
引用绝对路径，对个人项目够用。若将来 agent-canvas 有第二个人参与，这个决策需要重评。
