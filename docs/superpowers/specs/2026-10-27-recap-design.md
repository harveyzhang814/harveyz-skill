# recap 设计

## 定位

长对话里丢了对全貌的掌控，或者想换个新 session 重新做整体性工作时，在当前对话里调用 recap，产出一份全局回顾：背景、已定结论、进度、文档与代码线索。

读者主次：**人第一，新 session 的 agent 第二**。人读来找回方向；agent 读来知道从哪开始调查。查得出的东西只给调查方向，不替 agent 查完。

没有它，现有选择是 fork-topic（只写一条支线、越短越好）或 handoff（交出一个任务、建工作区、要验收）——都不是"把整个对话的全貌讲清楚"。

## 边界

- **触发**：只由用户发起（`/recap`、"full recap"、"big picture"、"回顾一下全貌"、"我们整体到哪了"）。agent 不主动建议。
- **不做**：不落文件、不建分支或工作区、不验收、不替用户派发。存档或交接是另外的需求。
- **与 fork-topic 的分界**：fork-topic 写一条支线、求精简；recap 写整个对话、求全面。
- **与 handoff 的分界**：handoff 交出任务并要回来验收；recap 不交任务。
- **不读 memory 进报告**：memory 可能陈旧，新 session 也读不到。依据只有当前对话 + 第 2 步的核实结果。

代价：不落文件，报告只活在当前对话里，没复制就丢了；换来零仓库副作用。

## 流程

1. **抽取**：通读当前对话，按下节七个章节归类。对话被压缩过时，压缩前的内容只剩摘要，相关条目标「（未核实）」，并在第 1 节后注明"早期内容来自压缩摘要"。
2. **轻量核实**：凡要写进报告的路径、分支、文件，检查是否存在；涉及代码时看一眼 `git status`。对话所述与磁盘不符 → 记入第 7 节，不替用户判断哪边对。第 7 节只列事实，不猜原因、不给建议。查无的指向仍留在第 6 节，标「（查无，见第 7 节）」。只核实存在性，不读文档内容逐条对照（那是新 session 的调查工作）。
3. **起草**：按下节顺序写，套可读性标准。
4. **删减**：逐条过删减测试（标准第 8 条）。
5. **输出**：直接输出渲染后的 Markdown，**不包代码块**。人读优先；复制时丢失的 `#`/`**` 标记不影响 agent 理解（推测，见测试第 3 项）。

## 报告结构（倒金字塔）

读到哪停都不亏。前两节给失去全貌的人找回方向；偏 agent 的材料（背景、线索）自然靠后。

| # | 章节 | 内容 | 何时写 |
|---|---|---|---|
| 1 | 一句话 | 这个对话在做什么、现在到哪了 | 必写 |
| 2 | 当前状态 + 下一步 | 做完了什么、卡在哪、下一步是什么 | 必写 |
| 3 | 已定结论 | 每条带理由；否决的方案带否决理由 | 有就写 |
| 4 | 未决问题 | 还没定的事，各自卡在什么上 | 有就写 |
| 5 | 背景 | 目标、约束、用户说过的偏好 | 有就写 |
| 6 | 线索 | 文档、代码、分支的指向 + 为什么看 | 有就写 |
| 7 | 核实冲突 | 第 2 步发现的对话与磁盘不符处 | 有就写 |

用不上的章节整节省略，不留空标题。

## 可读性标准

**结构层**

1. **第 1 节一句话可决策**：同时说清"在做什么"和"到哪了"，只读它就能决定要不要往下读。
2. **每节首句即该节结论**：之后才展开。只扫每节首句也能拼出全貌。

**内容层**

3. **每条结论脱离上下文可读**：不写"上面那个方案""刚才说的问题"。对话中途起的临时代号，要么展开，要么首次出现时锚定一句。
4. **否决方案带理由**：写"否决 X，因为……"，防止新 session 把 X 重新提出来。
5. **把握度三档**：对话里明确定下的 / 推出来的 / 未核实的，分开标。对话里明确定下的不标；推出来的标「（推断）」，未核实的标「（未核实）」。
6. **不添加对话里没有、也推不出的结论**；推出来的必须标「（推断）」。对文件内容的猜测、对原因的猜测、对话里没说过的操作建议，都算推断。

**线索层**

7. **一条线索一行，只给指向不抄内容**：

   ```
   `docs/superpowers/specs/xxx.md` — 第三节的数据流已被推翻，以对话结论为准
   ```

   人跳过路径读破折号后的"为什么看"，agent 直接拿路径。磁盘上查得到的内容不写摘要。「为什么看」取对话里关于它的说法；对话只说了它是什么，就只写它是什么。

**删减**

8. **删减测试**：每条问"不写这条，人会不会判断错？agent 会不会走错路？"两个都"不会"就删。

**篇幅**：不设固定上限，靠第 8 条控制。对话长度差异太大，固定上限对短对话太松、对长对话太紧。

## 落地

- 位置：`skills/coding/recap/SKILL.md`，与 fork-topic、handoff 同类。
- 注册：`skills-index.json`，`bundle: coding`、`installScope: global`（同 fork-topic）。
- description 写清与 fork-topic、handoff 的分界；不改那两个 skill 的 description。
- 命名：单段动词 `recap`。不在动词词表里，会触发 F9 警告（不阻断）；这次不扩词表。

## 测试

1. `npm test`：SKILL.md 格式校验。
2. **真实长对话试跑**：在一段真实长对话里调用，对照可读性标准八条逐条检查。
3. **跨宿主渲染与复制**（用户亲测，不在沙箱模拟）：在 Codex、opencode 里调用，看 Markdown 渲染效果；把输出复制粘贴进新 session，看丢失格式标记后 agent 是否仍能正确理解章节与线索。

## 另行讨论

- 命名规则：人工调用的 skill 是否不强制双段命名、尽量简短直接。用户计划用 fork-topic 单独开话题。
