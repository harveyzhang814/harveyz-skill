# fork-topic 设计

## 定位

讨论中冒出一个支线话题，要分出去交给另一个 agent 单独展开。fork-topic 把它写成一段**精简的可粘贴 prompt**。

主次关系：

1. **目的**：fork topic——把支线从当前讨论分出去。
2. **约束**：prompt 尽可能精简。
3. **手段**：接手方查不出的写全；查得出的只给线索（去哪找、为什么相关），不给内容。

没有它，现有选择只有 handoff：要写交接文档、建工作区、走验收，对"分个话题出去"来说流程太重。

## 边界

- **触发**：只由用户发起（`/fork-topic`、"把这个分出去"、"开个支线"、"带着这些结论开个新话题"）。agent 不主动建议。
- **覆盖两种场景**：讨论中的支线话题；带着本次讨论结论去开新话题（原 handoff eval #3 的场景，迁过来）。
- **不做**：不落文件、不建分支或工作区、不验收、不替用户派给其他 agent——只输出文本，用户自己贴。
- **与 handoff 的分界**：结果要不要被正式验收。要验收用 handoff。

代价：不落文件意味着 prompt 只活在当前对话里，用户没复制就丢了；换来的是零仓库副作用。

## 流程

1. **确定支线话题**：以用户说的为准；说不清就问一句。
2. **抽取**：从当前对话里挑出与支线相关的信息，逐条判"接手方查不查得出"。
3. **判断回流**：主讨论在等这个支线的结论吗？在等 → prompt 末尾加交回要求；不等 → 不加。
4. **起草**：按下节候选项顺序组织。
5. **自检**（两道）：
   - 查不出的写全了吗？（漏了接手方会重新纠结已定的事，或违背用户偏好）
   - 查得出的是不是只给了线索？（有没有把文件内容、代码结构、仓库文档的摘要写进来）
6. **输出**：prompt 放在一个代码块里，便于复制。代码块外最多一句说明。

## prompt 候选项

按顺序；除「目标」外，用不上的整项省略，不留空标题。

| 候选项 | 内容 | 何时写 |
|---|---|---|
| 目标 | 支线要讨论/解决什么，从哪个主讨论分出来，一两句 | 必写 |
| 已定结论 | 主讨论里定下的、与支线相关的结论 | 有相关结论时 |
| 否决方案 | 否决了什么 + 为什么 | 有时；防止接手方重提 |
| 偏好与约束 | 用户在对话里明确说过的 | 有时 |
| 线索 | 每条：位置（路径/章节/关键词）+ 为什么相关；不写那里的内容 | 有可查资料时 |
| 交回要求 | 结束时给一段可贴回主讨论的结论 | 第 3 步判定主讨论在等时 |

代价：固定顺序的清单会诱导"为了填满而写"。靠第 5 步自检和"整项省略"的规则压住，不靠脚本。

## 判据：查不查得出

- 在磁盘、仓库或接手方能访问的系统里 → **线索**。
- 只存在于对话里（含尚未落盘的草稿）→ **写内容**，只写支线用得上的部分。

线索的粒度：说清"去哪找、为什么看"，到此为止。例："看 `skills/coding/handoff/SKILL.md` author 第 2 步——那里判断交接目的的方式是本话题的起点"，而不是把第 2 步抄过来。

## 命名

`fork-topic`。`fork` 不在 `docs/reference/skill-spec.md` 动词表里，补进去（含义：从当前讨论分出支线话题），消掉 F9 警告。放在 `skills/coding/fork-topic/`，bundle 与 handoff 相同。

## 测试

fork-topic 两条 eval：

1. **支线讨论、主讨论在等结论**：对话里有已定结论、否决方案、一个仓库文件引用。
2. **带背景开新话题**（由 handoff eval #3 迁来）：主讨论不等结论。

断言：

- 没有写任何文件。
- 引用仓库文件时只给路径与用途，不贴内容。
- 否决方案带着理由。
- 交回要求：eval 1 出现，eval 2 不出现。

另跑 `npm test` 做 SKILL.md 格式与 index 校验。

## 未决 / 风险

- 两个 skill 的触发词可能互撞（"hand this off" 一类说法）。description 里写明分界"要不要回来验收"；实际是否撞上要靠触发测试确认，本设计未验证。
