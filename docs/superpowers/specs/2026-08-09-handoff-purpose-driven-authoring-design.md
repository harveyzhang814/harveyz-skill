# handoff skill —— author 阶段按目的判断最小必要信息

## 背景

`skills/coding/handoff/SKILL.md` 的 `author`（写交接）阶段目前只有一套流程：无论这次交接的实际目的是什么，都套用 `assets/handoff-template.md` 固定的 9 节骨架（背景、成功判据、关键决定、范围铁律、文档索引、工作流、受影响文件、验证步骤、验收合同）。

但交接的目的并不单一：

- 有些交接是让接手方**续做同一件事**（如实现一个已定的规格），需要精确的范围边界、决定依据、验证步骤，最后要走"验收"闭环。
- 有些交接只是把当前讨论的结论/进展作为**背景信息**传给下一个 session，接手方是去开展新话题，不是去完成一个待验收的产出——这种情况下"验收合同""受影响文件"这类重内容是噪音，甚至会误导接手方以为有一个待验收的硬任务。

不应该预设一份穷尽的场景分类表去分支（场景会不断出现新变体，分类表会越维护越臃肿）。应该让 agent 在起草前先判断这次交接的**目的**，再用**最小必要信息原则**（缺了这条信息，接手方会出问题——走错方向、误改已定方案、做出 scope creep、卡在验证不知道对没对）逐项决定要不要写某类信息，而不是无论目的是什么都写一份详实的交接。

## 目标

- `author` 阶段起草前新增「目的判断」步骤，把判断结果作为一句自由描述写入文档开头（不枚举穷尽分类，不受限于预设值）。
- 现有模板的内容类别保留为「候选清单」，每类配一句针对性的必要性测试问题，逐类过一遍，测试通过的才写入对应章节；不通过的章节整节不出现（不留空占位）。
- 文档结构变为按需增减章节，不再有固定的 9 节骨架和固定编号。
- 无论目的是什么，文档必须始终包含两个锚点：**目的声明**（本次改动新增）和**最小验收锚点**（一句话说明"怎么判断这次交接达到了目的"，可以是硬判据也可以是软判据）。
- `verify`/`accept` 阶段的定位方式从"固定 §N 编号"改为"语义定位"（找文档里的验收锚点那句话、找实际存在的相关章节），因为章节编号不再固定。
- 完整性门禁（冷读测试）从"逐项核对固定 5 项是否都填了"改为"只核对文档里实际出现的章节是否自洽"，并新增一条反向检查：有没有哪类信息被判定为不必要，但其实接手方会因此卡住。

## 非目标

- 不引入固定的场景分类枚举（如"续做型/背景传递型/xxx型"），避免未来场景变体导致分类表持续膨胀。
- 不改变 `verify`/`accept` 的整体三阶段生命周期结构，只改它们定位内容的方式（语义定位替代编号定位）。
- 不改变 `.hskill/handoff/config.md` 的项目级配置机制（输出路径/工作流/验证工具/权威依据指向），这部分与本次改动正交。
- 不针对已有的 3 条 eval 做大改，只新增一条覆盖「背景传递型」的 eval 用例，验证 agent 真的会省略验收合同类章节而不是无脑套模板。

## 设计

### 1. Author 阶段新增「目的判断」前置步骤

在现有 Step 2（汇集上下文）之前插入新 Step：从当前对话判断这次交接的目的——不是分类打勾，而是一句自然语言判断（例如"接手方续做同一个实现任务"或"把讨论结论作为背景传给接手方去开展新话题"或其他）。判断结果写入文档开头，与状态字段并列展示，格式：

```
**交接目的**：<一句话，自由描述，不受预设分类约束>
```

这一行始终存在，不参与后面的必要性检查表（它本身就是必要性判断的输入）。

### 2. 内容选择：逐类必要性检查表

`assets/handoff-template.md` 从"待填空的固定 9 节骨架"改写为"候选内容清单 + 必要性测试"的起草指南：

| 候选内容 | 必要性测试 |
|---|---|
| 背景与现状 | 接手方不知道来龙去脉，会不会做错方向？ |
| 关键决定 | 接手方不知道这些决定，会不会推翻已定方案、重新纠结？ |
| 范围边界 in/out | 不划边界，接手方会不会顺手做超出范围的事？ |
| 相关文档索引 | 不给指针，接手方能不能靠自己找到权威依据？ |
| 受影响文件/落点 | 不列，接手方动手前要不要自己排查影响面？ |
| 工作流约定 | 项目有特殊分支/hooks 规范时才写；无特殊约定不写（沿用已有逻辑，本次不变）。 |
| 验证步骤 | 没有验证方法，接手方怎么知道做对了？ |

对每一类问自己这句必要性测试：答案是"会"就写，进对应章节；答案是"不会"就整节跳过，不写空占位、不留标题。

### 3. 两个始终存在的锚点

- **目的声明**（见第 1 点）。
- **最小验收锚点**：无论目的是什么，文档必须有一句"怎么判断这次交接达到了目的"。续做型可以是可证伪的硬判据（原 §2/§9 的样子，逐条对/错）；背景传递型可以是软判据（例如"接手方理解背景并能基于此推进新话题"）。这句话取代原来靠 §2/§9 固定编号定位的机制，成为 `accept` 阶段唯一的固定依据。

### 4. 完整性门禁（冷读测试）调整

不再逐项核对固定 5 项（原 §2/§3/§4/§5/§7）是否都填了，改为：

- 只核对文档里**实际出现**的章节是否自洽（如出现了「相关文档索引」就要核实路径真实存在；出现了判据就要可证伪）。
- 新增反向检查：**有没有哪类信息被必要性测试判定为"不需要"，但其实接手方会因此卡住？**（防止必要性判断本身错判，比如把关键决定误判为不必要，导致接手方推翻已定方案）
- 目的声明和最小验收锚点是否存在（这两项任何情况下都不能省）。

### 5. verify / accept 阶段定位方式调整

- `verify`：读交接文档，以怀疑视角核对可执行性——只核对文档里实际出现的章节，不再假设固定编号对应固定内容。
- `accept`：找文档里的最小验收锚点那句话，按其描述的判据方式验收（硬判据逐条实跑；软判据则做定性判断），记录 pass/fail（或达成/未达成）。全绿/达成才算完成。

### 6. 版本与联动改动

- 这是行为变更（不是措辞调整），`SKILL.md` 的 `version` 从 `1.0.0` bump 到 `1.1.0`。
- `skills-index.json` 中 `coding/handoff` 条目的 `contentHash`/`contentVersion` 需在改动完成后重新计算写入（沿用 F8 首次初始化/hash 变更 + 版本递增的既有流程）。
- `evals/evals.json` 新增一条「背景传递型」eval，验证 agent 在此类交接中会省略验收合同/受影响文件等章节，而不是无脑套完整模板。
