# Brainstorming 中文初版：流程分析与改写基线

## 目的与边界

本轮先建立一个可单独安装、可逐段审阅的中文初版，不在翻译时改变 Superpowers `brainstorming` 的行为规则。译文放在 `skills/superpowers-rewrite/brainstorming-zh/`，与仓库已有技能和上游同名技能区分。用户后续提出的意见再作为改写依据；每次改写都要标明改变了原版哪一条规则、为什么改变、可能影响什么行为。

基线为本地 Superpowers 包 `7.0.0` 中的 `skills/brainstorming/`。初版翻译其三份 Markdown 文件，复制可视化配套脚本并附上游 MIT 许可证。脚本保留交互协议和服务逻辑，仅将用户可见文案翻成中文，并将原版远程品牌图片改为本地文字署名与本技能版本号。仓库的 `skills/` 是本版本唯一的维护来源；插件缓存仅用于读取上游基线。

分工：三份 Markdown 的直译由 low effort 子 agent 完成；主 agent 独立分析原版流程、处理目录与打包、审阅译稿并验证。分析结论以本文为准，译稿仍作为待人工审阅的基线。

| 上游文件 | 中文初版中的位置 | 用途 |
| --- | --- | --- |
| `SKILL.md` | `skills/superpowers-rewrite/brainstorming-zh/SKILL.md` | 触发、对话、设计与门禁规则。 |
| `builder-check-prompt.md` | 同目录同名文件 | 设计文档的独立构建者检查提示词。 |
| `visual-companion.md` | 同目录同名文件 | 浏览器展示工具的使用指南。 |
| `scripts/` | 同目录 `scripts/` | 可视化展示服务与客户端交互。 |

## 一、制作与审阅流程

| 步骤 | 主要工作 | 产物或检查点 |
| --- | --- | --- |
| 1. 固定基线 | 确认上游版本、文件清单和许可证，阅读仓库的技能结构、索引及 Git 规范。 | 明确翻译对象与来源，避免在未注明的情况下混用上游版本。 |
| 2. 建立独立工作区 | 从明确的 `staging` 基线创建 `feature/` 分支和 worktree，设置 Git hooks 与合并配置。 | 初稿与集成分支隔离，可持续接受人工意见。 |
| 3. 建立目录和 bundle | 新建 `superpowers-rewrite` 类别，首个技能为 `brainstorming-zh`；在 `skills-index.json` 中登记 bundle 与技能。 | `hskill` 能发现并选择此初始 bundle。 |
| 4. 制作中文基线 | 将 `SKILL.md`、构建者检查提示词和可视化指南译成中文；保留步骤、例外、门禁、相对路径与跨技能引用。复制脚本和许可证，并翻译界面文案。 | 完整、可运行、可对照原版审阅的 `0.1.0` 初稿。 |
| 5. 分析流程 | 主 agent 拆解原版的触发、对话、设计、审批和后续交接，区分主线与按需分支。 | 本文档，供人工审阅时定位意见。 |
| 6. 验证初稿 | 检查 frontmatter、引用文件、索引版本与哈希，运行仓库测试，确认 npm 打包清单包含新技能。 | 可复查的验证结果；初稿仍停留在功能分支。 |
| 7. 人工审阅与迭代 | 按用户意见逐条修改规则，记录取舍与版本变化，重复必要验证。 | 逐步形成个人版本；是否合并、安装或发布由后续明确指令决定。 |

## 二、原版技能运行时的主流程

以下按实际决策顺序整理，而非照抄原文章节顺序。

| 阶段 | 主要动作 | 退出条件或下一步 |
| --- | --- | --- |
| 1. 判断已知信息 | 先问自己是否已理解用户要什么、为什么要做。信息完整的简单任务直接做；缺少重要信息才进入对话。 | 决定走快速执行路径，还是进入澄清路径。 |
| 2. 开启对话 | 第一条消息先告知用户可跳过提问，再只问一个能引出具体场景的开放问题。 | 用户选择跳过则说明重大制作选择并转入正常执行；否则继续探索。 |
| 3. 探索需求 | 每条消息只以一个问题收尾。先让用户描述，再按需追问目标、失败条件、已有工作、先例、约束和制作方式。Agent 可以提出明确猜测，但须与用户已确认的事实区分。 | 对某部分已足够理解时，进入复述；其余部分继续探索。 |
| 4. 分段复述 | 将已理解的部分约用 200–300 词复述给用户，标明推测，并询问遗漏或误解。探索与复述交替进行。 | 各关键部分得到校正，形成完整描述。 |
| 5. 确定工作规模 | 将任务归为快速明确任务、小改动或需要书面设计的项目；范围变大时升级处理；多个独立项目则逐个讨论。 | 选定聊天描述或书面设计作为后续依据。 |
| 6. 形成设计并检查 | 项目级任务写出意图、目标、反目标、限制、用户已决定的实现部分和留给实施者的选择。请独立构建者检查是否仍有会改变计划的重要疑问；将问题分为已有答案、可自行决定、必须问用户三类。 | 将重要疑问一次性集中问用户，补齐设计后交付审阅。 |
| 7. 审批与交接 | 完整描述获得用户批准后才能构建。项目级软件任务的下一步是 `superpowers:writing-plans`。 | 进入实施规划；此前只能阅读和探索。 |

### 横贯流程的按需分支

- **查看现状：** 有一定上下文且进一步查找有帮助时，先说明准备看代码、文件、数据或网页的哪些部分，再让用户决定是否查看。
- **可视化：** 当页面、布局、流程或选项看图比看文字更清楚时，在恰当时机单独提出浏览器展示。用户接受后才加载 `visual-companion.md` 并启动配套脚本；用户拒绝则继续文字讨论。
- **快速试探：** 允许用户同意后制作标记为临时的原型，用来检验需求或可行性。若要保留其成果，重新经过完整描述审批。
- **硬门禁的两个例外：** 用户明确跳过提问时，技能及其审批门禁结束；用户同意的临时原型可以先做。除此之外，产品代码、脚手架、依赖安装和实施技能调用都在审批之后。

## 三、人工审阅时值得重点判断的规则

下表只定位可能需要个人化的地方，不代表本轮已改动原版行为。

| 位置 | 原版当前做法 | 审阅时要判断的问题 |
| --- | --- | --- |
| 触发范围 | 几乎所有创作工作都先考虑此技能，但简单明确任务立即执行。 | 自己的版本是否也覆盖软件外的创作？怎样避免抢占无需澄清的任务？ |
| 第一条消息 | 固定为“可跳过提问”加一个开放问题。 | 在用户已提供充分需求或明确要求直接做时，这个格式是否仍适用？ |
| 对话节奏 | 每条消息只留一个问题；分段复述约 200–300 词。 | 中文语境下该长度和提问频率是否合适？ |
| 调查授权 | 原版要求先提出查看范围，再让用户决定是否查看。 | 只读仓库探索、联网调研、访问私人资料是否应采用不同门槛？ |
| 可视化实现 | 依赖浏览器标签页及本地 server 脚本。 | 目标宿主是否能运行这些脚本；是否需要跨宿主替代实现？ |
| 构建者检查 | 有子 agent 时派独立构建者；没有时自行模拟。 | 是否要保留强制检查、怎样控制成本、何时值得触发？ |
| 设计落点和交接 | 软件设计写入 `docs/superpowers/specs/`，获批后调用 `superpowers:writing-plans`。 | 是否改成自己的文档路径和计划技能；其他领域如何存档？ |
| 审批门禁 | 实施前必须获批完整描述，含对小改动的聊天描述。 | 哪些任务应以已有用户授权视为满足，避免重复确认？ |

## 四、初版验收口径

1. `skills/superpowers-rewrite/brainstorming-zh/` 至少包含三份中文 Markdown、可视化脚本及 MIT 许可证，所有文内相对引用可定位。
2. `SKILL.md` 的 `name`、`version`、`description` 和用户调用属性符合本仓库格式；`skills-index.json` 登记新 bundle、路径、版本与内容哈希。
3. 翻译不自行删改原版门禁、例外或先后关系；脚本的界面文案和署名本地化，连接、选项记录等运行逻辑与上游一致。
4. 运行 `npm test`；如出现已有基线失败，记录具体失败，不将其称为本技能通过。

本轮是可审阅初版。未来每轮用户意见应先落到上述运行阶段或横贯分支，再决定是文字表述调整、行为规则变更，还是宿主适配。

## 五、本轮验证记录

- `skills-index.json` 可解析，`contentVersion` 为 `0.1.0`，`contentHash` 与按仓库测试规则计算的 `SKILL.md` 摘要一致；`hskill list --json` 能发现新技能。
- `npm pack --dry-run --json` 确认新技能的三份 Markdown、五个脚本和 `LICENSE` 全部进入 npm 包。此检查使用临时 npm 缓存；本机默认 `~/.npm` 缓存无法写入。
- 可视化服务在沙箱外的本地临时目录完成启动、中文页面与新画面更新的冒烟验证。沙箱内的文件监听器会报 `EMFILE`。
- `npm test` 的技能结构 bats 检查通过；完整套件未全绿。沙箱外重跑后，`clip-url` 的 54 项浏览器测试通过；`forge-doc` 缺少 Python `markdown`，`browser-fetch` 和 `hub` 的异步测试缺少合适的 pytest 插件，另有一个真实网络图片用例失败。这些均不在新增技能路径下。
- 单独运行 Node 测试得到 331 通过、4 失败、7 跳过；失败分别涉及沙箱内向 `~/.hskill` 写入、缺少模块，以及现有打包测试对当前 npm JSON 输出形状的假设。直接检查 npm 打包文件清单已通过。
