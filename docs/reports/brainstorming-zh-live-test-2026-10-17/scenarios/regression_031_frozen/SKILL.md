# 头脑风暴

本技能帮助你在构建前核实用户想要什么、为什么想要，避免凭未经确认的理解做决定；通过提问厘清尚未成形的需求，才能依据用户意图处理他们未提及的选择。

## 首先：你究竟知道什么？

回复前判断是否已理解用户的目标及原因：信息充分的简单任务直接完成并说明结果；缺少影响结果的信息则进入对话。

## 你的第一条消息

发出第一条消息前，根据任务描述判断用户是在探索目标与方向，还是已有明确目标、只待确定方案；勿以描述长短判断或向用户询问分类。

- **探索性：** 以一个具体、开放的问题引出情境、动机或期望，例如：“你通常在什么时刻，会希望已经有这样一个东西？”
- **定义性：** 简短承接已定目标，只问最影响方案的一个未定事项，不重开已定内容。

问完即止。

## 对话

依据任务定位进入探索性或定义性对话，意图变化时切换；两者共用澄清标准和人工闸门，每轮沿用用户词汇、先说关键内容，末尾只问一个问题，不用流程术语。

### 探索性对话

**信息依据。** 从用户的场景、经历和问题中发现需求，将自己的解释标为待确认推断。

**提问方式。** 用具体场景的开放问题引导用户描述；卡住时给选择方向，要求建议时给可纠正的具体方案。

**推进方式。** 内部比较问题解释和可能方向，排除违背用户动机者；必要时经用户同意做用后即弃、无需完整测试和规划的试做，并把发现带回对话。

### 定义性对话

**信息依据。** 以用户明确的目标、成功标准和范围为已知，查阅相关资料并自行确认可查明的事实。

**提问方式。** 只问影响方案的需求缺口或冲突，按依赖与影响排序；每轮给出互斥且覆盖主要方向的选项、自定义入口、推荐及依据，不凑虚假选项，架构等方案选择留待方案审查。

**推进方式。** 据回答更新已定事项，增删待问问题；次要事项可提出标明由你决定的默认处理，纳入人工审查。

**共同澄清范围。** 以下六项是产品或开发需求能否进入方案形成的标准，不作为逐条提问的脚本：

- 目标用户、使用场景、问题及解决时机
- 新增或改变的产品能力与关键用户流程
- 成功标准、范围边界及不可破坏的现有行为
- 现有产品、代码、接口、数据、依赖及已做尝试
- 参考产品或功能，以及希望借鉴或避免的做法
- 影响方案的质量要求与技术约束

**结束条件。** 逐项标明已明确、待确认或不适用及原因；继续澄清影响方案的空缺，其余假设留待人工审查，用户说“够了”也不能代替确认剩余空缺和风险。

**制作方式的确认标准。** 以现有工作为基线，确认载体、工具或
材料、资源及决策归属；遵循用户已定选择，影响结果的未定选择按下文方案标准审查。

**有效问题的标准。** 只问已有信息无法回答、且能减少方案不确定性的具体情境、事实或决策；探索性对话可用经历或可纠正的猜测，定义性对话用可区分的选项。

**核查现状。** 现有实现会影响需求或方案时，在任务方向足以确定范围后，边澄清边查阅相关代码、配置、接口、测试和文档；范围较大时可派只读子代理并行调查。将查明的事实及依据、未核实的假设带回对话，据此调整问题和需求清单；查看当前项目以外的个人文件、数据或网络前，说明范围并由用户决定。

**阶段性复述。** 每弄清一部分需求，就用约 200–300 词复述其用途、对象或运作方式，标明用户所述、用户从选项中作出的选择及你的推断，并以一个纠错问题收尾；复述与提问交替，最后覆盖剩余内容，但不替代需求清单的人工批准。

**需求与决策记录。** 在同一份 Markdown 文档中只收录以下五类影响需求、关键方案或批准范围、且需要追溯的条目：

- **用户原始需求：** 与任务相关的每项要求，保留足以核对原意的原话摘录和出处。
- **Agent 推断与决定：** 纳入需求或方案、需要审查的推断及由你作出的次要决定，标明依据。
- **关键澄清：** 确定或改变需求、方案的问题及用户回答，保留必要原话。
- **方案选择：** 提交审查的关键候选、推荐依据及用户的选择或修正。
- **人工审批：** 需求清单、关键方案和最终 Spec 每次送审的条目或版本、用户答复、批准、否决或修正结果及覆盖范围。

每条记录独立编号并标明类别、来源和状态；审批关联覆盖的条目或版本，答复后同步审批及所涉条目状态，只将获批范围标为已批准，修正时保留旧结论及取代关系。批准不代替事实核查；错误推断标为失效并重审受影响结论。不存完整对话、草稿或无关调查。

**任务目录。** HSkill 系列每项任务使用项目根目录下的 `.hskill/spec/YYYY-MM-DD-<topic>/`，其中 `YYYY-MM-DD-<topic>-record.md` 保存上述审计记录，`YYYY-MM-DD-<topic>-spec.md` 保存书面设计；日期取首次建档日，同一任务修订沿用原目录及文件名，独立任务同名时在 topic 后加序号。其他任务询问保存位置。

**需求确认与人工闸门。** 形成方案前，提交从记录提炼的逐项需求清单，标明依据、状态及来源（用户直接提出或确认、你的推断、用户从选项中选择、你自行决定的次要事项）；用户逐项审查并明确批准后才形成方案，修改须重新提交，批准只覆盖展示内容。

**方案形成标准。** 以获批需求为依据，比较产品与实现路径，排除不满足要求者；对架构、核心机制、关键交互等含有你推断或决定的重大选择，逐项提交至少两种可行方案，说明运作逻辑、需求依据、收益、代价、风险、假设及推荐理由；仅有一种可行方案时，说明其他路径被排除的原因。用户选择或修正后才将方案记为已定，并将审查与选择写入记录；影响方案的新需求须重新澄清并通过人工闸门。

**前端设计稿审查。** 前端视觉或交互变动适合用设计稿评估时，调用 `sync-design` 的设计模式；多方案先以文字说明逻辑与取舍，再询问用户是否需要设计稿对照，经同意后制作并展示，将反馈纳入方案审查，设计稿不代表方案已获批准。

## 确定 Spec 的详略

Spec 的详略随涉及的模块与依赖、关键决策、异常路径和验证难度调整，只保留影响实现或验收的细节，不决定后续工作模式。

- **简单需求：** 用简明文字写清目标、范围、关键行为、已定方案与验收标准。
- **复杂需求：** 详细写清用户流程、系统边界、数据与接口、架构与核心机制、交互状态、异常处理、约束、取舍与验收方式，使实施者无需猜测关键决策。

## 书面设计

写作前核对需求与决策记录是否覆盖对话及审查中所有影响 Spec 的结论和审批，补齐缺漏、解决冲突；核实方案依赖的现状，缺乏依据时补查，若结果改变获批需求或方案则重新送审。

将获批需求和经用户审查的方案写入 Spec，使该领域有能力的构建者无需追问即可制定计划；按前述详略展开，不逐项誊写澄清清单或套用固定栏目。

**内容标准。** 写清意图、目标、范围、不可接受结果与验收依据，以及影响实现或验收的现状、约束和必须保持的既有行为；按需展开对象与场景、产品能力与流程、架构与核心机制、关键交互、数据与接口、状态及异常路径和重要取舍。标明关键决定的需求依据与归属（用户直接确认、用户从方案中选择、你的推断或次要决定），引用记录条目供追溯；仅将不改变用户认可结果的实施细节留给构建者。

**一致性检查。** 送审前按获批需求核对 Spec 的正常、变更、异常及并发路径、图示、验收和估算；方案修订后重查受影响的旧验收用例，确认同一场景的需求、规则、流程及验收结果一致。量化结论须核对计量对象、单位、范围、时间口径和推导依据；涉及并发或异步行为时，区分状态变化、操作生效和实际效果的时点，核对不同事件顺序下的结果与保证范围。无依据者标待核实，冲突或歧义提出方案及影响、更新记录并重新送审；批准后发现则暂停交付。

**可视化辅助。** 图示有助于人或 Agent 理解、审查 Spec 时，在相关内容旁嵌入 UML 或其他技术图示，呈现架构、组件、数据流、时序、状态或关键流程；文字足够清楚时无需绘制。图示须标明关键元素、关系、条件和异常路径，与正文一致，优先使用 Mermaid 等可随 Spec 维护的文本图示；图示不代替关键决定的文字说明。

**保存位置：** HSkill 系列将 Spec 保存并提交为上述任务目录中的 `YYYY-MM-DD-<topic>-spec.md`；其他任务询问保存位置，用户指定位置优先。

**构建者检查：** 简单任务由你按构建者视角自查；复杂任务用本目录的 `builder-check-prompt.md` 派未参与对话的全新子代理独立检查，无子代理工具时自行检查。交付前只找阻碍制定计划、且误判会改变用户认可结果的缺口，并分为三类：

- **已有答案：** 从获批需求、选定方案或项目事实补入文档，并标明依据。
- **次要决定：** 不改变用户认可的结果；自行决定并在文档中标明。
- **必须由用户决定：** 答案会改变需求或关键方案；返回相应的澄清或方案审查，并取得批准。

必须由用户决定的问题按影响排序、集中提问；更新文档并附上自行决定事项后，再交付用户审查。

**批准后同步。** 用户批准 Spec 后，记录获批版本与范围，同步记录及 Spec 的状态和决定标记；仅修正状态标记可沿用原批准，内容变更须重新送审，消除相反或过时标记后再制定计划。

<HARD-GATE>
人类伙伴批准完整描述之前，不得开始构建：小改动批准聊天中的描述，项目批准设计文档。构建包括编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用实现类技能。阅读与探索可以进行。

有两个例外。如果他们选择跳过提问，本技能即告结束，这道门槛也随之解除。经他们同意的探索性试做可以构建；它始终标记为用后即弃，如果要保留试做成果，就属于新请求，必须重新经过这道门槛。

项目文档获批后，下一步是制定计划。对于软件项目，调用 superpowers:writing-plans，不得调用其他技能。
</HARD-GATE>

## 警示信号

| 想法 | 实际情况 |
|------|----------|
| “我给些选项，替他们省点力气” | 探索性先问场景；定义性用选项澄清缺口；重大方案说明取舍供用户审查。 |
| “我来补上合理的默认选择” | 仅次要事项可自行决定，须说明依据并接受审查；重大选择交由用户。 |
| “我应该先解释流程” | 承接已知目标，只问未定事项；无需澄清时停止提问。 |
| “他们对这个想法说了‘听起来不错’” | “听起来不错”只批准已展示内容，不覆盖尚未写出的描述。 |
| “试做能运行，我就继续往下做吧” | 试做成果若要保留，须作为新请求重新经过门槛。 |
