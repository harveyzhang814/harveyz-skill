## 1. 目的、范围与不可接受的结果

**目的。** 在新建的共享工具借用系统（Python 服务）中，为每笔借用向借用人发送至多一条归还提醒短信，时点是当前约定归还时间的前 24 小时（U-01、U-04）。

**范围内：** 提醒的排期、改时间后的重排、取消与归还后的停止、到点占用与发送、失败与错过的记录、短信内容。

**范围外：** 借用本身的创建、取消、归还、改时间的业务入口与权限校验（由借用模块负责，本设计只规定它们必须满足的接口约束，见 3.2）；除借用人以外的收件人；送达回执；重试；退订；避开夜间。

**不可接受的结果**（验收时逐条检查）：
1. 同一笔借用有多于一次发送尝试（含失败与超时）。
2. 取消或归还之后仍发出提醒。【v1.1，待 H-05】“之后”以取消（归还）事务的**提交时点**为界：提交之后不得再发起对 AcmeSMS 的调用；提交之前已开始的发送会先完成，不算此项（P-02 选 C）。
3. 提醒发出尝试之后，因改时间而再次发出。
4. 发送尝试发生在计划时点所在分钟之后，却仍然发出。
5. 【v1.1，待 H-05】对 AcmeSMS 的调用发生在未持有该借用的借用行锁的时段，或持锁连接在调用返回、结果记录之前被释放。

## 3. 现状与约束

### 3.1 现状
- 这是新系统，项目目录为空，没有可读的现有代码（U-05）。因此借用模块的数据表、接口、身份模块都尚不存在，本设计对它们只提出下面的接口约束。
- 以下事项**尚未核实**，设计不依赖任何未经核实的 AcmeSMS 能力：AcmeSMS 是否支持签名“共享工具”（B-01）；AcmeSMS 的错误码、频率限制、超时建议、是否支持去重键（B-02）。

### 3.2 对借用模块与身份模块的接口约束
1. **借用状态：** 借用至少有“进行中、已取消、已归还”三种状态，后两种是终态，不可恢复（D-09）。
2. **同事务协同：** 借用的创建、改归还时间、取消、归还，必须在**同一个数据库事务**里调用提醒模块的对应操作（4.5）。这是并发正确性的基础，不能放在事务之外。
3. **改时间校验由借用模块负责：** 调用者必须是该借用的借用人；新归还时间晚于现在；新时间精确到分钟（秒不为 0 则拒绝，不截断，D-05）。
4. **手机号读取接口：** 身份模块提供 `get_verified_phone(borrower_id) -> 号码或空`，返回调用时刻借用人当前已验证的号码。
5. 【v1.1，待 H-05】**借用行锁与加锁顺序：** 借用模块对借用行的所有写操作（取消、归还、改时间及其他 UPDATE）都会与发送执行器的行锁冲突而等待。每个借用模块事务必须**先锁借用行、后碰 `loan_reminder` 行**；创建借用时插入新行不受此限。违反顺序会与发送执行器形成跨连接死锁，数据库检测不到，只能靠超时解开（D-13）。
6. 【v1.1，待 H-05】**借用模块的锁等待上限：** 取消、归还、改时间的事务所设 `lock_timeout` 须大于“持锁上界”（4.7），否则正常发送会使这些请求以超时失败。超时失败时整笔事务回滚、借用与提醒都不变，并向调用者明确报错，不得静默吞掉（D-15）。

## 4. 设计

### 4.1 组成【v1.1，待 H-05：增加持锁与双连接，v1 图见附录 A.1】

```mermaid
flowchart LR
    LM[借用模块<br/>创建 改时间 取消 归还] -->|同一事务 先锁借用行再碰提醒行| DB[(PostgreSQL<br/>loan 与 loan_reminder)]
    W[提醒工作进程] -->|每秒轮询 标记错过 查询到点提醒| DB
    W --> EX[发送执行器<br/>同进程内并发]
    EX -->|连接A 发送期间持借用行锁| DB
    EX -->|连接B 条件更新占用 记录结果| DB
    EX -->|持锁期间取当前已验证手机号| ID[身份模块]
    EX -->|持锁期间发送一次 不重试| SMS[AcmeSMS]
```

只有一个工作进程（S-08、U-19）。进程内分两部分：每秒一次的**轮询器**，和并发的**发送执行器**。发送执行器让慢速的 AcmeSMS 调用不会阻塞轮询（D-07）。【v1.1，待 H-05】每个在途发送占用两条数据库连接：连接 A 持借用行锁，连接 B 提交占用并写结果（D-14）。连接池须至少容纳 2×并发度，另加轮询器的连接。

### 4.2 数据模型

每笔借用对应 `loan_reminder` 表中的一行，主键为 `loan_id`。一笔借用不可能有两行，所以“每笔最多一条”在结构上成立。

| 字段 | 类型 | 说明 |
|------|------|------|
| `loan_id` | 主键，外键指向借用 | 一对一 |
| `state` | 枚举 | `NOT_SCHEDULED`、`SCHEDULED`、`ATTEMPTED`、`MISSED`、`CLOSED`，见 4.4 |
| `remind_at` | `timestamptz`，UTC，精确到分钟 | 恒等于当前归还时间减 24 小时。`ATTEMPTED` 与 `CLOSED` 之后不再随改时间变化，作为历史 |
| `attempted_at` | `timestamptz`，可空 | 占用成功的时刻，仅 `ATTEMPTED` 有值 |
| `outcome` | 枚举，可空 | `SUBMITTED`、`INVALID_PHONE`、`PROVIDER_ERROR`、`TIMEOUT`、`NO_VERIFIED_PHONE`、`INTERRUPTED`，仅 `ATTEMPTED` 有值 |
| `outcome_detail` | 文本，可空 | 供应商返回的错误码或说明，不存手机号 |
| `created_at`、`updated_at` | `timestamptz` | 记录用 |

约束与索引：
- `CHECK`：`state = 'ATTEMPTED'` 当且仅当 `attempted_at` 非空；`outcome` 非空时 `state = 'ATTEMPTED'`。
- 部分索引：`CREATE INDEX ON loan_reminder (remind_at) WHERE state = 'SCHEDULED'`，使每秒的轮询查询只扫待发记录。
- 不存手机号。发送时现取现用。

### 4.3 时间规则

- **统一用 UTC。** 所有时间用 `timestamptz`；短信中的时间也以 UTC 显示（S-06、D-02）。
- **归还时间精确到分钟**（C-04）。`remind_at = due_at − 24 小时`，也精确到分钟。
- **唯一时钟是数据库时钟（D-12）。** 所有“现在”的比较都在 SQL 内通过一个函数 `reminder_now()`（默认返回 `clock_timestamp()`）取得，且**每条语句内只取一次**，避免一条语句横跨分钟边界。应用进程的时钟不参与比较。测试时可以覆盖这个函数来控制时间。
- **“准时”的判定（C-04 选 A）。** 记 `now_min = date_trunc('minute', reminder_now())`：
  - `now_min = remind_at`：在计划时点所在分钟内，算准时。
  - `now_min > remind_at`：进入下一分钟或更晚，算错过。
  - `now_min < remind_at`：还没到点。
- **排期判定**（规则 2、6、7 的统一写法）。创建借用或改时间时，用 `now_min` 与新的 `remind_at` 比较：
  - `now_min < remind_at`：距归还时间超过 24 小时，进入 `SCHEDULED`，等到点。
  - `now_min = remind_at`：视为“恰好 24 小时”，进入 `SCHEDULED`，由轮询立即占用（规则 7）。
  - `now_min > remind_at`：不足 24 小时，进入 `NOT_SCHEDULED`，不发（规则 6）。

**这个选择的实际含义（请审查时留意）：** 因为同一分钟内算同一时点，在 `remind_at` 所在分钟的 0 到 59 秒内创建或改时间，都按“恰好 24 小时”处理、立即发。但如果占用恰好落在下一分钟，就算错过、不发。这来自你选的“按整分钟比较”，不是额外加的宽限。

### 4.4 状态与转换

```mermaid
stateDiagram-v2
    [*] --> SCHEDULED: 创建借用 当前分钟不晚于计划分钟
    [*] --> NOT_SCHEDULED: 创建借用 当前分钟已晚于计划分钟
    NOT_SCHEDULED --> SCHEDULED: 改时间 新计划分钟尚未过
    SCHEDULED --> SCHEDULED: 改时间 仍可排期 更新计划时点
    SCHEDULED --> NOT_SCHEDULED: 改时间 不足24小时
    SCHEDULED --> ATTEMPTED: 到点占用成功
    SCHEDULED --> MISSED: 计划分钟已过仍未占用
    MISSED --> SCHEDULED: 改时间 新计划分钟尚未过
    MISSED --> NOT_SCHEDULED: 改时间 不足24小时
    SCHEDULED --> CLOSED: 取消或归还
    NOT_SCHEDULED --> CLOSED: 取消或归还
    MISSED --> CLOSED: 取消或归还
    ATTEMPTED --> [*]
    CLOSED --> [*]
```

| 状态 | 含义 | 可否被改时间改变 | 终态 |
|------|------|------------------|------|
| `NOT_SCHEDULED` | 进行中的借用，当前不足 24 小时，不发 | 可。改到足够晚则变 `SCHEDULED` | 否 |
| `SCHEDULED` | 已排期，等待 `remind_at` 所在分钟 | 可。更新 `remind_at`，或变 `NOT_SCHEDULED` | 否 |
| `MISSED` | 计划分钟已过，没有发出尝试，也没有占用那一次机会 | 可（D-04）。改到足够晚则回到 `SCHEDULED` | 否 |
| `ATTEMPTED` | 已占用，即已有一次发送尝试，不论结果 | 不可，改时间对提醒无影响（规则 5） | 是 |
| `CLOSED` | 取消或归还，不发 | 不可 | 是 |

**不变量：** 没有任何路径把 `ATTEMPTED` 改回别的状态。这是“每笔最多一次尝试”的根。

### 4.5 流程

**所有状态变更都是对同一行的条件更新。** 占用、改时间、取消、归还都竞争这一行。PostgreSQL 在默认的 READ COMMITTED 下，后到的更新会等行锁，等到后再按已提交的新版本重新判断 `WHERE` 条件。所以它们互相排斥，不会各自读到旧状态。【v1.1，待 H-05】占用与取消、归还、改时间之间的先后，进一步由借用行锁决定，见 (4)。

**(1) 创建借用**（借用模块的同一事务内）
插入 `loan_reminder` 行：`remind_at = due_at − 24h`，按 4.3 的排期判定写入 `SCHEDULED` 或 `NOT_SCHEDULED`。

**(2) 改归还时间**（借用模块的同一事务内，在更新借用的 `due_at` 之后）
- 新旧归还时间相同：不改动提醒（D-10）。
- 否则：
  ```sql
  UPDATE loan_reminder
  SET remind_at = :new_remind_at,
      state = CASE WHEN date_trunc('minute', t.now_ts) <= :new_remind_at
                   THEN 'SCHEDULED' ELSE 'NOT_SCHEDULED' END,
      updated_at = t.now_ts
  FROM (SELECT reminder_now() AS now_ts) t
  WHERE loan_id = :id AND state IN ('NOT_SCHEDULED', 'SCHEDULED', 'MISSED');
  ```
  匹配 0 行说明状态是 `ATTEMPTED` 或 `CLOSED`，提醒保持不变（规则 5）。

**(3) 取消或归还**（借用模块的同一事务内）
```sql
UPDATE loan_reminder SET state = 'CLOSED', updated_at = reminder_now()
WHERE loan_id = :id AND state IN ('NOT_SCHEDULED', 'SCHEDULED', 'MISSED');
```
已经是 `ATTEMPTED` 的保持不变，保留发送历史。【v1.1，待 H-05】取消与归还事务先更新借用行（此时若发送执行器正持锁，就在此等待），再执行上面的语句。等待结束时若执行器已占用，提醒是 `ATTEMPTED`，语句匹配 0 行。这与规则 8 不矛盾：取消提交时那次调用已经结束，提交之后不会再有调用。

**(4) 轮询与发送**（提醒工作进程）【v1.1，待 H-05：发送改为持借用行锁，P-02 选 C；v1 原文见附录 A.2】

```mermaid
sequenceDiagram

    loop 每秒一次
        P->>B: 同一事务 标记错过 并查询当前分钟到点的待发提醒
        B-->>P: 候选 loan_id
        P->>E: 提交候选 进程内去重

```

轮询器每秒执行，同一事务内用同一个时间戳：
```sql
-- 1) 标记错过：计划分钟严格早于当前分钟
UPDATE loan_reminder SET state = 'MISSED', updated_at = t.now_ts
FROM (SELECT reminder_now() AS now_ts) t
WHERE state = 'SCHEDULED' AND remind_at < date_trunc('minute', t.now_ts);

-- 2) 查询候选：计划分钟等于当前分钟
SELECT loan_id FROM loan_reminder, (SELECT reminder_now() AS now_ts) t
WHERE state = 'SCHEDULED' AND remind_at = date_trunc('minute', t.now_ts);
```
轮询器只碰 `loan_reminder` 的行，不碰借用行，也不等待任何发送。

发送执行器对每个候选，按下面顺序执行，缺一不可：

1. **加锁（连接 A）。** 开启事务，设 `lock_timeout = :acquire_timeout`，执行 `SELECT 1 FROM loan WHERE id = :id FOR SHARE`（D-13）。这把锁持有到第 5 步。加锁超时：放弃本次，不占用，提醒仍是 `SCHEDULED`；该候选从进程内去重集合移除，计划分钟内下一轮可再提交。
2. **占用（连接 B，自动提交）。**
   ```sql
   UPDATE loan_reminder SET state = 'ATTEMPTED', attempted_at = t.now_ts, updated_at = t.now_ts
   FROM (SELECT reminder_now() AS now_ts) t
   WHERE loan_id = :id AND state = 'SCHEDULED'
     AND remind_at = date_trunc('minute', t.now_ts)
   RETURNING loan_id;
   ```
   - 返回 0 行：回滚连接 A，放弃，不调用。包括取消或归还已提交（同一事务已把提醒置为 `CLOSED`）、改时间已提交、已错过。
   - 返回 1 行：占用已提交，这次尝试成立，`attempted_at` 就是尝试时刻。**占用已提交之后才调用 AcmeSMS**（D-12；依据 S-01、S-02、R-03）。占用本身不算外部发送（P-02）。
   - 占用语句自带“计划分钟等于当前分钟”的条件，所以执行器自己拖到下一分钟才占用的，也会被拒绝并最终被标为错过。规则 9 对排队延迟同样成立。
3. **取手机号（持锁）。** 调用 `get_verified_phone`，须有超时（4.7）。无号码，或读取失败、超时：经连接 B 记 `NO_VERIFIED_PHONE`，跳到第 5 步（D-06、D-16）。
4. **调用 AcmeSMS 一次（持锁）。** 不重试。结果经连接 B 写入 `outcome`。
5. **释放。** 结果记录之后才提交连接 A、释放借用行锁。任何异常路径都在 `finally` 里释放。

**时序保证（P-02 选 C 的依据）。** 每次对 AcmeSMS 的调用都完整落在连接 A 持有借用行锁的时段内；取消、归还、改时间的事务要先更新借用行，所以它们的提交不可能落入这个时段。于是：
- 取消提交早于连接 A 加锁：该事务同时把提醒置为 `CLOSED`，占用返回 0 行，不调用。
- 连接 A 加锁早于取消：取消事务更新借用行时等待，直到结果记录、连接 A 提交之后才能继续并提交。调用发生在取消提交之前，取消提交之后不再有调用。
- 因此不存在“取消已提交、调用还在发起”的交叠（规则 8）。注意这只管我们发起调用的时点；`TIMEOUT` 之后供应商仍可能处理该请求，见第 5 节。

**不死锁的依据。** 所有借用模块事务先锁借用行、后碰提醒行（3.2(5)）。连接 A 持有借用行锁时，没有任何借用模块事务能持有该笔提醒行的锁，所以连接 B 的占用语句不会等到借用模块；它只可能短暂等待轮询器的标记错过，而轮询器不等待任何持锁方。连接 B 也设一个很短的 `lock_timeout` 作兜底，超时按放弃处理（不占用，不调用）。违反锁序的写法会造成数据库检测不到的跨连接死锁，所以锁序是约束，不是建议。

`NO_VERIFIED_PHONE` 表示占用后发现借用人此刻没有已验证手机号，不调用供应商、不重试、这一次机会已用（D-06）。

**(5) 进程重启**
工作进程启动时，把所有 `state = 'ATTEMPTED' AND outcome IS NULL` 的记录标为 `INTERRUPTED`（D-08）。因为只有一个工作进程，这些必然是上一个进程在占用之后、记录结果之前中断的。它们**不重试**，也无法知道短信是否真的发出，只做记录。【v1.1，待 H-05】进程崩溃时连接 A 随连接断开，行锁自动释放，等待中的取消、归还、改时间随即继续。重启期间错过的计划分钟，由轮询器按 `MISSED` 处理。

### 4.6 短信内容

- 文本固定为：`【共享工具】借用将于{时间}到期`。其中 `{时间}` 是发送时刻该借用当前的归还时间，格式 `YYYY-MM-DD HH:MM UTC`。例：`【共享工具】借用将于2026-10-18 09:00 UTC到期`（U-12、D-02、D-03）。
- 不含工具名、链接、退订提示。借用人同时借多件工具时，无法从短信区分是哪一件。这是按你给的文案保持的，如需区分请告知。
- 该文本为 32 个字符，在常见的“中文短信每条 70 字符”规则下是一条。这个分段规则是 AcmeSMS 的实际规则，尚未核实（B-02）。如果 AcmeSMS 按多条计费，会影响“每笔最多一条”的预算口径，需在实施前确认。
- 签名不随供应商要求自动更改。AcmeSMS 不支持该签名时，记录为阻塞，由你决定（U-16、B-01）。

### 4.7 AcmeSMS 集成要求

- 每次占用成功后**最多调用一次**，任何失败都不重试（S-01）。
- 调用必须设置超时。超时算一次尝试，记为 `TIMEOUT`，不重试。超时数值作为配置项，待 B-02 核实供应商建议后确定，本设计不预设数值。
- 失败分类 `INVALID_PHONE`、`PROVIDER_ERROR`、`TIMEOUT` 只用于记录与排查，三者行为一致（都不重试）。AcmeSMS 错误码到类别的映射待 B-02 核实；无法识别的一律归为 `PROVIDER_ERROR`（D-11）。
- 发送执行器的并发度作为配置项，须不超过 AcmeSMS 的频率限制，数值待 B-02。轮询器不得被发送阻塞（D-07）。【v1.1，待 H-05】并发度还受连接池限制：连接池至少 2×并发度加轮询器连接（D-14）。
- 【v1.1，待 H-05】**持锁上界：** 单次发送持有借用行锁的最长时间 = 手机号读取超时 + AcmeSMS 调用总时限 + 写结果的数据库时间。AcmeSMS 的超时必须是**总时限**（连接、发送、读响应合计），任何情况下不得无限期阻塞，因为取消、归还、改时间都在等这把锁。身份模块读取同样须有超时，失败或超时按“取不到已验证手机号”处理，记 `NO_VERIFIED_PHONE`，`outcome_detail` 注明读取失败（D-16）。
- 【v1.1，待 H-05】**配置约束（D-15）：** 手机号读取超时、AcmeSMS 总时限、加锁超时 `:acquire_timeout`、借用模块 `lock_timeout`、`idle_in_transaction_session_timeout`、连接池大小都是配置项，数值待 B-02。必须满足：借用模块 `lock_timeout` > 持锁上界；`idle_in_transaction_session_timeout` > 持锁上界（否则数据库会杀掉持锁连接，锁提前释放，破坏规则 8）；`:acquire_timeout` 远小于持锁上界（否则执行器槽位被长时间占住）；连接池 ≥ 2×并发度 + 轮询器连接。工作进程启动时校验这些约束，不满足则拒绝启动。

### 4.8 可观测性与预算核对

- 每次状态转换写一条结构化日志，含 `loan_id`、旧状态、新状态、时间。
- 指标：各 `outcome` 的计数、`MISSED` 的计数、轮询每次耗时、从分钟起点到占用成功的延迟。【v1.1，待 H-05】另增：持锁时长分布、加锁超时次数、借用模块因 `lock_timeout` 失败的取消/归还/改时间次数、取消/归还/改时间的锁等待时长（由借用模块上报）。
- ~~**预算核对：** 每日统计 `state = 'ATTEMPTED'` 且 `outcome <> 'NO_VERIFIED_PHONE'` 的行数，应不超过当日新增借用数的上限。每笔借用至多一行，所以短信数每日不超过 1000 的上限（A-04、U-17）。~~ 【已失效：提醒落在 `due_at − 24h` 所在日，不是创建日，每日提醒数不受每日新增上限约束（A-04 失效，U-22）。】
- 【v1.1，待 H-05】**预算核对（A-06）：** 每笔借用至多一行（主键保证），因此任意时刻 `state = 'ATTEMPTED'` 且 `outcome <> 'NO_VERIFIED_PHONE'` 的行数不超过已创建借用总数；预算按“每笔一条”核算（U-06）。每日、每分钟的发送数只作监控，不断言不超过 1000，其峰值取决于当日、当分钟到点的进行中借用数，不设上界（C-06、规则 16）：集中到点超出处理能力的部分记 `MISSED`，不补发。
- 对 `MISSED` 与 `INTERRUPTED` 设置告警，因为它们意味着有借用人没有收到提醒或结果不明。

## 5. 边界与异常

| 情形 | 行为 | 依据 |
|------|------|------|
| 创建时已不足 24 小时 | `NOT_SCHEDULED`，不发 | 规则 6 |
| 创建或改时间落在计划分钟内 | `SCHEDULED`，立即占用；若占用落在下一分钟则 `MISSED`，不发 | 规则 7、9 |
| 已排期，改到不足 24 小时 | `NOT_SCHEDULED`，不占用那一次机会 | 规则 6 |
| `NOT_SCHEDULED` 或 `MISSED`，改到距今 ≥24 小时 | 回到 `SCHEDULED` | 规则 6、10 |
| 占用之后改时间 | 提醒不变，不补发 | 规则 5 |
| 占用与改时间同时发生 | 借用行锁决定先后：加锁先到则占用成功，改时间等待并在发送结束后提交，对提醒无影响（规则 5）；改时间先提交则占用匹配 0 行 | 4.5(4) |
| 占用与取消、归还同时发生 | 【v1.1，待 H-05】取消（归还）先提交：占用 0 行，无调用。加锁先到：取消等待，发送结束后才提交，提交后无调用（规则 8、15）。v1 原文见附录 A.3，该原文与规则 8 矛盾（U-22） | P-02 选 C |
| 发送持锁期间到达取消、归还、改时间 | 等待至发送返回或超时，最长为持锁上界；借用模块 `lock_timeout` 大于持锁上界，正常不会因此失败 | 规则 15、3.2(6) |
| 加锁超时（别的事务长时间占着借用行） | 放弃，不占用，提醒仍为 `SCHEDULED`；计划分钟内下一轮可再试，过了计划分钟记 `MISSED` | D-13 |
| 持锁期间进程崩溃或连接断开 | 行锁随连接释放，等待的操作继续；记录重启后标 `INTERRUPTED`，不重试 | D-08 |
| `TIMEOUT` 之后供应商仍可能处理该请求 | 不属于“取消后发起调用”。锁在超时后释放，取消随即提交；此后短信仍可能被供应商投递，本设计无法撤回，也不假设供应商可撤回 | 规则 8、B-02 |
| 集中到点超出处理能力 | 计划分钟内占用不上的记 `MISSED`，不补发，不设到点上限 | 规则 16、C-06 |
| 工作进程停机、数据库不可用、进程卡住超过计划分钟 | 该分钟的提醒错过，不补发 | 规则 9 |
| 占用后、调用前进程崩溃 | 不重发；重启后标 `INTERRUPTED` | D-08 |
| 误启动了第二个工作进程 | 条件更新仍保证最多一次尝试（但不属于支持的部署方式） | 4.5 |
| 同一分钟大量借用同时到点 | 在计划分钟内占用不上的，错过 | 规则 9；见第 7 节风险 |
| 借用已取消或已归还后又收到改时间请求 | 提醒不受影响，请求是否允许由借用模块决定 | D-09 |
| 手机号在排期后更换 | 发送时用当时已验证的号码 | S-09 |

## 7. 风险

1. **突发集中到点。** 【v1.1，待 H-05】到点数量不受“每日新增最多 1000 笔”约束：不同日子创建的借用、以及被改时间的借用，都可能落在同一天或同一分钟（A-06）。上界不设（C-06、U-23）：超出处理能力的部分记 `MISSED`、不补发，由你接受。如果很多借用的计划分钟相同（例如大量借用约定同一时刻归还），发送执行器必须在该分钟内逐个占用。AcmeSMS 的频率限制或延迟让占用赶不上，就会错过，且不补发。缓解：执行器并发度按 B-02 设定，并监控 `MISSED`。这是零宽限的直接代价（S-04）。
2. **单点。** 只有一个工作进程，它或数据库不可用的那一分钟，提醒全部错过。这是你选定方案和“错过不补发”的结果，不会造成多发。
3. **超时和中断的结果不明。** `TIMEOUT` 与 `INTERRUPTED` 时不知道短信是否真的发出，也不重试。借用人可能收到，也可能没收到。
4. **供应商计费口径。** 如果 AcmeSMS 的分段规则与 70 字符假设不同，预算口径可能偏离（B-02）。
5. **短信不含工具名**，同时借多件时无法区分。
6. 【v1.1，待 H-05】**借用写操作被拖慢（选 C 的直接代价）。** 持锁期间到达的取消、归还、改时间最长等待持锁上界。AcmeSMS 整体变慢时，所有在途发送对应借用的这类请求都会变慢，借用模块须能容忍并向用户展示等待（P-02）。
7. 【v1.1，待 H-05】**连接占用。** 每个在途发送占两条连接，连接 A 在整个调用期间空闲在事务内。AcmeSMS 变慢时连接池可能耗尽，迫使调低并发度，进而带来更多 `MISSED`（D-14）。
8. 【v1.1，待 H-05】**锁序与超时配置是正确性前提。** 违反锁序会产生数据库检测不到的跨连接死锁；配置违反约束会使取消失败或让锁提前释放。启动时校验可缓解，不能替代借用模块遵守约束（3.2(5)(6)、4.7）。
9. 【v1.1，待 H-05】**取消提交后供应商仍可能投递。** `TIMEOUT` 的请求在我们放弃等待后供应商可能仍在处理，本设计无法撤回（B-02 未核实）。

### A.2 v1 的 4.5(4) 轮询与发送

**(4) 轮询与发送**（提醒工作进程）

```mermaid
sequenceDiagram
    participant P as 轮询器
    participant E as 发送执行器
    participant DB as PostgreSQL
    participant ID as 身份模块
    participant SMS as AcmeSMS
    loop 每秒一次
        P->>DB: 同一事务 标记错过 并查询当前分钟到点的待发提醒
        DB-->>P: 候选 loan_id
        P->>E: 提交候选 进程内去重
    end
    E->>DB: 条件更新占用 要求待发且计划分钟等于当前分钟
    alt 占用失败 0 行
        DB-->>E: 放弃 已被改时间或取消或已错过
    else 占用成功 1 行
        DB-->>E: 状态变为 ATTEMPTED
        E->>ID: 取当前已验证手机号
        alt 无已验证手机号
            E->>DB: 记录 NO_VERIFIED_PHONE 不调用供应商
        else 有号码
            E->>SMS: 发送一次 不重试
            alt 供应商受理
                E->>DB: 记录 SUBMITTED
            else 无效号码 其他失败 超时
                E->>DB: 记录 INVALID_PHONE 或 PROVIDER_ERROR 或 TIMEOUT
            end
        end
    end
```

轮询器每秒执行，同一事务内用同一个时间戳：
```sql
-- 1) 标记错过：计划分钟严格早于当前分钟
UPDATE loan_reminder SET state = 'MISSED', updated_at = t.now_ts
FROM (SELECT reminder_now() AS now_ts) t
WHERE state = 'SCHEDULED' AND remind_at < date_trunc('minute', t.now_ts);

-- 2) 查询候选：计划分钟等于当前分钟
SELECT loan_id FROM loan_reminder, (SELECT reminder_now() AS now_ts) t
WHERE state = 'SCHEDULED' AND remind_at = date_trunc('minute', t.now_ts);
```
发送执行器对每个候选，在调用 AcmeSMS 之前，先做**占用**：
```sql
UPDATE loan_reminder SET state = 'ATTEMPTED', attempted_at = t.now_ts, updated_at = t.now_ts
FROM (SELECT reminder_now() AS now_ts) t
WHERE loan_id = :id AND state = 'SCHEDULED'
  AND remind_at = date_trunc('minute', t.now_ts)
RETURNING loan_id;
```
- 返回 1 行：这次尝试成立，`attempted_at` 就是尝试时刻。**占用已提交之后才调用 AcmeSMS**（D-12 之外的关键顺序，依据 S-01、S-02、R-03）。
- 返回 0 行：这条已被改时间、取消、归还，或已错过，放弃，不调用。
- 占用语句自带“计划分钟等于当前分钟”的条件，所以执行器自己拖到下一分钟才抢占的，也会被拒绝并最终被标为错过。这保证规则 9 对发送执行器的排队延迟同样成立。

调用 AcmeSMS 的结果写入 `outcome`，不重试。`NO_VERIFIED_PHONE` 表示占用后发现借用人此刻没有已验证手机号，不调用供应商、不重试、这一次机会已用（D-06）。
