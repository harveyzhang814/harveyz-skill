提醒已经发出后，借用人把归还时间改了，应该怎么处理？

- **A. 严格一次**：每笔借用终身只发一次，改时间后也不再补发。方案最简单，但改成更晚的日期后，借用人可能收不到新的提醒。

我推荐 **B**。借用人改了时间，原来那条提醒就已经过时，补发一条才符合提醒的目的。你说的“只发一次”，也可以理解为同一个约定时间不重复发。如果你的本意是限制短信条数或成本，那就选 A 或 C。

## 零宽限带来的冲突（C-04）

“严格晚于计划时点”如果按连续时间比较，任何调度、网络、处理延迟都会让尝试时刻比计划时点晚几毫秒。结果有两个：
- 几乎所有提醒都会被判为错过，功能基本发不出。
- S-10 的“恰好 24 小时立即发送”也会被判为错过，因为处理总要花时间，这和 S-10 直接矛盾。

所以必须先定“晚于”按什么精度比较。我不能替你选，因为选择会改变哪些提醒会发出。

## 方案比较 P-01：排期与防重复发送

两个方案共用同一个机制：**先在数据库里记下“已尝试”，再调用 AcmeSMS**。依据是 S-01、S-02、R-03：失败和超时也算用掉那一条，所以必须先落库再发送。进程在落库后、调用前崩溃，这条提醒会丢，但预算不会多花，这符合“不重试、不补发”。

**方案 A：数据库记录状态，工作进程高频轮询**
- **运作：**
  1. 每笔借用在数据库里存提醒状态和 UTC 计划时点（`remind_at`）。
  2. 工作进程轮询到点的记录，用一条条件更新把状态从“待发”改为“已尝试”，成功抢到的才去调用 AcmeSMS。
  3. 改时间、取消、归还都用同样的条件更新，只在“待发”时生效。
- **收益：**
  - 不引入新的基础设施。
  - 每日 1000 笔的量远低于任何数据库的承载能力。
  - 多个工作进程同时跑也不会重复发，因为靠条件更新抢占。
  - 状态都在一张表里，排查和对账容易。
- **代价与风险：**
  - 要保证轮询足够密，错过一次轮询就可能错过计划时点。
  - 数据库必须支持事务和条件更新。
- **假设：** 有 PostgreSQL 这类关系型数据库。你还没说用什么，我目前只是假设。

**方案 B：延迟任务队列，数据库条件更新兜底**
- **运作：**
  1. 创建或改时间时，向队列投递一条在 `remind_at` 执行的延迟任务。
  2. 改时间、取消、归还时撤销旧任务。
  3. 任务执行时仍要回到数据库做同样的条件更新，才能保证最多一条。
- **收益：** 到点由队列触发，不用自己写轮询，触发时刻可能更准。
- **代价与风险：**
  - 要多维护队列这套基础设施。
  - 撤销任务通常只能尽力而为，所以必须保留数据库兜底。这等于方案 A 的状态机一样不能省，还多了一套系统。
  - 任务数量和延迟时长受队列实现限制，很多队列对长延迟（最长到数天）支持不好。
  - 队列丢任务或堆积会直接造成错过，而你的口径是错过不补发。
- **假设：** 部署环境里能运行并运维一个持久化的延迟队列。

**排除：进程内存定时器。** 重启会丢任务，也无法保证最多一条，直接违反 R-03。

**我推荐方案 A。** 在你的约束下，数据库兜底这一层两个方案都必须有，方案 B 只是在它上面多加一套队列，却没有换来更强的保证。每日 1000 笔的规模也不需要队列。它还有一个好处：不同的“晚于”口径，只需要改轮询比较那一处，机制本身不变。

## 设计要点

- **每笔借用一行 `loan_reminder`：** 用主键保证一笔借用只会有一行。状态有五种：
  - `NOT_SCHEDULED`：当前不足 24 小时，不发。
  - `SCHEDULED`：已排期，等到点。
  - `MISSED`：计划分钟已过，没发出，也没占用那一次。
  - `ATTEMPTED`：已占用，即已有一次发送尝试，是终态。
  - `CLOSED`：取消或归还。
- **先占用、后发送：** 工作进程每秒轮询，用一条条件更新把状态改成 `ATTEMPTED`，提交之后才调用 AcmeSMS。改时间、取消、归还和占用都竞争同一行，所以不会出现两条短信。
- **时间规则：** 全部用 UTC，且以数据库时钟为准。计划分钟内的尝试算准时，进入下一分钟就算错过。
- **改时间、取消、归还：** 都在借用模块的同一个事务里更新这一行。

`now_min` 与新的 `remind_at` 比较：\n  - `now_min < remind_at`：距归还时间超过 24 小时，进入 `SCHEDULED`，等到点。\n  - `now_min = remind_at`：视为“恰好 24 小时”，进入 `SCHEDULED`，由轮询立即占用（规则 7）。\n  - `now_min > remind_at`：不足 24 小时，进入 `NOT_SCHEDULED`，不发（规则 6）。\n\n**这个选择的实际含义（请审查时留意）：** 因为同一分钟内算同一时点，在 `remind_at` 所在分钟的 0 到 59 秒内创建或改时间，都按“恰好 24 小时”处理、立即发。但如果占用恰好落在下一分钟，就算错过、不发。这来自你选的“按整分钟比较”，不是额外加的宽限。\n\n### 4.4 创建借用**（借用模块的同一事务内）\n插入 `loan_reminder` 行：`remind_at = due_at − 24h`，按 4.3 的排期判定写入 `SCHEDULED` 或 `NOT_SCHEDULED`。\n\n**(2) 改归还时间**（借用模块的同一事务内，在更新借用的 `due_at` 之后）\n- 新旧归还时间相同：不改动提醒（D-10）。\n- 否则：\n  ```sql\n  UPDATE loan_reminder\n  SET remind_at = :new_remind_at,\n      state = CASE WHEN date_trunc('minute', t.now_ts) <= :new_remind_at\n                   THEN 'SCHEDULED' ELSE 'NOT_SCHEDULED' END,\n      updated_at = t.now_ts\n  FROM (SELECT reminder_now() AS now_ts) t\n  WHERE loan_id = :id AND state IN ('NOT_SCHEDULED', 'SCHEDULED', 'MISSED');\n  ```\n  匹配 0 行说明状态是 `ATTEMPTED` 或 `CLOSED`，提醒保持不变（规则 5）。\n\n**(3) 取消或归还**（借用模块的同一事务内）\n```sql\nUPDATE loan_reminder SET state = 'CLOSED', updated_at = reminder_now()\nWHERE loan_id = :id AND state IN ('NOT_SCHEDULED', 'SCHEDULED', 'MISSED');\n```\n已经是 `ATTEMPTED` 的保持不变，保留发送历史。\n\n**(4) 轮询与发送**（提醒工作进程）\n\n```mermaid\nsequenceDiagram\n    participant P as 轮询器\n    participant E as 发送执行器\n    participant DB as PostgreSQL\n t.now_ts\nFROM (SELECT reminder_now() AS now_ts) t\nWHERE state = 'SCHEDULED' AND remind_at < date_trunc('minute', t.now_ts);\n\n-- 2) 查询候选：计划分钟等于当前分钟\nSELECT loan_id FROM loan_reminder, (SELECT reminder_now() AS now_ts) t\nWHERE state = 'SCHEDULED' AND remind_at = date_trunc('minute', t.now_ts);\n```\n发送执行器对每个候选，在调用 AcmeSMS 之前，先做**占用**：\n```sql\nUPDATE loan_reminder SET state = 'ATTEMPTED', attempted_at = t.now_ts, updated_at = t.now_ts\nFROM (SELECT reminder_now() AS now_ts) t\nWHERE loan_id = :id AND state = 'SCHEDULED'\n  AND remind_at = date_trunc('minute', t.now_ts)\nRETURNING loan_id;\n```\n- 返回 1 行：这次尝试成立，`attempted_at` 就是尝试时刻。**占用已提交之后才调用 AcmeSMS**（D-12 之外的关键顺序，依据 S-01、S-02、R-03）。\n- 返回 0 行：这条已被改时间、取消、归还，或已错过，放弃，不调用。\n- 占用语句自带“计划分钟等于当前分钟”的条件，所以执行器自己拖到下一分钟才抢占的，也会被拒绝并最终被标为错过。这保证规则 9 对发送执行器的排队延迟同样成立。\n\n调用 AcmeSMS 的结果写入 `outcome`，不重试。`NO_VERIFIED_PHONE` 表示占用后发现借用人此刻没有已验证手机号，不调用供应商、不重试、这一次机会已用（D-06）。\n\n**(5) 进程重启**\n工作进程启动时，把所有 `state = 'ATTEMPTED' AND outcome IS NULL` 的记录标为 `INTERRUPTED`（D-08）。因为只有一个工作进程，这些必然是上一个进程在占用之后、记录结果之前中断的。它们**不重试**，也无法知道短信是否真的发出，只做记录。重启期间错过的计划分钟，由轮询器按 `MISSED` 处理。\n\n### 4.6 短信内容\n\n- 文本固定为：`【共享工具】借用将于{时间}到期`。其中 `{时间}` 是发送时刻该借用当前的归还时间，格式 `YYYY-MM-DD HH:MM UTC`。例：`【共享工具】借用将于2026-10-18 09:00 UTC到期`（U-12、D-02、D-03）。\n- 不含工具名、链接、退订提示。借用人同时借多件工具时，无法从短信区分是哪一件。这是按你给的文案保持的，如需区分请告知。\n- 该文本为 32 个字符，在常见的“中文短信每条 70 字符”规则下是一条。这个分段规则是 AcmeSMS 的实际规则，尚未核实（B-02）。如果 AcmeSMS 按多条计费，会影响“每笔最多一条”的预算口径，需在实施前确认。\n- 签名不随供应商要求自动更改。AcmeSMS `INVALID_PHONE`、`PROVIDER_ERROR`、`TIMEOUT` 只用于记录与排查，三者行为一致（都不重试）。AcmeSMS 错误码到类别的映射待 B-02 核实；无法识别的一律归为 `PROVIDER_ERROR`（D-11）。\n- 发送执行器的并发度作为配置项，须不超过 AcmeSMS 的频率限制，数值待 B-02。轮询器不得被发送阻塞（D-07）。\n\n### 4.8 的行数，应不超过当日新增借用数的上限。每笔借用至多一行，所以短信数每日不超过 1000 的上限（A-04、U-17）。\n- 对 `MISSED` 与 `INTERRUPTED` 设置告警，因为它们意味着有借用人没有收到提醒或结果不明。\n\n## 5. 边界与异常\n\n| 情形 | 行为 | 依据 |\n|------|------|------|\n| 创建时已不足 24 小时 |
