## 一、每日新增 ≤1000 笔，推不出每日提醒 ≤1000 条

**推不出。** 提醒按借用的 `due_at − 24h` 触发，计数对象是"到点的借用"，不是"当天新建的借用"。两者的时间窗口不同，还会跨天累积。

**依据：**
- 规则 14（spec:38）和 U-17（record:26）只限制了每日新建的借用数。
- A-04（record:41）把这个上限推成"每日约 1000 条提醒"，U-17 只确认了前半句，没确认这个推论。
- spec:241 写"每笔借用至多一行，所以短信数每日不超过 1000"，这一步不成立。
  - 每笔至多一条，只能推出累计发送数 ≤ 累计创建数。
  - 推不出任何一天的发送数 ≤ 1000。

**反例：**
- 连续 30 天每天新建 1000 笔，全部约定在第 31 天同一分钟归还，共 30,000 笔。
- 那一分钟会有 30,000 条提醒到点，每日新增上限一直没被违反。
- 规则 13（spec:37）允许借用人无限次改时间，所以即使创建很分散，提醒也可以被改到集中的某一天。

**波及的条目：**
- **AC-20**（spec:286）要求"`ATTEMPTED` 计数不超过该日新增借用数"。这条用例本身就是错的，今天发的提醒大多属于以前创建的借用。
- **AC-19**（spec:285）把"同一分钟 1000 笔"当作最坏情形，实际峰值没有这个上界。
- **第 7 节风险 1**（spec:290）的规模判断也建立在同一个前提上。
- **U-06 的预算要求**（record:14）按累计口径仍可由单行结构保证，没有问题。

**下一步：**
- **用户决定：**
  1. "1000"是什么约束？是只需要"累计发送数 ≤ 累计创建数"的预算口径，还是要强制每日发送上限？后者是新需求，必须规定超限时是延后还是放弃，而这会和已批准的规则 3、9 冲突。
  2. 实际要按多大的峰值（每天、每分钟的到点数）来设计，以便确定 AC-19 的规模和 B-02 的并发度。

## 二、`ATTEMPTED` 之后、调用 AcmeSMS 之前取消，Spec 前后矛盾

**两处说法相反：**
- **要求不发。** 规则 8（spec:32）说"取消借用、借用已归还：不发"。"不可接受的结果 2"（spec:17）说"取消或归还之后仍发出提醒"不可接受。record 里的 U-07、R-08 也是这个意思。
- **实际会发。**
  - 取消的 SQL（spec:157–160）只更新 `NOT_SCHEDULED`、`SCHEDULED`、`MISSED`，对已是 `ATTEMPTED` 的行不做任何改动。
  - spec:253 明确写"占用先到则……取消不影响提醒，且短信照发"。
  - 流程里占用提交之后，执行器不再检查借用状态，直接取号码并调用（spec:214、spec:181–185）。
  - 取消事务照常提交，借用已取消，但短信发出，这正是不可接受的结果 2。

**现有的并发论证盖不住这个窗口：**
- spec:136 说行锁让各更新互相排斥。
- 但占用是独立语句，调用 AcmeSMS 之前就已提交（spec:214），锁不覆盖外部调用。
- 这种情况下事务或行锁只能保证数据库里的更新有序，不能保证范围外的调用受控。

**验收没有覆盖：**
- AC-08（spec:274）只测计划分钟之前的取消。
- AC-13（spec:279）只写"每次最多一次调用"，没有说取消后是否还会调用。
- AC-15（spec:281）测的是崩溃，和取消无关。
- 所以现在没有一个用例能判定这个场景是否合格。

**下一步：用户需要选一种取消语义。**
- **A. 接受现状：** 取消在占用提交之后到达，短信照发。
  - 需要把规则 8 和"不可接受的结果 2"改成"取消在占用提交前才保证不发"，并补一条 AC。
  - 这会收窄已批准的 R-08。
- **B. 调用前再校验一次（我推荐）：**
  - 执行器在调用 AcmeSMS 前再读一次借用状态。已取消或已归还则不调用，记一个新的 outcome，例如 `CANCELLED_BEFORE_SEND`，这次机会算用掉。
  - 残余窗口仍在：校验之后、请求发出之前取消，短信仍会发。
  - 验收应写成"取消提交早于二次校验则零调用，晚于则允许一次调用"，需要你认可这个"取消后不发"的精确定义。
- **C. 取消等发送结束：** 持锁跨越外部调用，取消会被 AcmeSMS 的延迟和超时阻塞。我不推荐。

这是新系统，项目目录为空，没有可读的现有代码（U-05）。因此借用模块的数据表、接口、身份模块都尚不存在，本设计对它们只提出下面的接口约束。\n- 以下事项**尚未核实**，设计不依赖任何未经核实的 AcmeSMS 能力：AcmeSMS 是否支持签名“共享工具”（B-01）；AcmeSMS 的错误码、频率限制、超时建议、是否支持去重键（B-02）。\n- 4.5、4.8 所述 PostgreSQL 借用的创建、改归还时间、取消、归还，必须在**同一个数据库事务**里调用提醒模块的对应操作（4.5）。事务内必须**先更新借用行，再调用提醒操作**（先借用行、后提醒行，D-13）。这是并发正确性的基础，不能放在事务之外。这些事务内不得做外部调用或其他耗时操作，避免自己长时间占着借用行锁。\n3. **改时间校验由借用模块负责：** 调用者必须是该借用的借用人；新归还时间晚于现在；新时间精确到分钟（秒不为 0 则拒绝，不截断，D-05）。\n4. **手机号读取接口：** 身份模块提供 `get_verified_phone(borrower_id) -> 号码或空`，返回调用时刻借用人当前已验证的号码。调用方设有总时限 `T_id`，超时或异常按 `PHONE_LOOKUP_FAILED` 处理（D-16）。\n5. **借用行可被共享锁定：** 提醒模块与借用模块使用同一个 PostgreSQL，默认 READ COMMITTED；提醒模块可对借用行执行 `SELECT 状态, due_at ... FOR SHARE`（表名、列名由借用模块确定）。\n6. **等锁上限：** 借用模块的取消、归还、改时间事务，其 `lock_timeout` 与请求时限必须不小于 `H_max` 加余量（4.8）。若更短，等锁超时则整个事务回滚，借用与提醒保持原状，向调用方返回可重试的错误，不留下半截状态。\n\n## 4. 设计\n\n### 4.1 组成\n\n```mermaid\nflowchart **归还时间精确到分钟**（C-04）。`remind_at = due_at − 24 小时`，也精确到分钟。\n- **唯一时钟是数据库时钟（D-12）。** 所有“现在”的比较都在 SQL 内通过一个函数 `reminder_now()`（默认返回 `clock_timestamp()`）取得，且**每条语句内只取一次**，避免一条语句横跨分钟边界。应用进程的时钟不参与比较。测试时可以覆盖这个函数来控制时间。应用进程只用单调时钟度量各项时限（4.8），这些时长不参与任何排期或“准时”的比较。\n- **“准时”的判定（C-04 选 A）。** 记 `now_min = date_trunc('minute', reminder_now())`：\n  - `now_min = remind_at`：在计划时点所在分钟内，算准时。\n  - `now_min > remind_at`：进入下一分钟或更晚，算错过。\n  - `now_min < remind_at`：还没到点。\n- **排期判定**（规则 2、6、7 的统一写法）。创建借用或改时间时，用 `now_min` 与新的 `remind_at` 比较：\n  - `now_min < remind_at`：距归还时间超过 24 小时，进入 `SCHEDULED`，等到点。\n  - `now_min = remind_at`：视为“恰好 24 小时”，进入 `SCHEDULED`，由轮询立即占用（规则 7）。\n  - `now_min > remind_at`：不足 24 小时，进入 `NOT_SCHEDULED`，不发（规则 6）。\n\n**这个选择的实际含义（请审查时留意）：** 因为同一分钟内算同一时点，在 `remind_at` 所在分钟的 0 到 59 秒内创建或改时间，都按“恰好 24 小时”处理、立即发。但如果占用恰好落在下一分钟，就算错过、不发。这来自你选的“按整分钟比较”，不是额外加的宽限。取借用行锁的等待时间同样计入这个分钟判定。\n\n### 4.4 SHARE`，**一直持有到本次发送的结果写入之后**才释放。取消、归还、改归还时间的第一条写语句是对借用行的 `UPDATE`，与共享锁冲突，所以发送期间它们在这条语句上等待。必须用 `FOR SHARE`：它与对非键列的 `UPDATE` 冲突；`FOR KEY SHARE` 不冲突，不可用。\n2. **提醒行的条件更新。** 占用、改时间、取消、归还对 `loan_reminder` 行的状态变更仍是条件更新。PostgreSQL 在默认的 READ COMMITTED 下，后到的更新会等行锁，等到后再按已提交的新版本重新判断 `WHERE` 条件。\n\n只靠第 2 层，行锁只管得住数据库内的更新，管不住占用提交之后的外部调用，这正是 v1 的缺陷（C-06）。第 1 层补上这个缺口。\n\n**加锁顺序（D-13）。** 任何事务都按“先借用行、后提醒行”取锁。占用语句和轮询器的“标记错过”只碰提醒行，不请求借用行锁，因此不与这个顺序形成环。\n\n**(1) 创建借用**（借用模块的同一事务内）\n插入 `loan_reminder` 行：`remind_at = due_at − 24h`，按 4.3 的排期判定写入 `SCHEDULED` 或 `NOT_SCHEDULED`。\n\n**(2) 改归还时间**（借用模块的同一事务内，在更新借用的 `due_at` 之后）\n- 更新借用行时，若发送执行器正持有该借用的共享锁，则在此等待，最长 `H_max`（D-17）。\n- 新旧归还时间相同：不改动提醒（D-10）。\n- 否则：\n  ```sql\n  UPDATE loan_reminder\n  SET remind_at = :new_remind_at,\n      state = CASE WHEN date_trunc('minute', t.now_ts) <= :new_remind_at\n                   THEN 'SCHEDULED' ELSE 'NOT_SCHEDULED' END,\n      updated_at = t.now_ts\n  FROM (SELECT reminder_now() AS now_ts) t\n  WHERE loan_id = :id AND state IN ('NOT_SCHEDULED', 'SCHEDULED', 'MISSED');\n  ```\n  匹配 0 行说明状态是 `ATTEMPTED` 或 `CLOSED`，提醒保持不变（规则 5）。\n\n**(3) 取消或归还**（借用模块的同一事务内）\n先更新借用行状态（取得借用行排他锁）；若发送执行器正持有共享锁，则在此等待，直到执行器写完结果并释放锁，最长 `H_max`。取得锁后再执行：\n```sql\nUPDATE loan_reminder SET state = 'CLOSED', updated_at = reminder_now()\nWHERE loan_id = :id AND state IN ('NOT_SCHEDULED', 'SCHEDULED', 'MISSED');\n```\n已经是 `ATTEMPTED` 的保持不变，保留发送历史。**事务提交的时点就是取消或归还的生效点**（规则 8）。\n\n**(4) 轮询与发送**（提醒工作进程）\n\n```mermaid\nsequenceDiagram\n    participant P as 轮询器\n    participant E as 发送执行器\n    participant L as 锁连接\n    participant D as 占用连接\n    participant ID as 身份模块\n    participant SMS as AcmeSMS\n    loop 每秒一次\n        P->>D: 标记错过 并查询当前分钟到点的待发提醒\n        D-->>P: 候选 loan_id\n        P->>E: 提交候选 进程内去重\n    end\n    E->>L: BEGIN 对借用行 FOR SHARE 并读状态和归还时间\n    alt 等锁超过 T_xlock 或借用已取消或已归还\n        L-->>E: 放弃 不占用 不调用 释放锁\n    else 取得锁 借用进行中\n        E->>D: 条件更新占用 自动提交\n        alt 占用失败 0 行\n            D-->>E: 放弃 已被改时间或已错过 释放锁\n        else 占用成功 1 行\n            D-->>E: ATTEMPTED 已提交\n            E->>ID: 取当前已验证手机号 限时 T_id\n            alt 无号码 或 查询失败 超时\n                E->>D: 记录 NO_VERIFIED_PHONE 或 PHONE_LOOKUP_FAILED 不调用供应商\n            else 有号码\n                E->>L: 调用前确认锁连接仍在\n                alt 锁连接已失\n                    E->>D: 记录 INTERRUPTED 不调用供应商\n                else 锁连接仍在\n                    E->>SMS: 发送一次 不重试 总时限 T_sms\n                    SMS-->>E: 受理 失败 或超时\n                    E->>D: 记录 SUBMITTED INVALID_PHONE PROVIDER_ERROR 或 TIMEOUT\n                end\n            end\n            E->>L: 结果写入之后 释放借用行锁\n        end\n    end\n```\n\n轮询器每秒执行，在占用连接上用同一个时间戳：\n```sql\n-- 1) 标记错过：计划分钟严格早于当前分钟\nUPDATE loan_reminder SET state = 'MISSED', updated_at = t.now_ts\nFROM (SELECT reminder_now() AS now_ts) t\nWHERE state = 'SCHEDULED' AND remind_at < date_trunc('minute', t.now_ts);\n\n-- 2) 查询候选：计划分钟等于当前分钟\nSELECT loan_id FROM loan_reminder, (SELECT reminder_now() AS now_ts) t\nWHERE state = 'SCHEDULED' AND remind_at = date_trunc('minute', t.now_ts);\n```\n发送执行器对每个候选，按以下顺序执行：\n\n1. **取借用行锁（锁连接）。**\n   ```sql\n   -- 锁连接，事务内\n   SET LOCAL lock_timeout = :t_xlock;\n   SELECT status, due_at FROM <借用表> WHERE id = :id FOR SHARE;\n   ```\n   锁连接所在会话预先设置看门狗 `idle_in_transaction_session_timeout = W_dog`（4.8）。等锁超过 `T_xlock`，或读到借用不在“进行中”，则放弃：不占用、不调用、释放锁。等锁超时放弃的，提醒仍是 `SCHEDULED`，同一分钟内可被下一秒的轮询再次选中；分钟过了则被标为 `MISSED`。\n2. **占用（占用连接，自动提交）。**\n   ```sql\n   UPDATE loan_reminder SET state = 'ATTEMPTED', attempted_at = t.now_ts, updated_at = t.now_ts\n   FROM (SELECT reminder_now() AS now_ts) t\n   WHERE loan_id = :id AND state = 'SCHEDULED'\n     AND remind_at = date_trunc('minute', t.now_ts)\n   RETURNING loan_id;\n   ```\n   - 返回 1 行：这次尝试成立，`attempted_at` 就是尝试时刻。**占用已提交之后才继续取号码和调用 AcmeSMS**，且此时仍持有借用行锁（D-12、D-13，依据 S-01、S-02、R-03）。\n   - 返回 0 行：已被改时间、取消、归还，或已错过，放弃，释放锁，不调用。\n   - 占用语句自带“计划分钟等于当前分钟”的条件，所以执行器自己拖到下一分钟才抢占的（包括等借用行锁拖过分钟的），也会被拒绝并最终被标为错过。这保证规则 9 对发送执行器的排队延迟同样成立。\n3. **取手机号（有总时限 `T_id`）。** 持锁状态下调用 `get_verified_phone`。\n   - 无已验证手机号：记 `NO_VERIFIED_PHONE`（D-06）。\n   - 查询超时或异常：记 `PHONE_LOOKUP_FAILED`（D-16）。\n   - 这两种都不调用供应商、不重试、这一次机会已用。\n4. **调用前确认。** 在锁连接上执行一条轻量语句确认会话仍在、锁仍被持有，并确认自取锁起的单调时长未超过允许值。否则不调用，记 `INTERRUPTED`、`outcome_detail = lock_lost_before_call`（D-15）。\n5. **调用 AcmeSMS。** 最多一次，设总时限 `T_sms`，不重试。短信文本中的归还时间用第 1 步在锁下读到的 `due_at`（4.6）。\n6. **记录结果（占用连接）。**\n   ```sql\n   UPDATE loan_reminder SET outcome = :o, outcome_detail = :d, updated_at = reminder_now()\n   WHERE loan_id = :id AND state = 'ATTEMPTED' AND outcome IS NULL;\n   ```\n   写入失败不重试写库，记错误日志并告警，记录的 `outcome` 保持为空，重启时按 (5) 标 `INTERRUPTED`。\n7. **释放借用行锁。** 结果写入之后才结束锁连接的事务，等待中的取消、归还、改时间此时继续。\n\n`NO_VERIFIED_PHONE` 表示占用后发现借用人此刻没有已验证手机号，不调用供应商、不重试、这一次机会已用（D-06）。\n\n**(5) 进程重启或崩溃**\n- 进程崩溃时数据库会话随之断开，借用行锁自动释放，等待中的取消、归还、改时间继续。\n- 工作进程启动时，把所有 `state = 'ATTEMPTED' AND outcome IS NULL` 的记录标为 `INTERRUPTED`（D-08）。因为只有一个工作进程，这些必然是上一个进程在占用之后、记录结果之前中断的。它们**不重试**，也无法知道短信是否真的发出，只做记录。重启期间错过的计划分钟，由轮询器按 `MISSED` 处理。\n\n### 4.6 短信内容\n\n- 文本固定为：`【共享工具】借用将于{时间}到期`。其中 `{时间}` 是发送时刻该借用当前的归还时间，取自持借用行锁时读到的 `due_at`，格式 `YYYY-MM-DD HH:MM UTC`。持锁期间归还时间不会被改动，所以文本与被锁定的状态一致。例：`【共享工具】借用将于2026-10-18 09:00 UTC到期`（U-12、D-02、D-03）。\n- 不含工具名、链接、退订提示。借用人同时借多件工具时，无法从短信区分是哪一件。这是按你给的文案保持的，如需区分请告知。\n- 该文本为 32 个字符，在常见的“中文短信每条 70 字符”规则下是一条。这个分段规则是 AcmeSMS 的实际规则，尚未核实（B-02）。如果 AcmeSMS 按多条计费，会影响“每笔最多一条”的预算口径，需在实施前确认。\n- 签名不随供应商要求自动更改。AcmeSMS 不支持该签名时，记录为阻塞，由你决定（U-16、B-01）。\n\n### 4.7 AcmeSMS 集成要求\n\n- 每次占用成功后**最多调用一次**，任何失败都不重试（S-01）。\n- 调用必须设置**总时限** `T_sms`，覆盖连接、发送请求、读取响应的全过程，按墙钟计，不能只设单次读超时，否则慢速响应可以无限期占着借用行锁。超时算一次尝试，记为 `TIMEOUT`，不重试。`T_sms` 作为配置项，待 B-02 核实供应商建议后确定，本设计不预设数值。\n- 失败分类 `INVALID_PHONE`、`PROVIDER_ERROR`、`TIMEOUT` 只用于记录与排查，三者行为一致（都不重试）。AcmeSMS 错误码到类别的映射待 B-02 核实；无法识别的一律归为 `PROVIDER_ERROR`（D-11）。\n- 发送执行器的并发度作为配置项，须不超过 AcmeSMS 的频率限制，数值待 B-02。因为每个在途发送占用一条锁连接，并发度同时受数据库连接数约束（4.8）。轮询器不得被发送阻塞（D-07）。\n\n### 4.8 持锁、等待与超时（新增）\n\n**(a) 三个时点与结果。** 区分“占用提交”（数据库里记下一次尝试）、“调用”（外部请求从发起到结束）、“取消或归还提交”（用户操作生效）。取消或归还请求到达的时刻不同，结果如下：\n\n| 取消或归还请求到达时 | 对任一借用，AcmeSMS 请求的发起时点早于取消或归还事务的提交时点；提交之后零新请求。\n- **G2：** 若执行器在取消或归还请求到达时已持锁，则该事务的提交晚于该次请求的结束（完成、失败或超时）及结果写入。\n- **不在保证内：** 持锁会话被外部强制终止（如管理员终止会话、数据库故障切换）；见风险 8。\n\n**(c) 时限参数。** 全部为配置项，数值在实施前确定，其中 `H_max`。看门狗用于工作进程挂起、网络分区等无法自行结束的情形：数据库在锁连接空闲超过 `W_dog` 后终止该会话，锁被释放，等待者继续。此后该执行器恢复运行，会在“调用前确认”发现锁连接已失，不调用，记 `INTERRUPTED`（AC-28）。\n\n**(f) 连接与并发度。** 每个在途发送占用一条锁连接，持锁最长 `H_max`。并发度不得超过锁连接池大小，也要给占用连接、轮询器和借用模块留出 `max_connections` 余量。同一分钟到点的借用多于并发处理能力时，来不及占用的记 `MISSED`，不补发，不设上限（规则 9、15）。\n\n### 4.9 可观测性与预算核对\n\n- 每次状态转换写一条结构化日志，含 `loan_id`、旧状态、新状态、时间。每次 AcmeSMS 请求写一条含 `loan_id` 的日志。\n- 指标：各 `outcome` 的计数、`MISSED` 的计数、轮询每次耗时、从分钟起点到占用成功的延迟、每分钟到点数与占用数、持锁时长、取消/归还/改时间的锁等待时长。\n- **预算核对（累计口径，U-23、A-06）：**\n  1. 结构保证：`loan_id` 为主键，每笔借用至多一行、至多一次 `ATTEMPTED`（4.4 不变量）。\n  2. 累计核对：`state = 'ATTEMPTED'` 且（`outcome IS NULL` 或 `outcome` 不属于 `NO_VERIFIED_PHONE`、`PHONE_LOOKUP_FAILED`）的行数，即“可能发生过供应商调用的次数”，应不超过累计创建的借用数。\n  3. 请求日志核对：同一 `loan_id` 的 AcmeSMS 请求日志条数不超过 1。\n  4. 供应商账单对账（待 B-02 提供账单与分段口径）：账单条数不超过上面的次数乘以每次尝试的计费条数上界。\n  5. 每日发送数、每分钟到点数只作观测，**不设上限，也不据此阻断发送**。某一天的发送数超过当日新增借用数是正常现象，因为提醒按归还时间前 24 小时到点，而不是按创建日期到点。\n- 对 `MISSED`、`INTERRUPTED`、`PHONE_LOOKUP_FAILED`、写结果失败、持锁时长接近 `H_max` 设置告警，因为它们意味着有借用人没有收到提醒、结果不明，或锁等待异常。\n\n## 5. 边界与异常\n\n| 情形 | 行为 | 依据 |\n|------|------|------|\n| 创建时已不足 24 小时 | `NOT_SCHEDULED`，不发 |
