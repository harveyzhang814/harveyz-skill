# hskill list bundle 筛选：决定记录

创建日期：2026-10-17。状态：需求、方案、写前记录与 `spec.md` 0.1 均已批准；未决事项：无。

需求批准依据：用户在需求审查中明确批准 D-001 至 D-009、D-013，并确认 D-014 的 `bundleMeta` 键、大小写、`all` 与工具 bundle 边界。此次批准不覆盖 D-011、D-012；用户将其明确归为待选方案。随后用户在两次方案审查中分别选择 D-011、D-012。

写前记录批准依据：用户重新逐项核对修正后的当前决定、来源、依据及失效条目，明确表示它们完整、准确，并批准以此编写 Spec。该次批准仅覆盖写前记录；Spec 的独立批准见下。

Spec 批准依据：用户审查 `spec.md` 0.1 后明确表示「批准这份完整设计及其中标明的次要实现决定，作为后续开发依据」。批准覆盖 D-001～D-009、D-011～D-014；D-010 仍为已失效。当前批准版本为 0.1。

## 当前决定

### D-001 — 在 `hskill list` 增加按 bundle 查看技能的能力

- 状态：已批准
- 来源：用户原始需求
- 决定：支持类似 `hskill list --bundle research` 的调用，筛出指定 bundle 的技能。
- 依据：初始请求：「`hskill list` 输出太多，我想按 bundle 查看技能，比如 `hskill list --bundle research`」。

### D-002 — JSON 输出同样支持筛选

- 状态：已批准
- 来源：用户原始需求
- 决定：`--json` 与 bundle 筛选组合时只输出筛选结果。
- 依据：初始请求：「`--json` 也应支持筛选」。

### D-003 — 保持无筛选行为

- 状态：已批准
- 来源：用户原始需求
- 决定：没有提供筛选条件时，现有 `hskill list` 行为不变。
- 依据：初始请求：「无筛选时的行为不要变」。
- 补充依据：用户第一轮答复：「无筛选时原来的内容和格式都要保持」。

### D-004 — 此阶段只交付开发可用的设计

- 状态：已批准
- 来源：用户原始需求
- 决定：整理需求和实现方案，不写产品代码。
- 依据：初始请求：「请先把需求和实现方案整理成开发可用的设计，不写产品代码」。

### D-005 — 每次只筛选一个 bundle

- 状态：已批准
- 来源：用户选择
- 决定：`list --bundle` 一次接受一个 bundle 名称，无需逗号分隔的多 bundle 筛选。
- 依据：针对「一次筛选多个 bundle，还是只筛选一个」的问题，用户第一轮答复：「我只需要一次看一个 bundle」。

### D-006 — 筛选结果只展示技能

- 状态：已批准
- 来源：用户原始需求
- 决定：提供 bundle 筛选时，文本结果不展示 shell tools；JSON 不包含 shell tool 条目。
- 依据：用户第一轮主动补充：「筛选时只关心技能，不需要 shell tools」。

### D-007 — 需求场景

- 状态：已批准
- 来源：用户原始需求
- 决定：支持已知 bundle 名称的用户快速定位该 bundle 的技能，避免浏览整份列表或自行筛 JSON。
- 依据：用户第一轮主动补充：「我通常已经知道 bundle 名称，却要从很长的 `hskill list` 输出中逐项找，或先用 `--json` 再自行筛选」。

### D-008 — 筛选后的 JSON 形态

- 状态：已批准
- 来源：用户选择
- 决定：筛选后的 JSON 保留现有 `skills`、`tools` 两个字段，其中 `skills` 只含所选 bundle 的技能，`tools` 为 `[]`。
- 依据：针对「保留空 `tools` 数组还是省略字段」的问题，用户第二轮答复：「筛选后的 JSON 保留现有 `skills`、`tools` 两个字段，`tools` 取空数组」。

### D-009 — 无效 bundle 参数报错

- 状态：已批准
- 来源：用户选择
- 决定：bundle 名称不存在或 `--bundle` 缺少值时，清楚报错且非零退出；若有 `--json`，错误写到 stderr，stdout 无输出。
- 依据：针对「报错还是返回空列表」的问题，用户第三轮答复：「名称不存在或缺少值都应清楚报错并非零退出；配合 `--json` 时错误写到 stderr，stdout 不输出 JSON」。

### D-011 — 筛选后的可读格式沿用现有技能表

- 状态：已批准
- 类别：已选方案，不是用户原生需求
- 来源：用户选择
- 决定：有筛选时仍显示 `NAME`、`BUNDLE` 两列及现有排序方式，只显示匹配技能且不显示 `SHELL TOOLS` 区块；有效空 bundle 显示表头但没有数据行。
- 提议依据：Agent 根据无筛选格式保持要求及 `bin/cli.js` 当前双列表格提出沿用现有格式。
- 选择依据：Agent 提出 A（沿用双列表格、空 bundle 仅表头）与 B（仅列技能名、空 bundle 提示）后，用户答复：「选 A，沿用现有表格和排序；有效空 bundle 显示表头且没有数据行」。

### D-012 — 筛选逻辑保留在 CLI 的 `list` 分支

- 状态：已批准
- 类别：已选方案，不是用户原生需求
- 来源：用户选择
- 决定：在 `bin/cli.js` 的 `list` 分支中解析并验证 `--bundle`，直接筛选已读取的 `skills-index.json` 数据，再沿用现有排序与输出。同步更新 `list` 帮助和 CLI 使用说明、验证新增与无筛选路径；不更改其他命令和 MCP 的现有行为。
- 提议依据：Agent 根据 `list` 分支直接读取 `skills-index.json` 的现状提出局部实现；现有 `lib/bundles.js` 的 `resolveSkills()` 面向安装、读取版本且不支持有效空 bundle。
- 选择依据：Agent 提出 A（在 CLI `list` 分支筛选）与 B（在 `lib/bundles.js` 新增共享查询函数）后，用户答复：「实现路径也选 A，集中在 `bin/cli.js` 的 `list` 分支；按你所列范围更新帮助、说明和测试，保持其他命令与无筛选行为」。
- 事实修正：用户在写前复核指出 `bundle list` 可能不是现有命令；核查 `bin/cli.js` 后确认没有该子命令，`node bin/cli.js bundle list --json` 退出码为 1。已删去此前对它的错误引用。

### D-013 — 精确匹配索引中的 bundle ID，容许空 bundle

- 状态：已批准
- 来源：用户原始需求
- 决定：按索引中的 bundle ID 精确匹配；名称有效但暂时没有技能时成功返回空技能列表，JSON 为 `{"skills":[],"tools":[]}`。
- 依据：用户第三轮补充：「按索引中的 bundle ID 精确匹配；名称有效但当前没有技能时成功返回空技能列表，JSON 为 `{"skills":[],"tools":[]}`」。

### D-014 — 有效名称判定及特殊值

- 状态：已批准
- 来源：Agent 推断
- 决定：以 `skills-index.json` 的 `bundleMeta` 键作为有效技能 bundle ID；区分大小写；安装命令的特殊值 `all` 和 tool bundle ID 不属于有效技能 bundle ID。
- 依据：`skills-index.json` 将技能 bundle 登记在 `bundleMeta`，工具 bundle 登记在 `toolBundleMeta`；`all` 仅在 `lib/bundles.js` 的安装选择逻辑中使用。
- 批准依据：用户在需求审查中明确表示：「同意 D-014 所说的技能 bundle 使用 `bundleMeta` 键、区分大小写，`all` 和工具 bundle 不属于此筛选」。

## 已否定或已失效的决定

### D-010 — 使用现有 bundle 身份精确筛选

- 状态：已失效
- 来源：Agent 推断
- 旧决定：按 `skills-index.json` 中技能的 `bundle` 字段做精确、区分大小写匹配；有效名称从 `bundleMeta` 取，不把安装命令的特殊值 `all` 或 tool bundle 名称视为可筛选的技能 bundle。已登记但暂时无技能的 bundle 返回空技能结果。
- 原依据：`skills-index.json` 中 `bundleMeta` 与 `skills[].bundle` 分别记录名称及成员；`lib/bundles.js` 将 `all` 用于安装选择。
- 失效原因：用户明确补充精确匹配与空 bundle 规则；将用户决定与仍需复核的推断拆成 D-013、D-014。替代编号：D-013、D-014。
