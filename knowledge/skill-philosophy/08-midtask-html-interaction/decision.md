> 关联文档：[[research]] · [[principle]]
> 用途：把 `research.md` 里三种思路的取舍变量压缩成一份可直接对照的决策清单，供之后设计/审查某个 Skill 是否要引入"中途 HTML 交互"、以及引入哪一种时直接查用。

## 一句话结论

**中途 HTML 交互是内容驱动的特例工具，不是长任务的默认基础设施**——只有当候选内容本身有空间/图形结构、且你能明确回答下面两个问题时，才值得引入；答案的组合决定该用三种思路里的哪一种。

## 决策流程

```
Step 0: 内容本身是不是空间/图形性的？
        (布局、依赖关系图、UI 视觉设计、多方案 before/after 对比……)
        NO  -> 不引入 HTML，留在终端里用文字/AskUserQuestion 解决。
        YES -> 进入 Step 1

Step 1: 候选方案会不会被反复"重新生成"？
        (用户点了以后大概率要来回改好几轮，而不是选一次就完事)
        NO  -> 用【静态快照展示式】(MSkill improve-codebase-architecture)
        YES -> 进入 Step 2

Step 2: 这套交互能力要不要跨多个问题/多轮次长期复用？
        (不是为单个功能定制，而是整个技能流程里反复要展示/收集反馈)
        YES -> 用【通用会话服务器式】(Superpowers brainstorming/visual-companion)
        NO  -> 用【专用双向反馈服务器式】(G stack design-shotgun)
```

## 三条分支速查

| 分支 | 触发信号 | 用哪种思路 | 关键实现动作 |
|------|---------|-----------|-------------|
| A | 内容不是空间性的，或候选方案很少且一次性 | 不用 HTML | AskUserQuestion / 终端文字确认即可，见 [[principle]] 悬而未决问题 3 |
| B | 空间性内容 + 不会反复重新生成 | 静态快照展示式 | 写自包含 HTML 到系统临时目录，`open`/`xdg-open` 打开，终端里问"选哪个" |
| C | 空间性内容 + 会反复迭代 + 要跨多轮/多问题复用 | 通用会话服务器式 | 起通用轻量服务器（写文件驱动画面更新），按"看比读更容易懂"逐题判断要不要用它，离开时推 waiting 屏 |
| D | 空间性内容 + 会反复迭代 + 只服务单个功能 | 专用双向反馈服务器式 | 起专属服务/二进制，前端直接提交结构化 JSON 反馈，支持原地 reload 同一标签页，收到反馈后仍要口头复述确认 |

## 三条分支各自不可省略的底线动作

无论走哪条分支，以下几条是研究中三个生态**共同**做到、且省略后会明显变差的动作，实现时不要漏：

1. **产物路径要显式声明去哪、活多久**——系统临时目录即弃（分支 B）、项目目录但要求 `.gitignore`（分支 C）、用户级持久化目录（分支 D）三选一，不要默认写进代码仓库或让它无限堆积。
2. **即便有结构化回传，也保留一次终端确认**——三个生态没有一个完全信任浏览器端数据免检；`principle.md` 悬而未决问题 2 的结论就是"机器可读回传是增强项，终端确认是兜底项"，两者不是互斥关系。
3. **失败要有退化路径**——服务器起不来、端口占不到、CI/headless 环境没有浏览器时，必须能退回纯文字方案（内联展示 + AskUserQuestion），不能让整个流程因为 HTML 交互失败而卡死。

## 何时重新评估这份决策清单

如果之后研究发现某个生态开始把 HTML 用作**纯进度展示**（不承载任何决策内容），或者出现了真正的"用户点击立刻打断当前轮次"的推送机制（而不是"写文件 + 下一轮读"），这份清单的 Step 0 和"三个生态共同底线动作"部分需要重新审视——参见 `principle.md` 里"尚未解答的更深问题"的最后一条。
