### 核心命题

当 Skill 执行的任务较长、较复杂时，可以在执行过程中（而非仅在结尾）构建 HTML / web 页面，用来向用户展示结构化的进度，或收集用户需要做出的确认与选择——用可视化、可交互的中间产物，替代或补充终端里线性滚动的文字流，解决长任务"过程不可见、确认不直观"的问题。

### 悬而未决的设计问题

#### 1. 本地文件 vs 启动服务器

- **选项 A：生成静态 HTML 文件**。Claude 在任务过程中把当前进度/中间结果写入一个 `.html` 文件，提示用户用浏览器打开查看。实现简单，无需额外进程，但内容是"快照"，用户要看最新状态得重新打开或手动刷新；如果需要用户回传选择，无法在文件内完成，只能靠用户口头/手动告知。
- **选项 B：启动本地 web server**。支持页面自动轮询/推送最新状态，甚至提供表单/按钮做出选择后直接提交到本地接口，实现真正的实时刷新与回传。但需要额外起进程、管理端口/生命周期、处理并发和清理，复杂度和"意外常驻进程"的风险更高。
- **张力**：轻量单向展示 vs 实时双向交互，复杂度和"用完即走"的简洁性之间的取舍。

**研究结论**：三个生态给出三种不同答案，取舍变量是"candidate 是否会被反复重新生成"和"反馈是否需要结构化数据"——两者皆否用静态文件（MSkill `improve-codebase-architecture`）；两者皆是且值得为单功能投入专属服务用 HTTP 服务器（G stack `design-shotgun`，支持原地 reload 同一标签页）；需要长期跨多个问题复用同一套能力则走通用轻量服务器路线（Superpowers `visual-companion`，协议是"写文件驱动画面更新"）。详见 [[research]] 第四节·1。

#### 2. 双向回传机制

- **选项 A：用户手动回传**。HTML 页面只是展示/收集想法的媒介，用户看完后仍要回到终端里用文字告诉 Claude 自己的选择——HTML 本质上是"更好看的只读视图"，交互闭环仍然发生在对话里。
- **选项 B：机器可读的自动回传**。页面上的选择/表单直接写回一个本地文件（Claude 轮询读取）或通过本地 HTTP 接口提交，Claude 无需用户口头转述即可拿到结构化结果，实现真正的"点击即生效"。
- **张力**：实现简单、但依赖用户配合转述 vs 实现复杂、但交互体验无缝——机制复杂度与用户负担成反比。

**研究结论**：没有一个生态真正做到"点击即唤醒"（都不依赖 webhook 打断当前轮次）——共同模式是前端把选择写成文件，Claude 轮次先以某种方式结束（AskUserQuestion 阻塞或提示用户回终端），下一轮读文件。区别在于信任程度：MSkill 完全不做文件回传；Superpowers 有结构化事件文件，但明确说终端文字才是主渠道，浏览器数据只是补充；G stack 把 JSON 反馈当唯一权威来源，但收到后仍强制二次口头确认。结论是机器可读回传是可选增强项而非必需项，且即便做了也普遍保留终端确认作为兜底。详见 [[research]] 第四节·2。

#### 3. 什么任务值得用 HTML 而不是终端文本

- **选项 A：仅在信息密度/可视化诉求高时使用**（如多方案并排对比、图表、截图证据），终端文字进度对大多数长任务已经够用，HTML 是特例而非常态。
- **选项 B：只要任务足够长/步骤足够多就该有结构化进度视图**，无论内容是否需要可视化，HTML/结构化面板本身就比滚动文字更利于用户随时查看当前状态。
- **张力**：HTML 中途交互是"内容驱动的特例工具"，还是"长任务的通用基础设施"。

**研究结论**：明确倾向选项 A。只有 Superpowers 把判据写清楚了——"would the user understand this better by seeing it than reading it?"，且强调按问题粒度判断而非按会话。MSkill 和 G stack 没写判据但场景印证同一倾向：内容本身有空间/图形结构（架构依赖图、UI 视觉设计）才用 HTML。三个生态无一例外把 HTML 用于承载需要用户看懂/挑选的决策内容本身，没有一个把它当作纯粹的进度条或防焦虑工具。详见 [[research]] 第四节·3。

### 尚未解答的更深问题

- 如果 Skill 生态中普遍不存在"中途 HTML 双向交互"这种模式，是因为技术门槛/维护成本，还是因为终端本身的确认机制（AskUserQuestion 等）已经足够，HTML 交互被认为没有必要？
- 中途生成的 HTML 文件如何清理，是否会像本地日志/临时文件一样造成生态里的"遗留物"问题？（MSkill 写系统临时目录即弃；Superpowers 写项目目录要求用户手动 `.gitignore`；G stack 强制写用户级目录且永久保留——三种清理策略本身也是一层未展开的设计差异，值得单独研究。）
- 三个研究对象都没有用 HTML 做纯粹的"进度条"（只用于呈现决策内容），是否意味着"长任务缺乏可见进度"这个原始问题意识，在当前生态里根本没有对应的 HTML 类解法？这个问题本身可能需要另一轮独立研究。
