### 研究命题

Skill 在工作到一半时，是否会通过构建 HTML / web 页面来向用户展示任务进度，或收集需要确认的交互点？

### 问题意识

长任务（多步骤、执行时间长的 Skill）缺乏可见进度：用户在终端里只能看到文字流不断滚动，无法直观、结构化地了解当前进展到哪一步、还剩多少、每一步的中间结果是什么。

### 边界与例外

调查范围包括两类中途行为：
1. **中途实时交互**：任务执行过程中生成 HTML 页面，用户需要在上面点击/选择/确认，Claude 读取结果后继续执行（真正的双向闭环）。
2. **中途展示进度（单向）**：把进度或中间结果写成 HTML 供用户查看，但不需要用户回写任何内容，任务照常继续。

**明确排除**：任务完成后的最终交付物（如 `design-review` 生成的设计稿 HTML、`document-generate` 产出的文档）——那是终点产物，不是"中途"行为。

### 核心设计疑问

1. **本地文件 vs 启动服务器**：是生成一个静态 HTML 文件让用户用浏览器打开，还是启动一个本地 web server 支持实时刷新/回传？两者的取舍和适用场景是什么？
2. **双向回传机制**：如果需要用户在 HTML 页面上确认/选择，Claude 如何知道用户点了什么？是靠用户手动把结果粘贴回来、轮询本地文件、还是本地 HTTP 接口？
3. **什么任务值得用 HTML 而不是终端文本**：是否所有长任务都适合，还是只有特定类型（多方案对比、可视化数据）才值得引入 HTML 中途交互，终端文字进度为什么不够？

### 研究目标

不预设结论，把三个生态（G stack / Superpowers / MSkill）中实际存在的相关思路并列呈现，说明各自的适用场景、代价与取舍，供用户自行判断如何借鉴，而非直接给出一个推荐方案或强行收敛到共识。
