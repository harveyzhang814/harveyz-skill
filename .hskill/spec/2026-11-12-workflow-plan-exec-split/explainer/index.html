1. 定位：为什么要改

这套机制管的是“一个仓库里怎么开分支、在哪开工、怎么合回集成分支”。它被 devflow 的每一步用到：建档、写计划、交接、验收、合并。

现在同一套规矩被三处各自理解 读到的：

谁怎么理解规矩已经出的问题
init-workflow解析配置，生成 hooks 和工作流文档文档还写着“在当前工作树上切分支”“切到 staging 再 merge”，和现行流程相反
manage-worktree自己再解析一遍配置，推出基线；worktree 放哪写死在自己身上两份解析只要有一边改了解读，文档说的基线和实际建 worktree 用的基线就对不上，且不报错
compose-agentsmd集成分支、合并方式由人手填同一个集成分支要在两处手填

另外两件策略没有登记在任何地方：合并必须走脚本（只在 agent-canvas 的 hooks 里手写了拦截，harveyz-skill 没有），以及合并前要跑哪些项目检查（agent-canvas 的 token 预算写死在脚本里）。

2. 部件：谁解释，谁只读

部件职责不做什么
init-workflow（规划侧）唯一读配置、唯一做推断（集成分支、各类分支的基线、worktree 目录、合并目标、合并前检查）。一次运行同时写出下面四样产物，它们来自同一次解释不在任务里被调用；不替任何任务建 worktree 或合并
resolved.env解释结果，一行一个取值，提交进仓库。执行侧与 compose-agentsmd 之间的唯一契约不由人编辑；消费方逐行读，不当脚本执行
git-workflow.md给人和 agent 看的工作流文档，末尾有一块“项目自填区”，重跑不覆盖自填区以外的手改会被下次部署覆盖（会打印提醒）
git hooksgit 自动触发：拦截直接提交、拦截不经过脚本的合并、拦截推送里的违规提交不防恶意：手写一行合并标记就能骗过
合并脚本标准版，按配置写死目标分支；先跑项目检查，再无锁合并进本地集成分支不 push；不删 worktree 和分支
manage-worktree（执行侧）按任务做：准备、进入、离开、检测、合并。所需取值只从 resolved.env 来不解析配置；没有 resolved.env 就停，不猜
compose-agentsmd生成 AGENTS.md 时从 resolved.env 取集成分支不再接受手填的集成分支、合并方式

信任关系：消费方不信任自己对配置的理解，只信 resolved.env；resolved.env 又只信“集成分支上已提交的那份”（第 5 节）。

代价：改了配置但没重跑 init-workflow，所有产物和执行侧都停在旧取值上——彼此仍一致，但都是旧的。换来的是“同一时刻文档、hooks、脚本、执行侧说法一定相同”。另一个代价是仓库里多一个必须提交、不能手改的文件。

3. 调用时机总表

按“谁触发”分三类：人主动跑的、devflow skill 在固定步骤调用的、git 自动触发的。

动作什么时候谁触发读 / 写要不要人确认
init-workflow 部署仓库第一次接入；改了分支规矩；init-workflow 升级后人读配置；写 resolved.env、文档、hooks、合并脚本、.gitignore有冲突时逐条确认（沿用现有流程）
manage-worktree「准备」① init-spec 建档前（高档）
② develop-plan 第 1 步，带 spec 路径作锚点
③ handoff author 第 4 步，带计划或 spec 作锚点
④ 低档、琐碎档在改动前由 agent 直接调		devflow skill / agent读基线分支上的 resolved.env；必要时新建 worktree只在新建时确认一次（基线、分支名、路径）；复用不问
「进入」handoff verify（接手方开工前）、accept（交出方验收前）handoff读 resolved.env 做检测，然后进入不问；检测不过就打回
「检测」每个动作内部第一步；人也可单独要求其他动作 / 人只读不问
「离开」handoff 各方离开交接工作区时handoff不写；工作区保留不问
「合并」（新增）只在用户明确说“合并”，或项目指令规定时。独立任务：Step 7 由当前 agent 调；交接任务：交出方在 accept 通过后调agent，受人的指令驱动读 resolved.env；执行仓库里的合并脚本时机由人定；动作本身不再问
合并脚本被「合并」调用；没装新版 manage-worktree 时人或 agent 直接运行（兜底）「合并」/ 人只更新本地集成分支—
git hooksgit 自己触发：普通提交、合并提交、推送git按部署时写死的取值判断—
compose-agentsmd 生成人要生成或升级 AGENTS.md 时人读 resolved.env；写 AGENTS.md手改过的 AGENTS.md 要人同意才覆盖（沿用现有）
代价：「合并」不判断“该不该合并”，判断留给人和项目指令。好处是自动调用的 skill 不会自作主张合并；代价是每次合并都要人说一句。

4. 一个任务里的时序

在哪等待

整条链上只有两处停下来等人：新建 worktree 前的一次确认，以及“合并”这句话。其余调用（复用工作区、进入、检测、离开）都不问。读到的（Spec 5.5、D20）

在哪失败、失败后是什么状态

读不到解释结果时，「准备」直接停下，此时还没有建任何东西；「合并」的失败点见第 6 节，所有失败都停在“集成分支没动”的状态，唯一的例外是真实冲突——冲突标记会落在当前工作区，等人解决。

5. 执行侧怎么读到规矩

问题在于：resolved.env 在哪个检出里？主工作树可能正停在别的会话的分支上，你要进入的工作区也可能是部署之前建的老分支。两者里的 resolved.env 都可能是旧的，甚至没有。

所以执行侧分两步读 推出来的（构建者检查后的次要决定 S8，随 Spec 送审）：

步骤做什么为什么
① 引导从当前工作区或主工作树里随便取到一份，只用来知道“基线分支叫什么”不读任何文件就不知道集成分支是哪条
② 权威再去读基线分支上已提交的那份，以它为准输出新 worktree 从哪条分支拉出，就该用那条分支上的规矩
情形结果
主工作树停在别的分支、那里的文件是旧的不影响，取值来自基线分支
要进入的是部署前建的老分支「进入」「检测」照常；「合并」会因为老分支里没有标准脚本而停下，提示先把集成分支并入
基线分支上也没有这个文件（仓库还没部署新版）所有动作停下，提示先部署 init-workflow
代价：“没部署就停”是你在方案审查里选的（C1b）。新版 manage-worktree 一旦装进本机，其余 17 个还没重新部署的项目，devflow 会全部停下，直到逐个重跑 init-workflow。所以 Spec 规定本轮合并后不同步装机副本，装机与批量部署由你一起排期。

6. 「合并」的关卡

结果含义集成分支下一步
退出 0已合并，或本来就已包含前进一个合并提交push 另做；worktree 保留
退出 1出错，或项目检查（如 token 预算）没过没动按提示修，再「合并」
退出 2真实冲突没动冲突标记已落在当前工作区，解决并提交后再「合并」
退出 4仓库没部署新版 init-workflow没动先部署
拒绝不在 worktree 根、detached、或正站在集成分支上没动换到正确的工作区

“写入 staging”这一步是无锁的——多个 worktree 同时合并时，后到的一方发现目标分支被抢先移动，就重新试合并再写，不互相覆盖。这是现有脚本已有的机制，本轮只是把它标准化 读到的。

代价：老分支（部署前建的）里没有标准脚本，必须先把集成分支并入才能「合并」，多一步。换来的是不用从别的分支“借”脚本来跑，项目检查用的文件也一定和被合并的代码同版本。

7. 拦截：哪个 hook 在什么时候起作用

一个关键事实决定了拦截要放在哪：干净的手动 git merge 不会触发 pre-commit，只会触发 commit-msg 没查的（依据 git 文档，本会话处于 worktree 隔离无法实测，已排进计划首个任务与验收第 1 条）。这意味着现在 init-workflow 生成的“staging 只接受 feature/* 合并”检查，对干净合并其实不起作用。

操作pre-commitcommit-msgpre-push结果
在 staging 上直接提交拒绝——拒绝
在 staging 上手动 git merge（干净）不触发拒绝：没有合并标记—拒绝
手动合并有冲突，解决后 commit放行到下一关拒绝：没有合并标记—拒绝
标准脚本合并不触发任何 hook（脚本不走 commit 命令），提交信息自带合并标记放行通过
从远端同步 staging 产生的合并—放行（例外）放行（例外）通过
绕过本地 hook 后推送无标记的合并——拒绝：逐个检查推送的主线提交拒绝
代价：拦截靠的是提交信息里的一行标记，手写这一行就能骗过。目标是防误操作，不防有意绕过——你在方案审查里接受了这一点（C4a）。另一条路是不认标记、直接拦所有手动合并，但要为远端同步开更多例外，且少了推送这道关。

8. 部署：什么时候要重跑 init-workflow

场景要不要重跑不重跑会怎样
新仓库接入要没有 resolved.env，执行侧直接停
改了分支规矩、worktree 目录、合并前检查要所有产物和执行侧继续用旧取值（彼此一致）
init-workflow 升级要文档、hooks、脚本停在旧模板
只改了项目自填区不用—

第一次用新版重跑一个手改过文档的老仓库时：照旧整份覆盖，打印一行提醒和找回命令（你选的 C）。所以本轮在 harveyz-skill 和 agent-canvas 上，要先由人把需要保留的手写内容挪进自填区，再部署。agent-canvas 那份要挪的包括：合并脚本用法、“未自动同步”警告的处理、token 预算说明、冲突处理、主工作树常驻 staging 的问答 读到的。

9. 失败后停在什么状态

情形停在哪
仓库没部署新版manage-worktree 各动作停下（退出 4）；compose-agentsmd 报错；什么都没建、没写
配置里没有 feature 分支的合并去向不部署合并脚本和拦截；文档保留通用 merge 写法；「合并」报“未配置合并目标”
项目检查没过集成分支没动；退出 1，并说明哪条检查失败
合并冲突集成分支没动；冲突标记在当前工作区
装机副本还是旧版（没有「合并」）指令文件写明兜底：直接运行仓库里的合并脚本
文档或脚本被手改过、没有生成标记照旧覆盖，打印提醒和找回命令

10. 边界与判断

明确不做

  • manage-worktree 不清理：合并后不删 worktree、不删分支（留作以后）。
  • 不 push：合并只到本地集成分支。
  • 不标准化发布流程：模板里只改成“不切主工作树”，并指向项目自己的发布流程。
  • 本轮只部署 harveyz-skill 和 agent-canvas；File Translator 和其余 16 个项目以后再说。
  • 不验证 Codex 等非 Claude Code 宿主。

技术判断：“部署时一次解释、写成文件”把一致性问题从“三段代码各自理解”变成“有没有重跑部署”，后者可见、可检查（文件头记着版本和来源），前者是静默的。风险集中在过渡期：没部署的仓库会因为“没部署就停”而整体不可用，这是一次性成本，但发生时影响面大。

产品判断（依据只到代码与本仓库流程，未考虑其他使用者）：装机副本同步和 17 个项目的批量部署应当排在同一个时间窗口里做；先装机后部署，会在中间这段时间让这些项目里的 devflow 停摆。
