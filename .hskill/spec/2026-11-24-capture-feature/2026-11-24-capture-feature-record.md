## 当前决定

### D1 capture-vocab 的延伸：维护用户可感知的功能词汇及其层级

- **决定：** 新能力是 capture-vocab 的延伸，仍作为一个入口；维护项目里“产品功能地图”——对用户可感知的功能词汇，并自动维护它们之间的层级关系。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户原始需求——“这个需求属于 Capture vocab skill的延伸需求。它仍然是一个入口，但是涉及到项目里面的类似产品功能地图，它会维护特定对用户可感知的功能的词汇，然后自动维护这些功能词汇的一些层级关系。”

### D2 非全量检索

- **决定：** 词汇可检索，且检索不读全量，避免词汇膨胀后成本随之膨胀。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户原始需求——“这个词汇一方面要求可检索，而且是非全量检索的方式，避免膨胀之后。”

### D3 数据化存储，可扩展为类本体对象

- **决定：** 存储采用数据化形式（非 Markdown 散文），以对象形式存放，可扩展为类似本体的结构化数据。具体格式见 D14。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户原始需求——“它的存储方式最好是数据化的存储方式，这样后面方便拓展成结构化这一套数据的存在形式，应该是可扩展类似于本体的这种对象的形式存储。”

### D4 关联代码线索，按称谓直达代码

- **决定：** 当前要建立的关联之一是代码线索：拿到功能称谓即可经线索直接找到对应代码，不需要全量搜索。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户原始需求——“目前它所需要建立的关联关系一个是码线索。这样的话拿到这个产品地图对应的称谓，它就可以去直接通过线索去找到对应的代码，不需要全量。”

### D5 维护版本；capture 中的产品功能描述路由到这套数据；跨项目通用

- **决定：** 功能需维护版本（含义见 D9）；capture 过程中出现的产品功能描述路由到功能地图；形式跨项目通用，任何项目都适用。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户原始需求——“这个功能是需要维护一定版本的，这样子的话就把 Capture 部分产品功能的描述需要路由到这个数据存在形式，这个是跨项目通用的形式，任何一个项目都会这样一套产品的功能”。

### D6 先做独立初步版本，未来接入 PRO

- **决定：** 本轮做独立、轻量的初步版本，不依赖 PRO（product-requirement-ontology）服务；未来再接入 PRO，PRO 可能为此改造。因此数据形状不必硬对齐 PRO 当前模型，但须可导出、可映射。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户选择——问题：“功能地图和 PRO 是什么关系？”选项：A 独立轻量、形状对齐 PRO / B 直接用 PRO 当存储 / C 两者无关。答复：“先做一个初步版本，未来再接入PRO，PRO有可能也会因此改造。”
- **依据：** PRO 已有 `Feature`、`Component`、`implements: Component → Feature` 与 ModelVersion（`~/Projects/product-requirement-ontology/docs/superpowers/specs/2026-09-15-pro-mvp-scope-design.md`）。

### D7 独立 skill `capture-feature`，capture-vocab 路由过去

- **决定：** 拆成独立 skill（暂名 `capture-feature`），自有数据与脚本；capture-vocab 继续只管领域术语，`add` 时若判定为用户可感知的功能则路由给功能地图；查词时两边都查（见 D19）。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户选择——问题：“功能地图在形态上和 capture-vocab 怎么相处？”选项：A 独立 skill / B capture-vocab 子命令 / C 取代 vocab.md。答复：“A，拆成独立 skill”。
- **依据：** capture-vocab 的 `SKILL.md` 每次 invoke 全文注入上下文，刻意只留查词路径（`skills/coding/capture-vocab/SKILL.md` 维护者注）。

### D8 归属判据：用户可感知的都进功能地图

- **决定：** 用户能直接看到或操作的东西——界面区域、功能、交互入口——进功能地图，以类型字段区分；内部机制与抽象概念留在 capture-vocab。`add` 时由 agent 按此判据判归属、说出结论、等用户确认。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户选择——问题：“哪些词归功能地图、哪些留 capture-vocab？”选项：A 用户可感知的都进、类型区分 / B 只收能力。答复：“A，用户能感知的都进功能地图”。

### D9 版本 = 产品发布版本

- **决定：** 每个功能记录引入、变更、废弃所在的产品发布版本，可查“某版本时有哪些功能”；地图自身的修改历史交给 git（数据文件随仓库）。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户选择——问题：“维护一定版本指什么版本？”选项：A 产品发布版本 / B 地图快照 / C 两者都要。答复：“A”。

### D11 版本号来源与记录时机

- **决定：** 版本号取项目自身版本（如 `package.json` 的 `version` 或 git tag）；存量功能可填“未知”。初版不挂发版钩子，由 `add` / `update` 时记录。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** Agent 推断——依据：初版范围从简；跨项目的版本来源各异，不宜在初版自动化。

### D12 层级：单父树、仅“包含”关系，agent 提议、用户确认

- **决定：** 层级为单父树，只有“包含”一种关系；新增或修改时脚本给出候选父节点（按名称、别名、代码路径相近），agent 选定，随条目交用户确认后写入；提供 `check` 命令报告孤儿、环与失效父节点引用。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户选择——问题：“层级关系自动维护到什么程度？”选项：A agent 提议、用户确认、单父树 / B 同 A 但多父 DAG / C 全自动。答复：“A”。

### D13 代码线索 = 路径 + 可选符号名；agent-canvas 试点迁移

- **决定：**
  1. 代码线索为文件路径加可选符号名（组件、函数、store 字段等），不记行号；一个功能可有多条；`check` 验证路径存在、符号可被 `rg` 搜到，失效只报告不自动修。
  2. agent-canvas 为首个试点：把其 `.hskill/capture-vocab/vocab.md` 中按 D8 归功能地图的词迁移过去，迁走的从 vocab 删除、不留双份；迁移清单（归属与父节点）一次列出逐条确认。其他项目按需接入。
- **状态：** 已批准（question-me 摘要确认）
- **来源：** 用户选择——问题一：“代码线索的粒度？”选项：A 路径+符号 / B 路径:行号 / C 目录级。答复：“A”。问题二：“已有功能词迁移与试点？”选项：A 试点迁移并删除原条目 / B 不迁移 / C 迁移但保留原条目。答复：“A”。
- **依据：** agent-canvas 的 vocab.md 共 346 行，`_Reference_` 多为 `文件:行号`（如 `PanelArea.tsx:55`），代码改动后会漂移。

### D14 存储格式：一个对象一个 JSON 文件

- **决定：** 每个功能对象存为 `<project-root>/.hskill/capture-feature/features/<id>.json`；脚本扫描目录做匹配，只把命中条目、父链与直接子节点返回给 agent。不用单文件 JSON/JSONL，不用 SQLite，不用 YAML。
- **状态：** 已批准（方案审查，用户选择）
- **来源：** 用户选择——问题：“存储格式？”选项：A 一个对象一个 JSON 文件 / B 单个 JSON/JSONL 文件 / C SQLite（另提折中：按顶层功能分片）。用户先追问“会不会导致文件膨胀？项目开发时整体 grep 的效率是否会因此大幅降低？”，经核实后答复“1选a”。
- **依据：**
  - D2 的“非全量”约束的是进入 agent 上下文的量；脚本本地扫描后只返回命中条目即满足。
  - 实测：1000 个典型对象文件内容不足 1 MB（磁盘按 4 KB 块计约 3.9 MB），Python 全量读取解析 0.034 s。
  - `.hskill/` 是隐藏目录，`rg` 默认跳过：agent-canvas 中 `rg --files` 见 0 个 `.hskill/` 文件，`--hidden` 时见 1040 个；仓库已跟踪 11465 个文件。
  - 单文件在多会话并行新增时易冲突；SQLite 为二进制，无法 diff 与合并（前次 capture-vocab 检索设计否决 SQLite 的同一理由，本决定与之一致）；YAML 需额外依赖 PyYAML。

### D17 层级关系用固定字段 `parent`

- **决定：** 对象用单个字段 `"parent": "<id>" | null` 表达“包含”层级，不引入通用的类型化关系列表。以后要加其他关系或对接 PRO 时再做数据迁移。
- **状态：** 已批准（方案审查，用户选择）
- **来源：** 用户选择——问题：“对象里的关系怎么表达？”选项：A 通用类型化关系列表（初版只开放 `part_of`）← 推荐 / B 固定字段 `parent`。答复：“2选最简单的层级关系”。
- **代价：** 新增关系类型时需迁移全部对象文件；对象带 `schema` 版本号以便迁移脚本识别（见 Spec 次要决定）。

### D18 区分 `aliases` 与 `avoid`

- **决定：** 对象有两个别名字段：`aliases`（可通用的别称）与 `avoid`（应避免的叫法，每项可附简短说明）；两者都参与匹配，卡片分两行展示，「避免」行带说明。迁移时 vocab 的 `_Avoid_` 转入 `avoid`，说明取自原括号内容。
- **状态：** 已批准（构建者检查后，用户选择）
- **来源：** 用户选择——问题：“迁移时 `_Avoid_` 怎么处理？”选项：A 拆 `aliases` + `avoid` 两字段 ← 推荐 / B 只有 `aliases`，丢说明。答复：“1，a”。
- **依据：** vocab 的 `_Avoid_` 兼有匹配与“别用旧叫法”两层作用（capture-vocab `references/project-setup.md`）；只用 `aliases` 会丢失后者。

### D19 有功能地图时每次查词都调用 capture-feature；skill 须精简、渐进披露

- **决定：** 项目存在 `.hskill/capture-feature/` 时，capture-vocab 的 `query` 无论 vocab 是否命中，都 invoke capture-feature 的 `query`；capture-vocab 的 `add` 查重也同样调用。因每次查词都多注入一份 capture-feature 的 `SKILL.md`，该文件必须精简，只留查词路径，其余按需在 references 中渐进披露。
- **状态：** 已批准（构建者检查后，用户选择）
- **来源：** 用户选择——问题：“什么时候查功能地图？”选项：A 两边都查，capture-vocab 直接调兄弟脚本 ← 推荐 / B 维持仅 vocab 未命中才查 / C 每次都 invoke capture-feature skill。答复：“2，C，所以skill要注意精简和渐进式披露”。
- **依据：** 整句查询时 vocab 只要命中任一词就不会兜底，功能地图会被漏查（构建者检查发现）。
- **取代：** 原 Spec v0.1 草稿中的 S13（未命中才两跳）。
