# CLAUDE.md 评审判据（C1–C17）

每条给**判据**（怎样算命中）、**怎么查**（具体动作）、必要时给**代价**（遵守它要付出什么）。
标 `[阻塞]` 的命中后不修就会真的出错；标 `[建议]` 的是累积成本，不致命。

---

## 一、读者

### C1 读者是 agent，不是人 [建议]

表达形式按"agent 能不能稳定解析"取舍，不按"人看着直不直观"。ASCII 流程图、艺术字对齐、
需要视觉扫描才成立的排版，换成章节编号层级或表格——编号本身就是层级，不必在视觉上重建一次。

**怎么查**：文档里每处图形化表达，问"换成编号/表格会丢信息吗"。不丢就换。

**代价**：人快速扫读时不如图直观。这是有意识付出的代价，不是疏忽。

### C2 写进去的指令必须 agent 真能执行 [阻塞]

凡是"调用 X"的句子，先查 X 的可调用性。人工触发的东西只写"它归谁触发、agent 不代跑"，
**绝不把它的步骤抄进来**——抄了就是给 agent 一条它执行不了的指令：它要么照着手跑（绕过了
那个机制存在的理由），要么在那里卡住。

**怎么查**：grep 文档里所有被点名的可执行体，逐个读它的声明。skill 看 frontmatter 的
`disable-model-invocation` / `user_invocable`；CLI 看它在不在 PATH、要不要交互式输入；
工具看当前 harness 给没给。

## 二、内容归属（占评审工作量的一半以上）

### C3 只写流程，不写执行体怎么执行 [阻塞]

文档只承担三样：**每一步什么时候发生、判据是什么、要落什么产物**。被调用的 skill/脚本
自己怎么执行、有哪些边界和坑，去读那个执行体。

**怎么查**：逐条问"这句如果删掉，是不是还有另一个地方写着同一件事"。两处都写，改了一处
就会对着打架——**这是删除的唯一理由，不是"太长了"**。

### C4 脚本已经自动处理的，不写 [阻塞]

默认优先靠脚本修复，不靠文档叮嘱人绕开。机制加了自动处理之后，当初的"注意……"就变成了
死约束，而它读起来像经验。

**怎么查**：读脚本源码确认它真的处理了，不凭记忆、不凭 README。

### C5 不越过执行体规定手法 [阻塞]

**怎么查**：句子里出现具体命令、文件路径、匹配方式，而这个动作有现成的 skill/脚本——就是
越界。改成"调那个 skill"，把手法交回去。

典型形态：文档写"先 grep `<某个数据文件>` 查该词条（不要把整篇读进上下文）"，而那个 skill
的 query 操作本来就规定了匹配方式和只读命中段落——文档该写的只有"优先调它查"。

### C6 对照读权威源，不读拷贝 [阻塞]

装机副本、vendored 拷贝、镜像目录都会落后于源仓库。

**怎么查**：对照前确认读的是源（skill 看它的源仓库，不是 `~/.claude/skills/`），版本号能
对上再开始。拿落后的副本做对照会同时造出两类误判：把"源里已修"读成"还没修"，把"源里还缺"
读成"重复了"。

### C7 执行体自己缺了该有的约定 → 改上游 [建议]

不要在下游文档里替它补。

**代价**：上游改完到下游生效之间有窗口期。**窗口期内下游那段不能删**——删早了，这条知识
在真实环境里会有一段时间完全不存在，而那段时间恰好是最容易踩坑的时候。

### C8 决定保留时，要说得出"唯一载体" [建议]

保留的理由只能是"这条知识在别处没有"，不能是"写着也没坏处"。

**怎么查**：对每条打算保留的，写一句"它在 X 里没有、在 Y 里也没有"。写不出来就是该删。

## 三、规定到哪里为止

### C9 只规定优先级和时机，不规定未定情况下的应对 [建议]

"优先查 X"是约束；"查不到就去做 Y"通常不是——那是当场才知道的判断，写死会把多种情况压成
一种（有的词本来就自明，有的该去翻代码，有的该反问用户）。

**怎么查**：找"如果……就……"的兜底分支，问分支里装的是硬约束还是判断。是判断就删。

### C10 不写已经不存在的约束 [阻塞]

机制变了、警告还留着，比没有警告更糟——它看起来像是经验，agent 会绕开一个并不存在的坑。

**怎么查**：每条"注意/警告/不要"，去执行体里找它现在还成不成立。

## 四、组织结构

> C11–C14 只适用于**流程主导型**文档（大部分内容围绕一条主流程展开）。
> 不是这种形态的，整组跳过并说明，不要硬套。

### C11 围绕主流程组织全文 [建议]

与流程无关的内容另起章节、集中在前面。理由：大部分内容本来就是围着流程长出来的，不按主
流程排，约束就会散落到判断不出归属的地方。

### C12 流程简述 + `Step N` 编章 [建议]

开头一段流程简述（N 步一览），之后严格按 `Step N` 编章，一步一章。

### C13 每一步的标准和执行细则写在它自己那一章 [阻塞]

**怎么查**：随便挑一条约束，问"它属于哪一步"。答不上来，就是散的。散落的约束会被同时当成
"到处都要遵守"和"哪儿都不归我管"。

### C14 章内统一槽位，缺的整节省略 [建议]

每章内部用固定槽位、编号与顺序不变，说明是说明、标准是标准、执行细则是执行细则，
Special Case 单独成节、不混进正文。本步没有的那一节**整节省略**，不留空标题。

**代价**：有的步骤会只剩一两个槽位、显得空。但槽位缺席本身是信息——它说明这一步没有判据
或没有特例，比塞点东西填满诚实。

### C15 分类由内容决定，不是固定几类 [建议]

"流程 / 执行细则 / 标准"是**分离原则的例子**，不是章节清单。原则是"同类内容归一处、不同类
不混写"，具体分几类由这份文档实际装了什么决定。

## 五、精简方式

### C16 压措辞，不外迁内容 [建议]

主文件仍是唯一入口。外迁的代价是多一跳，而且被移走的那份很容易失联——**除非**那个目标文件
本来就是该内容的权威载体（那属于 C3 的归属问题，不属于精简）。

### C17 规则落仓库文件，不落 agent 的私有 memory [阻塞]

memory 只有写它的那个 agent 读得到、会陈旧、接手方访问不到。一条给所有人的规则，唯一载体
不能是一个只有一个人能看见的文件。

**怎么查**：评审中发现的每条该留的规则，确认它落在仓库里的具体文件，而不是"我记住了"。
