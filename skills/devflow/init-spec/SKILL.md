# 从初步想法到 Spec

本技能依据 question-me 澄清并经用户确认的需求，记录关键决定、审查方案并写出 Spec，避免凭未经确认的理解做决定。

## 触发条件

用户已决定要做、需要在实现前形成获批 Spec 时使用，例如“比较几个方案”“写个设计 Spec”“把想法做成 Spec”，或要做的新功能仍有未定需求或关键选择。

不触发：
- 只需澄清一个模糊请求、不需要成文 Spec → `question-me`
- 新建 skill → `init-skill`
- 已有获批 Spec，要拆成实施任务 → `develop-plan`

## 两份文档

- **决定记录（`record.md`）：** 按决定组织，保存当前决定及被否定或修订的旧决定，供用户核对与追溯；它不是按时间排列的审计日志。
- **Spec（`spec.md`）：** 写明获批需求、选定方案、实施约束与验收标准，供后续制定计划和实现使用，不依赖决定记录补齐关键决定。

## 第一阶段：取得需求摘要并记录决定

1. **简单任务：** 信息充分且用户已批准完整描述的简单任务，直接完成并说明结果。
2. **取得摘要：** 会话中若已有一份本会话内经用户确认的 question-me 摘要（用户从 question-me 转入），直接使用；否则按名调用 `question-me`，并告知它由 init-spec 发起。用户贴入的摘要不视为已批准：把它交给 question-me 作为已知信息，按 question-me 摘要的七个字段补问缺口，再请用户确认一次。
3. **澄清：** question-me 澄清并经用户确认摘要后，把摘要交回本技能。
4. **建档：** 只依据这份摘要建决定记录，不回看对话历史。用户对摘要的确认即为需求批准，直接进入第二阶段。

**非正常出口。**
- question-me 判定为发散型并停下，或用户在澄清中决定不做：本技能随之结束，不建决定记录，告诉用户方向收敛后可重新发起。

建档前调用 `manage-worktree` 的「准备」，在返回的工作区里写决定记录与 Spec，并按项目 Git 规则提交；`manage-worktree` 不可用时停下，告诉用户需要安装 `devflow` bundle 中的 manage-worktree；返回“不适用”时在当前目录继续。

**按摘要建档。** “用户原始需求”字段中每项建一条来源为用户原始需求的决定；“决定”字段中每项建一条决定，来源沿用摘要标注；“已查明事实”只在构成决定依据时引用；“假设”中的项作为 Agent 推断建条目；“未决”中的项建为“已提出”状态的条目，在第二阶段处理。摘要已确认的条目标“已批准”，批准依据写“question-me 摘要确认”。

### 记录决定

**当前决定。** 边对话边将每项影响需求、范围或关键方案的决定写成有唯一编号的独立条目，逐条标明决定内容、状态、依据及以下一种来源：

- **用户原始需求：** 用户直接提出的要求或主动修正，附足以核对原意的原话和出处。
- **Agent 推断：** 由用户要求或项目事实推导的决定，以及 Agent 作出的次要决定，附推导依据；用户批准不改变其来源。
- **用户选择：** 用户回答 Agent 的澄清问题或从方案中作出的选择，附问题、相关选项及答复的必要摘要。

**否定与修订。** 用户否定的旧决定标“已否定”，与用户原话不符或被修订取代的标“已失效”；移入单独部分，保留原编号、旧表述、来源、原因及替代编号（如有），并重审依赖旧决定的条目。新决定另建编号，不沿用旧决定的批准状态。

**随对话更新。** 决定形成、用户答复或核查结果出现时，更新条目及其“已提出、待审、已批准、已否定、已失效”状态，并关联批准依据；调查事实只在构成决定依据时引用，不另记调查流水。

**保存位置。** 默认将决定记录保存到工作区根目录下的 `.hskill/spec/YYYY-MM-DD-<topic>/YYYY-MM-DD-<topic>-record.md`；日期取首次建档日，同一任务修订沿用原目录及文件名，独立任务同名时在 topic 后加序号；用户指定位置优先。

## 第二阶段：确认需求与方案

**需求确认与人工闸门。** 需求批准来自用户对 question-me 摘要的确认，不再重复提交需求条目审查。此后任何阶段出现影响需求的新问题，由你自行补充提问（不重新调用 question-me），按“记录决定”规则更新并重新送审；修改须重新提交，批准只覆盖展示内容。

**方案形成标准。** 以获批需求为依据，比较产品与实现路径，排除不满足要求者；对架构、核心机制、关键交互等含有你推断或决定的重大选择，逐项提交至少两种可行方案，说明运作逻辑、需求依据、收益、代价、风险、假设及推荐理由；仅有一种可行方案时，说明其他路径被排除的原因。用户选择或修正后才将方案记为已批准，以其选择为批准依据，并更新决定记录。

**试做。** 对方案可行性拿不准时，经用户同意可做用后即弃、无需完整测试和规划的试做，把发现写回决定记录。

**前端设计稿审查。** 前端视觉或交互变动适合用设计稿评估时，调用 `sync-design` 的设计模式；多方案先以文字说明逻辑与取舍，再询问用户是否需要设计稿对照，经同意后制作并展示，将反馈纳入方案审查，设计稿不代表方案已获批准。

## 第三阶段：编写与审查 Spec

### 确定详略

Spec 只保留影响实现或验收的细节，详略随任务复杂度调整，不决定后续工作模式。

- **简单需求：** 简明写清目标、范围、关键行为、方案与验收标准。
- **复杂需求：** 展开流程、系统边界、数据与接口、核心机制、状态与异常、约束及取舍，使构建者无需猜测关键决定。

### 书面设计

写作前核实方案依赖的现状，缺乏依据时补查；若结果改变获批决定，更新决定记录并重新送审。

只将决定记录中当前已批准的决定，以及标明由你决定、随 Spec 一并送审的次要决定写入 Spec，使该领域有能力的构建者无需追问即可制定计划；补充实施所需的现状、约束和未核实前提，标明版本、审查状态、已批准范围及未决事项，送审稿不得预记为已批准。

**内容标准。** 写清意图、目标、范围、不可接受结果与验收依据，以及影响实现或验收的现状、约束和必须保持的既有行为；按需展开对象与场景、产品能力与流程、架构与核心机制、关键交互、数据与接口、状态及异常路径和重要取舍。标明关键决定的依据与来源（用户原始需求、Agent 推断或用户选择），引用决定编号供追溯；仅将不改变用户认可结果的实施细节留给构建者。

**一致性检查。** 送审前按获批需求核对 Spec 的正常、变更、异常及并发路径、图示、验收和估算；方案修订后重查受影响的旧验收用例，确认同一场景的需求、规则、流程及验收结果一致。无依据者标待核实，冲突或歧义提出方案及影响、更新决定记录并重新送审；批准后发现则暂停交付。

**可视化辅助。** 图示有助于理解或审查 Spec 时，在相关内容旁嵌入 UML 或其他技术图示，优先用 Mermaid 绘制，用于快速审查而非精美展示；图示须标明关键元素、关系、条件和异常路径并与正文一致。文字足够清楚时无需绘制，图示不代替关键决定的文字说明。

**保存位置。** 将 Spec 保存为决定记录同目录下的 `YYYY-MM-DD-<topic>-spec.md`。

**构建者检查：** 简单任务由你按构建者视角自查；复杂任务用本目录的 `builder-check-prompt.md` 派未参与对话的全新子代理独立检查，无子代理工具时自行检查。交付前只找阻碍制定计划、且误判会改变用户认可结果的缺口，并分为三类：

- **已有答案：** 从获批需求、选定方案或项目事实补入 Spec，并标明依据。
- **次要决定：** 不改变用户认可的结果；自行决定并在 Spec 中标明。
- **必须由用户决定：** 答案会改变需求或关键方案；需求问题按「需求确认与人工闸门」处理，方案问题返回方案审查，并取得批准。

必须由用户决定的问题按影响排序、集中提问；更新决定记录与 Spec 并附上自行决定事项后，再交付用户审查；同时提交决定记录中上次批准后新增或改动的条目及否定与修订部分，供用户核对是否准确反映此前结论。

**批准后同步。** 用户批准 Spec 后，在决定记录中标明获批 Spec 版本、覆盖的决定及批准依据，在 Spec 中标明当前批准版本、范围和未决事项，并同步两处状态；仅修正状态标记可沿用原批准，内容变更须重新送审，消除相反或过时标记后再制定计划。

<HARD-GATE>
用户批准完整描述之前，不得开始构建：小改动批准聊天中的描述，项目批准设计文档。构建包括编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用实现类技能。阅读与探索可以进行。

有两个例外。如果他们明确表示不要 Spec、要求直接构建，本技能即告结束，这道门槛也随之解除。经他们同意、在方案审查中做的试做可以构建；它始终标记为用后即弃，如果要保留试做成果，就属于新请求，必须重新经过这道门槛。

项目文档获批后，下一步是制定计划。对于软件项目，调用本 `devflow` bundle 的 `develop-plan` 技能，传递已批准的 Spec 路径、版本和范围；计划与 Spec 放在同一目录。沿用默认命名时，计划文件名为 `YYYY-MM-DD-<topic>-plan.md`，其中日期和 topic 与 Spec 一致。此处不得调用其他技能。
</HARD-GATE>
