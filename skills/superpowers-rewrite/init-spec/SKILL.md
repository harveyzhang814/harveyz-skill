# 从初步想法到 Spec

本技能帮助你在构建前核实用户想要什么、为什么想要，避免凭未经确认的理解做决定；通过提问厘清尚未成形的需求，才能依据用户意图处理他们未提及的选择。

## 两份文档

- **决定记录（`record.md`）：** 按决定组织，保存当前决定及被否定或修订的旧决定，供用户核对与追溯；它不是按时间排列的审计日志。
- **Spec（`spec.md`）：** 写明获批需求、选定方案、实施约束与验收标准，供后续制定计划和实现使用，不依赖决定记录补齐关键决定。

## 第一阶段：对话并记录决定

回复前判断是否已理解用户的目标及原因：信息充分且用户已批准完整描述的简单任务直接完成并说明结果；缺少影响结果的信息则进入对话。

### 你的第一条消息

发出第一条消息前，根据任务描述判断用户是在探索目标与方向，还是已有明确目标、只待确定方案；勿以描述长短判断或向用户询问分类。

- **探索性：** 以一个具体、开放的问题引出情境、动机或期望，例如：“你通常在什么时刻，会希望已经有这样一个东西？”
- **定义性：** 简短承接已定目标，只问最影响方案的一个未定事项，不重开已定内容。

问完即止。

### 对话方式

依据任务定位进入探索性或定义性对话，意图变化时切换；两者共用澄清标准和人工闸门，只问现有信息无法回答、且能减少方案不确定性的具体问题；每轮沿用用户词汇、先说关键内容，末尾只问一个问题，不用流程术语。

#### 探索性对话

**信息依据。** 从用户的场景、经历和问题中发现需求，将自己的解释标为待确认推断。

**提问方式。** 用具体场景的开放问题引导用户描述；卡住时给选择方向，要求建议时给可纠正的具体方案。

**推进方式。** 内部比较问题解释和可能方向，排除违背用户动机者；必要时经用户同意做用后即弃、无需完整测试和规划的试做，并把发现带回对话。

#### 定义性对话

**信息依据。** 以用户明确的目标、成功标准和范围为已知，查阅相关资料并自行确认可查明的事实。

**提问方式。** 只问影响方案的需求缺口或冲突，按依赖与影响排序；每轮给出互斥且覆盖主要方向的选项、自定义入口、推荐及依据，不凑虚假选项，架构等方案选择留待方案审查。

**推进方式。** 据回答更新已定事项，增删待问问题；次要事项可提出标明由你决定的默认处理，纳入人工审查。

### 共同澄清

**共同澄清范围。** 以下六项是产品或开发需求能否进入方案形成的标准，不作为逐条提问的脚本：

- 目标用户、使用场景、问题及解决时机
- 新增或改变的产品能力与关键用户流程
- 成功标准、范围边界及不可破坏的现有行为
- 现有产品、代码、接口、数据、依赖及已做尝试
- 参考产品或功能，以及希望借鉴或避免的做法
- 影响方案的质量要求与技术约束

**结束条件。** 逐项标明已明确、待确认或不适用及原因；继续澄清影响方案的空缺，其余假设留待人工审查，用户说“够了”也不能代替确认剩余空缺和风险。

**核查现状。** 现有实现会影响需求或方案时，在任务方向足以确定范围后，边澄清边查阅相关代码、配置、接口、测试和文档；范围较大时可派只读子代理并行调查。将查明的事实及依据、未核实的假设带回对话，据此调整问题和需求清单；查看当前项目以外的个人文件、数据或网络前，说明范围并由用户决定。

**阶段性复述。** 每弄清一部分需求，就用约 200–300 词复述其用途、对象或运作方式，标明用户所述、用户从选项中作出的选择及你的推断，并以一个纠错问题收尾；复述与提问交替，最后覆盖剩余内容，但不替代决定记录的人工确认。

### 记录决定

**当前决定。** 边对话边将每项影响需求、范围或关键方案的决定写成有唯一编号的独立条目，逐条标明决定内容、状态、依据及以下一种来源：

- **用户原始需求：** 用户直接提出的要求或主动修正，附足以核对原意的原话和出处。
- **Agent 推断：** 由用户要求或项目事实推导的决定，以及 Agent 作出的次要决定，附推导依据；用户批准不改变其来源。
- **用户选择：** 用户回答 Agent 的澄清问题或从方案中作出的选择，附问题、相关选项及答复的必要摘要。

**否定与修订。** 用户否定的旧决定标“已否定”，与用户原话不符或被修订取代的标“已失效”；移入单独部分，保留原编号、旧表述、来源、原因及替代编号（如有），并重审依赖旧决定的条目。新决定另建编号，不沿用旧决定的批准状态。

**随对话更新。** 决定形成、用户答复或核查结果出现时，更新条目及其“已提出、待审、已批准、已否定、已失效”状态，并关联批准依据；调查事实只在构成决定依据时引用，不另记调查流水。

**保存位置。** HSkill 系列每项任务将决定记录保存到项目根目录下的 `.hskill/spec/YYYY-MM-DD-<topic>/YYYY-MM-DD-<topic>-record.md`；日期取首次建档日，同一任务修订沿用原目录及文件名，独立任务同名时在 topic 后加序号。其他任务询问保存位置，用户指定位置优先。

## 第二阶段：复核决定并确认需求与方案

**需求确认与人工闸门。** 形成方案前，提交决定记录中与需求有关的条目及其依据、状态和来源，用户逐项审查并明确批准后才形成方案；修改须重新提交，批准只覆盖展示内容。

**方案形成标准。** 以获批需求为依据，比较产品与实现路径，排除不满足要求者；对架构、核心机制、关键交互等含有你推断或决定的重大选择，逐项提交至少两种可行方案，说明运作逻辑、需求依据、收益、代价、风险、假设及推荐理由；仅有一种可行方案时，说明其他路径被排除的原因。用户选择或修正后才将方案记为已定，并更新决定记录；影响方案的新需求须重新澄清并通过人工闸门。

**前端设计稿审查。** 前端视觉或交互变动适合用设计稿评估时，调用 `sync-design` 的设计模式；多方案先以文字说明逻辑与取舍，再询问用户是否需要设计稿对照，经同意后制作并展示，将反馈纳入方案审查，设计稿不代表方案已获批准。

**写前复核。** 写 Spec 前向用户提交决定记录中的当前决定及否定与修订部分，逐项核对是否完整、准确反映此前结论；纠正后重新提交，明确批准后按覆盖范围同步各决定的状态和批准依据，再写 Spec。

## 第三阶段：编写与审查 Spec

### 确定详略

Spec 只保留影响实现或验收的细节，详略随任务复杂度调整，不决定后续工作模式。

- **简单需求：** 简明写清目标、范围、关键行为、方案与验收标准。
- **复杂需求：** 展开流程、系统边界、数据与接口、核心机制、状态与异常、约束及取舍，使构建者无需猜测关键决定。

### 书面设计

写作前核实方案依赖的现状，缺乏依据时补查；若结果改变获批决定，更新决定记录并重新送审。

只将决定记录中当前已批准的决定写入 Spec，使该领域有能力的构建者无需追问即可制定计划；补充实施所需的现状、约束和未核实前提，标明版本、审查状态、已批准范围及未决事项，送审稿不得预记为已批准。

**内容标准。** 写清意图、目标、范围、不可接受结果与验收依据，以及影响实现或验收的现状、约束和必须保持的既有行为；按需展开对象与场景、产品能力与流程、架构与核心机制、关键交互、数据与接口、状态及异常路径和重要取舍。标明关键决定的依据与来源（用户原始需求、Agent 推断或用户选择），引用决定编号供追溯；仅将不改变用户认可结果的实施细节留给构建者。

**一致性检查。** 送审前按获批需求核对 Spec 的正常、变更、异常及并发路径、图示、验收和估算；方案修订后重查受影响的旧验收用例，确认同一场景的需求、规则、流程及验收结果一致。无依据者标待核实，冲突或歧义提出方案及影响、更新决定记录并重新送审；批准后发现则暂停交付。

**可视化辅助。** 图示有助于理解或审查 Spec 时，在相关内容旁嵌入 UML 或其他技术图示，优先用 Mermaid 绘制；图示须标明关键元素、关系、条件和异常路径并与正文一致。文字足够清楚时无需绘制，图示不代替关键决定的文字说明。

**保存位置。** HSkill 系列将 Spec 保存为决定记录同目录下的 `YYYY-MM-DD-<topic>-spec.md`；其他任务沿用用户指定的位置。

**构建者检查：** 简单任务由你按构建者视角自查；复杂任务用本目录的 `builder-check-prompt.md` 派未参与对话的全新子代理独立检查，无子代理工具时自行检查。交付前只找阻碍制定计划、且误判会改变用户认可结果的缺口，并分为三类：

- **已有答案：** 从获批需求、选定方案或项目事实补入 Spec，并标明依据。
- **次要决定：** 不改变用户认可的结果；自行决定并在 Spec 中标明。
- **必须由用户决定：** 答案会改变需求或关键方案；返回相应的澄清或方案审查，并取得批准。

必须由用户决定的问题按影响排序、集中提问；更新决定记录与 Spec 并附上自行决定事项后，再交付用户审查。

**批准后同步。** 用户批准 Spec 后，在决定记录中标明获批 Spec 版本、覆盖的决定及批准依据，在 Spec 中标明当前批准版本、范围和未决事项，并同步两处状态；仅修正状态标记可沿用原批准，内容变更须重新送审，消除相反或过时标记后再制定计划。

<HARD-GATE>
人类伙伴批准完整描述之前，不得开始构建：小改动批准聊天中的描述，项目批准设计文档。构建包括编写产品代码、搭建脚手架、安装依赖、创建项目，以及调用实现类技能。阅读与探索可以进行。

有两个例外。如果他们选择跳过提问，本技能即告结束，这道门槛也随之解除。经他们同意的探索性试做可以构建；它始终标记为用后即弃，如果要保留试做成果，就属于新请求，必须重新经过这道门槛。

项目文档获批后，下一步是制定计划。对于软件项目，调用本 `superpowers-rewrite` bundle 的 `develop-plan` 技能，传递已批准的 Spec 路径、版本和范围；计划与 Spec 放在同一目录。沿用 HSkill 默认命名时，计划文件名为 `YYYY-MM-DD-<topic>-plan.md`，其中日期和 topic 与 Spec 一致。此处不得调用其他技能。
</HARD-GATE>
